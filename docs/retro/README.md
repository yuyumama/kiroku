# kiroku の使い方

Kiro での開発中の記録と現在のハーネスを比較し、改善案を文章で作ります。
目的は、同じ指摘・説明の繰り返しとハーネス整備の負担を減らすことです。不具合・作業失敗も分析します。

現在は評価段階です。週次を想定して手動で専用エージェントを呼びます。
自動起動・自動採否・適用・過去の提案管理は今後の対象です。
実装の対応範囲と製品上の検証状況は [互換性調査](compatibility.md) と [評価手順](evaluation.md) を参照してください。

## 必要なもの

- Kiro CLI V3 または Kiro IDE 1.x（旧 IDE 0.x は対象外）
- Python 3.9 以降、Git。Python の追加パッケージは不要
- Windows の導入は PowerShell、Linux/macOS は POSIX shell

公式の Kiro 導入手順は [Installation](https://kiro.dev/docs/getting-started/installation/) にあります。
CLI・IDE の認証は利用するアカウントで行います。

## 導入と更新

Linux/macOS:

```bash
sh /path/to/kiroku/install.sh /path/to/project
sh /path/to/kiroku/install.sh /path/to/project --update
```

PowerShell:

```powershell
& C:\tools\kiroku\install.ps1 -Target 'C:\work\my project'
& C:\tools\kiroku\install.ps1 -Target 'C:\work\my project' -Update
```

既定の Python 起動名は POSIX が `python3` です。
PowerShell で `-PythonCommand` を指定しないときは、`python`、`py -3`、`python3` の順に、Python 3.9 以降として動くものを探して使います（`python` が動く環境では、これまでどおり `python`）。どれも動かなければ、何も変えずに止まります。
Windows Python Launcher を使う場合は `-PythonCommand 'py -3'` を指定します。指定した起動名も、探すときと同じく Python 3.9 以降として動くかを確かめ、動かなければ、その名前と理由を出して何も変えずに止まります。
選択した起動名を、フック・専用エージェントのシェル許可規則・スキルの実行例に反映します。
起動名を指定しない更新（`--update`／`-Update`）では、導入済みのフックが使っている起動名を引き継ぎます。引き継いだ起動名がこの環境で Python 3.9 以降として動かないときは、フックが動かず記録が止まるおそれがあるので、注意と、動く起動名を指定して更新し直すコマンドを表示します。案内する起動名は、実際に起動して確かめたものだけです（フックは Kiro の環境で動くので、表示が出ても動く場合があります）。PowerShell で探した起動名は、インストーラーを動かすのに使うだけで、フックの起動名は変えません。変えるときは、更新のときに起動名を指定します。
`uninstall.ps1` も、起動名を指定しないときは同じ順に探します。
PowerShell のこの探し方は、Windows でも Linux 版 PowerShell でもまだ実行して確かめていません（未検証）。
`install.py` は両インストーラーの共通処理です。

既存の同名ファイルが異なる場合、通常導入は変更前に止まります。
`--update`／`-Update` では配布ファイルを更新しますが、既存の `config.json` は書き換えません。導入先で書いた設定を消さないためです。

この版から、ノートを読み終えたかどうかを、要約表示で見せた期間で判定します。以前の版で書いたノートには、その記録がありません。更新のあと最初の振り返りでは、ノートのあるセッションも「読んだ範囲の外に発話あり」として読み直しの対象になります。既存のノートは消さず、指摘を残したまま書き直します。手作業は要りません。1回に読む量は `retro_read_chars` で区切られ、残りは次の振り返りで読みます。

`config.json` に書くのは、変えたい項目だけです。書いていない項目は、スクリプトが持つ既定値で動きます。
kiroku の更新で設定項目が増えても、`config.json` に書き足す必要はありません。更新のときに、既定値で動く項目が表示されます。

| 項目 | 既定値 | 意味 |
|---|---|---|
| `tests` | `[]` | テスト実行とみなすコマンドと、JUnit XML の場所 |
| `sessions_dir` | なし | セッションログの場所。IDE のエクスポートを使うときに指定する |
| `write_tools` | `fs_write`、`fs_append`、`str_replace` | 書き込みとして記録するツール。書いた値は既定値に足される |
| `ignore_paths` | `.kiro/kiroku/data/**`、`.git/**` | 記録しないパス。書いた値は既定値に足される |
| `output_tail_chars` | 2000 | 失敗時に残す出力の末尾の文字数。0 にすると残さない。負数や数でない値は既定値で動き、`install --update` が知らせる |
| `retro_read_chars` | 50000 | 1回の振り返りで読む量の上限（文字数の見積もり） |
| `retro_output_chars` | 20000 | 集約の出力の長さの目安。超えるときは各一覧を上位だけに絞る。全件は `--section <節>` で出す |
| `test_start_max_seconds` | 3600 | テストの実行前に控えた記録を、終わりの記録が来ないまま残す秒数。最初の値で、根拠は薄い |

`write_tools` と `ignore_paths` は、既定値を置き換えずに足します。古い版の値が `config.json` に残っていても、新しい既定値は有効です。
旧 `prompt_max_chars` は現在使いません。

```text
.kiro/
├── hooks/kiroku.json
├── agents/kiroku-retro.json
├── skills/kiroku-retro/
│   ├── SKILL.md
│   ├── references/    harness-guide.md（案の形の選び方）
│   └── scripts/       record.py、aggregate.py、excerpt.py、prompts.py、harness.py、notes.py、ledger.py、review.py
└── kiroku/
    ├── config.json
    └── data/          events.jsonl、ledger.jsonl、notes/、reports/ など
```

`data/` はインストーラーが `.gitignore` に追加します。コード・出力・秘密値が含まれうるため、コミットや PR に含めません。
更新前に記録したユーザー発話本文は自動削除しませんが、集約には利用しません。

導入後、CLI は `/hooks`、IDE は Hooks の画面で5本の記録フックの読み込みを確認します。テスト実行前の `PreToolUse` と、ターンの終わりの `Stop` も必要です。
CLI と IDE には共通の v1 フック形式を使います。製品上の発火・入力形式は評価手順で確認してください。

## 記録するもの

| イベント | 内容 |
|---|---|
| `tool_failure` | シェル失敗のコマンド、終了コード、出力末尾 |
| `tool_cancelled` / `tool_timeout` / `tool_denied` | 人による取り消し（承認画面での Escape、Ctrl+C、Deny once）／タイムアウト／権限規則による拒否。応答の全体（先頭を含む）の文言で、記録の時点で分ける。集約はその種類を使い、出力の末尾から決め直すのは、この印（`judged`）が無い古い記録だけ |
| `write` | ファイルのパス、内容ハッシュ、コミット |
| `prompt` | 発話の時刻と session ID。本文は保存しない |
| `test_run` | 設定された JUnit レポートと、その時点の Git 状態 |
| `recording_gap` | 未知のシェル応答、理由の分からない未完了、終わりが記録されなかったテスト実行（`test_end_missing`）など、判定できなかった実行 |

通常の成功したシェル実行と kiroku 自身のコマンドは記録しません。
`/kiroku-retro` の発話、または集約スクリプトの実行より後は、振り返りの会話として扱います。同じセッションのそれ以降の発話と記録は、集約から除きます。
テスト実行の記録には、merge や rebase の最中だったかどうかも残します。その最中の失敗は、回帰候補ではなく「マージ中の失敗」に分けます。
`execute_bash` と `execute_pwsh`、書き込みは `fs_write`・`fs_append`・`str_replace` とファイル保存フックに対応します。
シェル応答は既存の `Exit Code:` 形式を解析します。未知の応答を成功扱いにはしません。

### 実行後のフックが呼ばれない場合

失敗や拒否の記録は、実行後のフック（`PostToolUse`）で行います。次の2つの場合は、このフックが呼ばれません（Kiro CLI 3.3.0 で実測）。

- 別のフックが、実行前にコマンドを止めた。
- 実行が始まったあとに、Ctrl+C で中断された。

この2つは、集約のときにセッションログから拾い、「実行前に止められた呼び出し」「実行中に中断された呼び出し」として出します。対象はシェル実行です。
拾うのは、ログで状態が `denied` または `failed` で、応答に `Exit Code` の行が無く、権限の規則による拒否でも承認画面での取り消し・拒否でもないものだけです。応答に `Exit Code` があるものは、実行後のフックで記録済みなので数えません。
止めたフックと理由はログに残りません。同じターンでそれまでに動いたフックの名前を候補として出しますが、止めたフックとは限りません。フックの定義ファイル（`.kiro/hooks/`、`~/.kiro/hooks/`）で実行前（`PreToolUse`）以外と分かるフックは、候補から外します。定義が見つからないフックは残します。
この2つは表示だけで、改善案の「対象の型」にはできません（採用後の追跡の対象外）。回数は、レポートの検証値（`unrecorded_calls`）に入ります。ログが無いセッションでは拾えません。
発話が集計期間の外でも、呼び出しが期間内なら拾います。完了していないシェル実行のうち、結果の行が無いもの、形式が想定と違うものは、止められたとも中断とも決めず、「記録の不足」に `unreadable_tool_call` として出します。

コマンド・出力は秘密値らしい文字列をマスクしますが完全ではありません。
記録処理の異常で本来の開発を止めず、`data/record-errors.log` にエラーを残します。
同時フックによる記録・JUnit 読込状態の競合は、OS のファイルロックで直列化します。

## テスト結果を取り込む

導入先の `.kiro/kiroku/config.json` に設定します。

```json
{
  "tests": [
    {"match": "\\bpytest\\b", "report": "reports/junit.xml", "format": "junit"}
  ],
  "sessions_dir": null
}
```

`match` はテストコマンドの正規表現、`report` はプロジェクトルートからの相対パスです。glob が使えます。
テスト側で毎回 JUnit XML を出す設定が必要です。設定がない場合はテスト結果の取り込みを行いません。

`match` は、まず起動先（実行プログラム、Pythonのスクリプト／モジュール、makeやnpm等のタスク名）に対して照合します。起動先として解釈できるのは、単一コマンド、先頭の `cd DIR &&`、末尾のリダイレクトです。これはシェルを実行する機能ではありません。

起動先で一致しないときは、コマンドの文面全体に対して照合します。パイプ（`pytest | tail -20`）、前置き（`uv run pytest`、`PYTHONPATH=. pytest`）、展開を含む実行がここに入ります。`echo pytest` のような言及もここに入るので、文面で一致したものは次のように扱います。

- 実行の前後で JUnit レポートが変わっていれば、テスト実行として結果を取り込みます。
- 変わっていなければ、テスト実行には数えず、「テスト結果の記録不足」に「文面で一致」と付けて出します。実行か言及かは判定しません。終了コードが0以外なら、ツール失敗としても記録します。

PowerShellの複雑な構文と、Windows／IDEの製品上の挙動は未検証です。

導入時は普段の実行方法を宣言して、設定の一致を確認します。例えば次のコマンドはテストを実行せず、検出設定・JUnitの設定・記録フック5本（名前、トリガー、`record.py` を呼んでいるか）の定義だけを診断します。足りないフックは、名前と、それが無いと記録されないものを出します。定義があることと、Kiro が実際にフックを発火させることは別です。

```bash
python3 .kiro/skills/kiroku-retro/scripts/doctor.py --command "python3 run_tests.py"
```

続いて、そのテストコマンドをKiroから実行し、`aggregate.py --section summary` で `test_run` と結果の取り込みを確認します。テスト記録0件は成功の証拠ではありません。

古いJUnitは、実行前後のファイル状態を比べて取り込みを防ぎます。実行前フックがない場合は `missing_test_start`、変化がない場合は `report_stale`、対応する実行が一意に分からない場合は `ambiguous_test_run` として結果を保留します。レポートの指定（`report`）が違っても、同じファイルを指しうる実行が重なったときは保留します（`reports/*.xml` と `reports/junit.xml` など）。ファイルの状態は更新時刻・大きさ・置き換えで比べ、権限の変更だけでは「変わった」としません。globの一部だけが古い場合も保留します。実行開始の記録は本文やコマンドの複製を含まない識別値としてstateに保持します。

Kiro の異常終了などで実行後のフックが来ないと、実行開始の記録が state に残ります。残っている間は、同じレポートを使う実行を `ambiguous_test_run` として保留します。この記録は `test_start_max_seconds`（既定 3600 秒。最初の値）を過ぎると、次のテスト実行の前に捨てます。捨てた記録は集約には出ません。期限より長くかかるテストの途中で別のテストが始まると、長いほうの結果は `missing_test_start` として保留します。

残った実行開始の記録は、期限を待たずに、同じセッションのターンの終わり（`Stop`）と次の発話（`UserPromptSubmit`）で閉じます。別のフックに止められたテスト実行や、実行中に中断したテスト実行がこれに当たります。閉じた記録は、「記録の不足」に `test_end_missing` として出します。取り消したターンでは `Stop` が呼ばれないため、次の発話で閉じます。閉じた記録には、実行が始まった時刻（`started_at`）を残し、集約はその時刻で期間と振り返りの前後を決めます。

制約：閉じたあとに、同じセッションで同じコマンドのテストをやり直し、その実行中に、閉じたほうの実行後フックが遅れて届いた場合は、新しい実行の記録と取り違えます。この順序が Kiro で起きることは確かめていません。Kiro には実行の途中で発話を送る機能があります。Kiro CLI 3.3.0 で各1回試した範囲では、割り込み（Steer）では次の発話のフックは呼ばれず、キュー（Queue）では実行と `Stop` が終わったあとに呼ばれました。実行中のテストの記録を閉じることはありませんでした。ほかのバージョンで実行中に呼ばれる場合は、記録を閉じてしまい、その結果は `missing_test_start` として保留になります。

バックグラウンドで起動したテスト実行（`run_in_background`）は、処理が終わる前に実行後のフックが呼ばれ、終了コードは起動の成否を表します。この場合は結果を読まず、`background_not_finished` として「テスト結果の記録不足」に出し、テスト実行の回数には数えません。バックグラウンドの処理が終わったことは分からないので、その結果は取り込みません。テスト結果を記録したいときは、テストをバックグラウンドにせず実行してください。
起動の記録は、同じレポートの「書き手が残っている」印として state に残します。裏の処理がレポートを書くまでの間に始まった通常のテスト実行は、どちらの結果か確かめられないので `ambiguous_test_run` として保留します。裏の処理が書いたかどうかは、通常の実行が終わった時点のレポートの状態を控えておき、次の実行の前にそこから変わっているかで判定します。通常の実行が書き換えただけでは、書き終えたとはみなしません。書き終えたと分かったあとか、期限（`test_start_max_seconds`）を過ぎたら、印を消します。裏の処理と通常の実行が同時に書いた場合は区別できないので、期限まで保留が続きます。レポートを書かずに終わったバックグラウンドの実行があると、期限まで保留が続きます。

失敗の集約と追跡は、先頭の作業場所指定と末尾のリダイレクトを除いたコマンド全体を使います。パイプや連結（`|`、`;`、`&&`）がある場合は、その手前までを使います（`npm run build 2>&1 | tail -20` は `npm run build`）。それでも解釈できないもの（`$` の展開、引用されていない `*.txt`・`~/x`・`{a,b}` などのファイル名の展開を含むもの）は、先頭3語でまとめます。旧版のレポートの対象は「先頭3語が同じ失敗すべて」を指します。その失敗がすべて今の同じ見出しに入るときだけ追跡し、複数の見出しに分かれる場合は、完全に一致する実行があっても「数えられない」とします。旧版のレポートかどうかは、検証値（`kiroku-facts`）の有無で見分けます。検証値のあるレポートの対象は、今の見出しに完全に一致する実行だけを数えます。過去のイベントや台帳は書き換えません。書き込みは直近の内容・発話区切り・集計期間で二重フックをまとめ、A→B→Aの復元も数えます。

分類は記録時ではなく集約時に行います。

| 分類 | 根拠 |
|---|---|
| Red 候補 | 全テスト成功後に新しく観測されたテスト、またはテストファイルの変更 |
| 回帰候補 | 過去に通っていたテストで、テストファイルの変更を確認できない |
| その他 | 基準になる成功記録や Git 状態などが不足 |

これは原因や意図の確定ではありません。テスト追加、部分実行、環境要因、flaky test などを会話・差分と照らします。
ファイルの内容差分も変更者を証明しないため、「人間の手直し候補」は確認材料として扱います。

## 会話はログから二段階で読む

会話本文を kiroku に複製保存しません。

1. セッションを1件ずつ要約表示で読み、改善候補を見つけます。
2. 候補の前後だけ、AI 応答・ツール実行を読みます。

ログの探索対象は、そのプロジェクトのイベントに登場する session ID と、ログの `session.json` の作業フォルダがこのリポジトリ（またはその配下）を指すセッションです。
後者により、フックが1度も動かなかった会話（質問だけのセッションなど）も一覧に出ます。一覧の「記録」の列が「ログのみ」になります。
CLI の既定探索先は `~/.kiro/sessions/*/<session_id>/messages.jsonl`（`KIRO_HOME` 指定時はその配下）。
ログの内容形式は公開された安定 API ではありません。ログがない・読めない・一部壊れている場合は不足を表示し、会話に基づく判断を保留します。
エージェント名は `session.json` の `agentMode` から読み、セッションの一覧・要約・レポート検証値の `session_agents` に出します。これはセッション単位のメタデータで、途中の切り替えは復元していません。メタデータが無い場合は未確認とし、権限拒否の `agent-profile` という文言から名前を推測しません。
サブエージェントのログは自動収集しません。

IDE の内部保存場所は決め打ちしません。Export Chat で保存した ZIP を、例えば git 対象外の `data/exports/` に展開し、設定します。

```json
{"sessions_dir": ".kiro/kiroku/data/exports"}
```

対応する配置は `<sessions_dir>/<session_id>/messages.jsonl`、その間に1階層ある配置、または `sessions_dir` 自体がセッション ID のディレクトリである配置です。
絶対パスも指定できます。ZIP は自動展開しません。本文形式の実機互換性は別途確認が必要です。

発話を全部読むと量が多すぎるため、次の3つで量を抑えます。

- **セッション一覧**：集約結果に、セッションごとの発話数と、振り返りノートの有無が出ます。
- **1件ずつの要約表示**：ユーザー発話は原文（長ければ頭と末尾）、その後のツール実行は件数、応答は最後の1件の冒頭だけを出します。
- **振り返りノート**：読み終えたセッションの要点を `data/notes/<session_id>.json` に残します。次回はノートを使い、ログを読み直しません。

```bash
python3 .kiro/skills/kiroku-retro/scripts/aggregate.py --since 7d
```

```bash
python3 .kiro/skills/kiroku-retro/scripts/aggregate.py --since 7d --session <session_id>
```

1回の振り返りで読む量は、件数ではなく文字数の見積もりで区切ります。集約の「未読のセッション」に、未読の合計と、今回読む分（新しい順に、上限に収まるところまで）が並びます。
短いセッションなら数十件、長いセッションなら数件になります。上限は `config.json` の `retro_read_chars`（既定 50,000 文字）で変えられます。

未読が残った場合は、集約とレポートに件数が出ます。もう一度 `/kiroku-retro` を実行すると、続きから読みます。ノートがあるセッションは読み直さないので、何度実行しても重複しません。

ノートで読み終えたとみなすのは、ノートを書く前に、要約表示（`--session`）で見せた期間に入る発話だけです。要約表示を出すたびに、その期間（開始と終わりの時刻）を `data/state.json` に控えます。会話の本文は控えません。
集約のセッション一覧の「振り返りノート」は、次のどれかです。「ノートあり」以外は、読み直しの対象として「未読のセッション」に入ります。

| 表示 | 意味 |
|---|---|
| 未読 | ノートが無い |
| ノートあり | 期間内の発話が、すべて読み終えた範囲に入っている |
| ノートの後に発話あり | ノートを書いた後に発話が増えた |
| 読んだ範囲の外に発話あり | ノートより前の発話に、要約表示で見せた記録が無いものがある。期間を前回より広げたとき（`--since 7d` で読んだ後に `--since 30d` で集約したとき）など |
| ノートを読めない | ノートが JSON として読めない、または `findings` が配列でない |

読み直すときは、既存のノートの指摘を残し、新しい指摘を足して書き直します。
全発話を全文で読みたいときは、予備として `--prompts` と `--prompt-offset` によるページ表示が使えます。対象は集約のセッション一覧と同じで、フックの記録が無くログだけがあるセッションも含みます。
フックの記録が1件も無くても、会話のログがあれば振り返りはそのセッションを読みます。記録が無いことは、これまでどおり「記録の不足」に出します。

```bash
python3 .kiro/skills/kiroku-retro/scripts/excerpt.py --session <session_id> --index <index> --context 3
```

`index` は要約表示に出ます。実行イベントから探す場合は `--around <時刻>` や `--command "<一部>"` を使います。
長い項目には続きの `--offset` を表示します。中身を保存せず、必要な範囲を出力します。
旧 `--conversation` は廃止しました。

## 振り返りを実行する

CLI は作業セッションと別に、専用エージェントを起動します。

```bash
kiro-cli chat --agent kiroku-retro
```

IDE は専用エージェント `kiroku-retro` を選び、新しいチャットで同じスキルを呼びます。

```text
/kiroku-retro
```

skillを現在の通常エージェントで呼ぶだけでは、専用エージェントの権限には切り替わりません。最初の集約の `--require-agent` は、`KIRO_SESSION_ID` とセッションメタデータの `agentMode` を照合します。確認できなければレポート作成を止め、どの確認に失敗したか（`KIRO_SESSION_ID` が無い、ログが見つからない、`agentMode` が無い）を表示します。この照合は実測済みのログ形式に依存するため、Kiroの形式が変わった場合も未確認として止まります。
`sessions_dir` は過去の開発セッションを探す場所です。実行中の振り返り自身のログ（専用エージェントの確認と、「確認済み」の照合に使う）は、`sessions_dir` に無ければ Kiro の既定の置き場（`~/.kiro/sessions/`、`KIRO_HOME` があればその下）も探します。CLI で実測した置き場です。IDE で実行中のセッションをどこから確認できるかは未検証で、確認できなければ止まります。

レポートは、スクリプトが骨組みを作ります（`aggregate.py --new-report`）。対象期間、件数、ハーネスの所在（範囲・パス・存在）、記録の不足（止められた呼び出し、中断された呼び出しの回数を含む）、前回の未判断の案の一覧、末尾の検証値（`kiroku-facts`）は、スクリプトが記録から書きます。振り返りのエージェントが書くのは、「【ここに書く…】」の欄（型、改善案、様子見、表の「確認の状態」と「役割」、補足）だけです。
保存後の `aggregate.py --check-report <保存先>` は、スクリプトが書いた行が順番どおり残っていること、欄がすべて埋まっていること、「対象の型」が集約にあること、案の番号（`P1` など）が1つのレポートの中で重複していないこと、表に「未確認」があるのに冒頭が「なし」になっていないことを確かめます。欄が埋まっているかは、目印（【ここに書く…】）が残っていないことに加え、各欄の値・節の本文・表の列が空でないことで見ます。「なし」と書いた欄は埋まっているとみなします。欄に書かれた文章の意味、引用の経緯、提案の妥当性は判定しません。別途本文で確認します。
型と改善案の中の主張には、出どころを示す引用を付けます（`引用（利用者）`、`引用（応答）`、`引用（ファイル）`）。検査は、引用がそのセッションの発話、またはそのファイルに実在することを確かめます。会話からの型には利用者の発話の引用、原因を述べるときは応答またはファイルの引用、既存のファイルを挙げたときはそのファイルの引用が無いと、不一致になります。引用が実在しても、その解釈が正しいとは限りません。ファイルの引用は、リポジトリの中と `~/.kiro` の中だけを対象にします。
骨組みには、振り返りをしているセッション（`KIRO_SESSION_ID`）を書き、`data/state.json` にも控えます。検査は、表で「確認済み」としたファイルについて、そのセッションのログに本文を取得した記録があるかを確かめます。数えるのは、成功した `read_file`、skill の読み込み（`load_resource`）、自動で文脈に入った資料（`steering_inclusion`）です。一覧（`list_directory`）や検索（`file_search`、`grep_search`）は数えません。記録が無ければ不一致です。セッションが分からない、ログを読めない、ログに今回の骨組みの作成がまだ記録されていない、のいずれかのときは、照合できないと表示し、不一致にはしません。確かめるのは本文を取得した記録だけで、内容を正しく読んだかどうかは判定しません。
欄が残っている書きかけの骨組みは、レポートとして数えません。目印だけを消して値が空の欄があるものも、同じ判定で書きかけとします。前回の未判断の案は、書き終えるまで未判断のまま残ります。骨組みの目印（`<!-- kiroku-report:3 -->`）の無い以前のレポートは、今までどおり検証値と対象の型だけを照合します。以前の版のレポート（目印なし、版1、版2）の検証値は、その版が出していた項目と判定で比べます。版3で足したハーネスの所在（`AGENTS.md`）は含めず、未読の数は版2までの既読の判定（ノートを書いた後に発話が無ければ既読）で数えます。振り返りで読むセッションは、これまでどおり今の判定で決めます。版2のレポートは、版2の骨組みを作り直して、スクリプトが書いた行も照合します。更新しただけで、以前に検査を通ったレポートが不一致になることはありません。最初の形（`kiroku-report:1`）のレポートは、欄の残りだけを見ます。版2（`kiroku-report:2`）のレポートには「載せなかった案と理由」「補足と、利用者に確かめたいこと」の行が無いので、ある行と節だけで空欄を見ます。引用の決まりは当てはめません。案が0件の最新レポートも最新として扱い、`P1`だけの指定で古い案へ戻ることはありません。古い案を指定するときは `レポート名#P1` と書きます。

既定は直近7日。期間は後ろに指定できます。
PowerShell の実行例は、導入時に選んだ `python` または `py -3` に読み替えてください。

比較するのはプロジェクト内とユーザー共通の steering・hooks・skills・agents・MCP 設定、および関連する開発設定です。
原則としてプロジェクト内の変更を提案し、共通設定の変更は他プロジェクトへの影響とともに別提案にします。
記録がない場合も、README・コード・開発設定から必要な初期ハーネスを検討します。

レポートは `data/reports/YYYY-MM-DD-HHMM.md` に保存します。同じ分にもう一度 `--new-report` を実行したとき、作り直すのは、同じセッションが作ったまま手を付けていない骨組み（作った時点の内容と一致するもの）だけです。書き始めたもの、別の振り返りが作ったものは上書きせず、`YYYY-MM-DD-HHMMSS.md`（同じ秒なら末尾に `-2` 〜 `-9`）の名前で新しく作ります。名前は文字列の順が時刻の順になるので、最新のレポートの判定は変わりません。
改善案は文章で書きます。既存設定との対応、変更の内容、その形を選んだ理由、期待する効果と確かめ方を含めます。
差分は作らず、ハーネスも変更しません。適用するかどうかは、レポートを読んだ人が決めます。必要性がなければ提案は「なし」です。

会話からの型は、原則として2つ以上の別のセッションに根拠があるものだけを挙げます。
案の形の選び方と、既存の決まりが効かなかった理由の切り分けは、skill の `references/harness-guide.md` にまとめています。Kiro の公式ドキュメントの推奨に基づきます。

専用エージェントの書き込みはレポートと振り返りノートの配下、シェルは集約・抜粋・台帳のスクリプトに制限します。
シェルの許可規則は、許可したスクリプトに渡す引数までは制限できません（[Permissions](https://kiro.dev/docs/permissions/) の Pattern matching。`*` は任意の文字列に当たる）。スクリプトが書くのは、すべて `--root` で決まるリポジトリの `.kiro/kiroku/data/` の下です。そこで Kiro のセッションの中（`KIRO_SESSION_ID` がある）では、`aggregate.py`、`ledger.py`、`review.py` は、`--root` に現在のリポジトリ以外を指定すると、何も書かずに終了コード1で止まります。人がいない実行（headless では、承認が要る操作はすべて拒否されます。[Headless mode](https://kiro.dev/docs/cli/headless/)）でも、書き込み先がこのリポジトリに収まるようにするためです。Kiro の外（人の端末）では、これまでどおり `--root` を使えます。`KIRO_SESSION_ID` が渡らない環境（IDE で渡るかは未検証）では、この制限は効きません。
この評価版で人が品質を確認する運用は、将来の自動化を制限するものではありません。

## 根拠を機械的に確かめる

振り返りのエージェントの申告を、そのままは信じません。次の2つはスクリプトが確かめます。

- **引用の照合**：ノートの引用が、そのセッションのユーザー発話に実在するかを確かめます。見つからない引用は数えず、集約の「ノートの検査で外したもの」に出します。
  4文字未満の引用は、発話の全体と一致するときだけ認めます。「ん？」のような短い発話は引用できますが、長い発話から数文字だけ切り出した引用は認めません。
- **確認事項の扱い**：趣旨がはっきりしない発話（確認事項）だけのセッションは、型の根拠となるセッション数に数えません。件数には内訳を添えて出します。
- **セッション数の集計**：同じトピックが、いくつの別のセッションに出たかを数えます。2つ以上のものだけが「会話からの型の候補」になります。継続的な方針は1回でも候補になります。ただし、その方針の発話が対象期間の中にあるときだけです。期間の後に述べた方針で、期間内の1回の指摘を候補にはしません。数えるのは期間内のセッションで、種類（`period_kinds`）も期間内のものを出します。

一度照合できた引用は `data/notes-verified.json` に残すので、あとで Kiro がログを消しても数えられます。

## 採用・見送りを記録し、効果を追う

レポートの案には `P1`、`P2` と番号が付き、それぞれに「対象の型」が書かれます。

**ふつうは、振り返りの会話の中で答えるだけです。** レポートを書き終えたエージェントが、どれを採用し、どれを見送るかを尋ねます。

```text
P1 は採用、P2 は見送り。今は不要だから
```

エージェントは、あなたが明言した判断だけを記録します。答えなかった案は記録されず、あとで決められます。
あとから決めるときは、振り返りのエージェントを起動して「前回の P1 を採用した」と伝えます。

ハーネスへの反映そのものは、これまでどおり手で行います。記録するのは「採用したかどうか」だけです。反映した日は、対象のファイルの変更からスクリプトが決めます（下の「採用した案の追跡」）。

コマンドで直接記録することもできます。

```bash
python3 .kiro/skills/kiroku-retro/scripts/ledger.py list
```

```bash
python3 .kiro/skills/kiroku-retro/scripts/ledger.py adopt P1
```

```bash
python3 .kiro/skills/kiroku-retro/scripts/ledger.py reject P2 --reason "今は不要"
```

番号だけを書くと、最新のレポートの案を指します。古いレポートの案は `2026-11-13-0856#P1` のように書きます。
同じレポートの中に同じ番号の案が2つ以上あると（検査を通っていないレポート、以前の版で作ったレポート）、その番号では採用・見送りを記録しません。レポートの番号を通し番号に直してから記録します。以前の版がこの番号で判断を記録していた場合も、どの案のものかは推測せず、`ledger.py list` は「番号が重複」と表示します。

### 判断しないまま、次の振り返りをした場合

判断するときに見るのは、**いつも最新のレポートだけ**です。過去のレポートを読み返す必要はありません。

- 前回のレポートに未判断の案が残っていると、次の振り返りがそれを1件ずつ見直します。
- 対象の型が今回も出ていれば、同じ案を新しく書かず、今回のレポートに引き継ぎます。番号は付け直し、根拠は今回の数に更新します。
- 型が出なくなった、または既に解消されている案は外し、レポートの「引き継がなかった案」に理由を書きます。
- 引き継がれたあとの古いレポートの案は、`ledger.py list` で「古いレポート。最新を見てください」と表示されます。

次回以降の集約に、次の2つが出ます。

| 節 | 内容 |
|---|---|
| 採用した案の追跡 | 対象の型が、反映（分からなければ採用）の前後で何回出たか。反映の日とその根拠、反映後に観測できた作業量。「再発なし」「減った」「減っていない」「まだ日が浅い」「反映後の観測なし」「対象のファイルに変更なし（反映を確認できない）」 |
| 見送った案 | 見送りの後に、対象の型が何回出たか。振り返りは、新しい発生が無ければ同じ案を出しません |

**反映の日は、人が申告しなくても、スクリプトが記録から決めます。** 案の「対象のファイル」（`…` で囲んだパス）が、レポートを作った後に最初に変わった時刻を反映の日とします。骨組みを作ったときに、その時刻と HEAD を `data/state.json` に控えます。コミットされた変更は、控えた HEAD から辿れないコミット（作った後のコミット）かどうかで判定するので、作ったのと同じ秒のコミットも前後を取り違えません。HEAD の控えが無いときは時刻で比べ、作ったのと同じ秒のコミットは「作る前か後かは判別できない」と書きます。時刻の控えも無い以前のレポートは、名前の分（または秒）の終わりの時刻を含め、それ以降の変更を数えます。その分の中で、作る前の変更を反映と取り違えないためです（同じ分の中で作った後に変えたものは拾えません）。コミットされていない変更は、ファイルの更新時刻で判定します。
同じレポートに同じ番号の案が2つ以上あるときは、その番号への判断を、採用・見送りの数と追跡から外します。

- コミットされた変更はコミットの時刻、コミットされていない変更はファイルの更新時刻を使います。ユーザー共通のファイル（`~/.kiro/…`）は git に無いので、更新時刻だけを見ます。
- 前後の比較の境目は反映の日です。採用を決めた日とハーネスを変えた日が違っても、変えた日で比べます。
- 対象のファイルが書かれていない案（以前の版のレポートなど）は、これまでどおり採用の時刻で比べ、「反映日は不明」と表示します。
- 対象のファイルがレポートの後に1度も変わっていなければ、「対象のファイルに変更なし（反映を確認できない）」と出し、効果は判定しません。
- ファイルが変わったことは、案どおりに反映したことの証明ではありません。同じファイルへのほかの変更でも、反映とみなします。レポートを作る前から未コミットだった変更を後でコミットした場合も、反映とみなします。

**発生が0回でも、作業が無かったのなら「再発なし」とは言いません。** 境目の後に、その型が起こりうる作業をどれだけ観測できたかを、型ごとに数えます。

| 対象の型 | 観測した作業量 |
|---|---|
| `test:…` | そのテストを含むテスト実行の回数（成功も数える） |
| `tool:…`、`denied:…`、`cancelled:…`、`timeout:…` | フックの記録があるセッションの数。成功したコマンドは記録しないので、実行の総数は不明 |
| `topic:…` | 発話があり、ノートで読み終えたセッションの数 |

観測が0なら「反映後の観測なし」（境目が採用なら「採用後の観測なし」）と出します。
反映後3日未満は「まだ日が浅い」として判定しません。反映前の期間は、反映後と同じ長さ（短くても7日）を取ります。
どれも記録から計算するので、人の入力が無くても動きます。採用・見送りを決めるのは、これまでどおり人です。

## steering の重さ

集約に、steering と `AGENTS.md` のファイルごとの文字数、読み込みの条件、常時読み込みの合計が出ます。
`AGENTS.md` は、リポジトリ直下に加えてサブディレクトリのものも数えます。Kiro の公式資料（[Steering](https://kiro.dev/docs/steering/#agentsmd)）が、サブディレクトリの `AGENTS.md` も見つけ、常に読み込むと説明しているためです。探すのは git が追跡しているファイルと、無視されていない未追跡のファイルです（git が使えなければ、`node_modules` などを除いてディレクトリを辿ります）。同じファイルは二重に数えません。レポートの比較表にも、`AGENTS.md` の行として出ます。Kiro が実際にその場面で読み込んだかは、ここでは確かめていません（未検証）。
常時読み込みに書き足す案には、合計が何文字増えるかが添えられます。
合計が目安（8,000 文字。最初の値です）を超えていると、足す前に分割や条件付きへの移動を検討します。

## 使い方を見直すときの要約

しばらく使ったあとで、どの信号が役に立ったか、振り返りの質は十分かを見直すための要約です。
数だけを出し、コード、コマンド、発話、ファイルのパス、トピックの名前は出しません。リポジトリの中身を見せずに、状況を共有できます。

```bash
python3 .kiro/skills/kiroku-retro/scripts/review.py --since 14d
```

出るのは、週ごとの記録の数、信号ごとの種類の数と繰り返しの度合い、セッションとログの状態、会話からの型の数、案の採用・見送りの数、採用した案のその後、steering の量です。
数え方は集約にそろえます。判定できなかったシェル実行は、重なった実行を含めた回数で数えます（集約の「記録の不足」と同じ）。レポートの数は、台帳と同じ判定で書き終えたものだけを数え、書きかけの骨組みは別に出します。

## アンインストール

kiroku を導入先から取り除きます。何を残すかを聞かれるので、番号で選びます。

Linux/macOS:

```bash
sh /path/to/kiroku/uninstall.sh /path/to/project
```

PowerShell:

```powershell
& C:\tools\kiroku\uninstall.ps1 -Target 'C:\work\my project'
```

| 選択 | 消すもの | 残すもの |
|---|---|---|
| 1) すべて消す | フック、専用エージェント、skill、設定、記録、振り返りノート、台帳、レポート、`.gitignore` の kiroku の行 | なし |
| 2) レポートだけ残す | 上のうち、レポート以外 | `.kiro/kiroku/data/reports/` と、`.gitignore` の行 |
| 3) やめる | なし | すべて |

選んだあとに、消すものと残すものの一覧が表示され、確認を求められます。`y` と答えるまで、何も消しません。

**消すのは kiroku が置いたものだけです。** steering や、ほかの hooks・skills・agents には触りません。
kiroku の改善案をもとに手で直したハーネスは、そのまま残ります。

レポートを残す場合は、`.gitignore` の行も残します。レポートには会話の引用が含まれうるので、コミットされないようにするためです。

選択をあらかじめ指定することもできます。

| オプション（PowerShell） | 意味 |
|---|---|
| `--all`（`-All`） | すべて消す |
| `--keep-reports`（`-KeepReports`） | レポートだけ残す |
| `--dry-run`（`-DryRun`） | 消すものを表示するだけで、消さない |
| `--yes`（`-Yes`） | 確認を省く |

```bash
sh /path/to/kiroku/uninstall.sh /path/to/project --keep-reports --dry-run
```

導入先のリポジトリに kiroku のファイルをコミットしていた場合は、取り除いたあとに `git status` に削除として出ます。内容を確かめてコミットしてください。

## 開発・評価

```bash
python3 -m unittest discover -s tests -v
```

テストは一時 Git リポジトリと模擬フック・ログを使います。製品連携や LLM の提案品質を証明するものではありません。
サンプルは `examples/demo/` です。ハーネス（steering、hooks、skill、agent）を備えた家計簿の CLI で、本番に近い振り返りを試せます。手順と、仕込んである不備は [demo-scenario.md](demo-scenario.md) にあります。
繰り返しの指摘、一時的な依頼、既存規則との重複、再振り返りなどの [拡張ケース](demo-cases.md) では、実行・集計・提案の意味を分けて判定します。
製品での確認手順は [evaluation.md](evaluation.md) にあります。
過去の CLI 実測は [verification.md](verification.md) に記録されています。
