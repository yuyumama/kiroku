# kiroku と「AI に直接頼む」の比較（2026-11-25）

「kiroku を使うより、AI に直接ハーネスの改善を頼むほうが早いのでは」という問いを、デモで確かめた記録です。
これは模擬です。Kiro では動かしていません（下の「確かめていないこと」）。

## 結論

- 記録を読まずに頼む（A）と、拾えるのは今のファイルで分かる2件（`make test`、`fileMatch`）だけでした。繰り返しの指摘、承認、手作業の確認は拾えません。
- セッションログを読ませて頼む（B）だけで、繰り返しの指摘と承認のほとんどを拾えました。費用は kiroku の約5分の1です。一方で、1セッションだけの `ls` の許可や、`git push` の許可を勧めました。事実の取り違え（reviewer のセッションを通常のエージェントと誤認）もありました。
- B に「案を作る前に1回だけ質問して」と足す（D）と、危ない許可の勧めは消え、点数は kiroku に近づきました（6〜6.5／7）。費用は kiroku の約4割です。ただし回数の誤りが残りました（D2 は3件）。
- kiroku（C）は2本とも7項目すべてを拾い、確かめた後の誤りは0件でした。ただし費用は D の約2.4倍、時間は約2.2倍で、レポートの長さは約2.4倍（本文約1万4千字）です。

「直接頼むほうが早い」は、半分当たっています。
差の大部分は「ログを読ませる」（A→B：+3）と「1回質問する」（B→D：+0.5〜1。危ない勧めが消える）から来ています。
kiroku のスクリプトが足したのは、残りの0.5〜1点と、数の正しさ（回数・引用をスクリプトが数える）でした。

## 条件

同じデモ（`examples/demo/`）に、5セッションの会話を作りました（`sim.py`）。

| 条件 | 頼み方 |
|---|---|
| A | 「このリポジトリの開発ハーネスの改善を提案して」だけ |
| B | A に「過去のセッションのログが（場所）にある。それも読んで、繰り返している指摘や失敗、毎回の承認を踏まえて」を足す |
| C | kiroku を導入し、`/kiroku-retro` を実行する（専用エージェントの指示と権限をまねた） |
| D | B に「案を作る前に、記録だけでは決められないことがあれば、1回だけまとめて質問して、答えを待って」を足す |

- 被験者は、作業場所をデモのコピーにした新しい `claude -p`（Sonnet）です。答えを知りません。各条件2本です。
- 質問が出たら、結果を見る前に決めた答え（`rubric.md`）で答えました。答えの表に無い質問には「わからない」と答えました。
- 採点の基準（`rubric.md`）は、結果を見る前に書きました。X7 だけは B2 を読んだ後に足したので、点数には混ぜていません。
- 採点は、条件を伏せて並べ替えた8本を、別の AI（Opus）に1本ずつさせました（`judge_prompt.md`）。そのうえで、誤り（X）の根拠を私が元の提案と照らし合わせ、3件を直しました。

## 結果

V は拾うべきもの（7点満点）、X は出してはいけないものの件数（確かめた後）です。

| 条件 | 本 | V | X（確かめた後） | X7（事後の項目） | 費用 | 時間 | 本文の長さ |
|---|---|---|---|---|---|---|---|
| A 頼むだけ | A1 | 2.5 | 0 | 0 | $0.18 | 46秒 | 約4,600字 |
| | A2 | 2.5 | 1（X6） | 0 | $0.17 | 43秒 | 約5,200字 |
| B ログも読む | B1 | 5.5 | 1（X5） | 1 | $0.25 | 61秒 | 約5,500字 |
| | B2 | 5.5 | 3（X4、X5、X6） | 1 | $0.27 | 65秒 | 約7,100字 |
| C kiroku | C1 | 7 | 0 | 0 | $1.35 | 208秒 | 約14,800字 |
| | C2 | 7 | 0 | 0 | $1.27 | 182秒 | 約14,200字 |
| D ログ＋質問1回 | D1 | 6 | 1（X6） | 0 | $0.52 | 89秒 | 約6,700字 |
| | D2 | 6.5 | 3（X6） | 0 | $0.57 | 86秒 | 約5,700字 |

費用と時間は、質問の往復を含めた合計です。本文の長さは、C の照合用の検証値（JSON）を除いて数えました。

### 項目ごと

| 項目 | A | B | C | D |
|---|---|---|---|---|
| V1 `make test` を直す | 2/2 | 2/2 | 2/2 | 2/2 |
| V2 `fileMatch` を直す | 2/2 | 2/2 | 2/2 | 2/2 |
| V3 「結論から」を決まりに | 0/2 | 2/2 | 2/2 | 2/2 |
| V4 コミットは日本語、を決まりに | 0/2 | 2/2 | 2/2 | 2/2 |
| V5 完了前のテストを仕組み（hook）に | 0.5×2（一般論） | 0/2（文章だけ。hook を退けた） | 2/2 | 1/2 |
| V6 `run_tests.py` だけを許可 | 0/2 | 2/2 | 2/2 | 2/2 |
| V7 合計は自動、前月なしの表示は人 | 0/2 | 0.5×2 | 2/2 | 1.5/2 |

### 採点者の判定から直したもの

- C1 の X6（「`ls -la data` 1回」）は採点者の誤り。失敗した回数で、承認の回数ではない。
- C2 と B1 の X6（「完了前のテストの指摘は1セッション」）は、S2 の指摘（先にテストを書く）を別の話題として数えた分け方の違い。捏造とは扱わない。
- D2 の X6 は、採点者は4件としたが、うち1件（S5 の流れ）は読み方が分かれるので、3件にした。

### 気づいたこと

- C の質問 Q1（手作業の確認）の★は、C1 では「毎回、人が見る」でした。利用者が「はい」とだけ答えていれば、V7 は拾えていません。★の向きで結果が変わります。
- C2 は「完了前のテスト」の指摘を2つの話題に分けました。そのため2セッションの型にならず、様子見になりました。それでも hook の案（P1）は、ベストプラクティス集の BP-S2 を手がかりにして出ています。
- B と D は、「毎回言っている」と利用者が言った話題に、文章の決まりだけで応える傾向がありました（B は2本とも hook を退け、D1 は「今は足さない」とした）。仕組みに上げる案が出たのは、質問で hook を知っているか聞かれた D2 と、C です。
- C の `--check-report` は、2本とも一部の照合（回答の引用、表の確認済み）が通りませんでした。検査が読む振り返りのセッションのログを、模擬では最小限に作っただけで、Claude の会話が書き込まれないためです。kiroku の不具合とは判断していません（実機では未確認）。

## 確かめていないこと

- **Kiro では動かしていない。** 被験者は Claude Code の `claude -p`（Sonnet）です。Kiro のエージェント、モデル、ツール、権限の効き方は違います。C の権限は、専用エージェントの規則を `--allowedTools` でまねたものです。
- **ログは私が作った。** セッションログは、`verification.md` で実測した形に合わせて作りました。5セッションで約8千字と小さく、きれいです。実際のログ（1本で最大約2MB）を B・D のように生で読ませたとき、どこまで読めるかは確かめていません。量が多いほど、kiroku の区切って読む仕組みの差が出る可能性があります。
- **場面が kiroku に有利な可能性がある。** 会話は、kiroku の拡張ケース（`demo-cases.md`）を下敷きにして、私が書きました。kiroku が拾うように作られた信号が中心です。kiroku が拾わない種類の改善（`guard_shell.py` の抜け、`release.md` の前提の欠け、`add-category` の手順の順序など）は、A・B・D が多く挙げ、C はほとんど挙げていません。これは点数に入れていません。
- **本数が少ない。** 各条件2本です。差が小さいところ（C と D の0.5〜1点）は、ばらつきの範囲かもしれません。
- **答えは私が返した。** 答えの表は事前に決めましたが、質問への当てはめは私が行いました。
- **採点者は完全には伏せられていない。** C のレポートは形式で見分けられます。

## 模擬の途中で直した誤り

- 最初の版では、セッション4の変更で既存のテストが落ちているのに、会話ではエージェントが「通ります」と言っていました。実行の前に直しました（`sim.py` の `expect`）。
- A・B の履歴に「kiroku の設定を外す」というコミットが残る作り方をしていたので、kiroku の設定を最初から履歴に入れない形に直しました。
- C の最初の2本は、`--allowedTools` に渡す規則を引用符で囲んでいなかったため、集約が承認待ちで止まりました。その2本は結果から除き、やり直しました。C の続きの回からは、編集（Edit）も許可に足しました（Kiro の書き込みツールは置き換えを含むため）。

## ファイル

- `sim.py`：デモの5セッションを作り、記録フック（`record.py`）を本当に動かす。コード・テスト・git の操作も本物を実行する
- `prep.sh`：条件ごとに作業場所を写す。A・B・D からは kiroku の導入物を外す
- `run.sh`：被験者を起動する。`run.sh <本> 1` で最初の回、`run.sh <本> 2 "<答え>"` で続き
- `rubric.md`：事前に決めた採点の基準と、質問への答え
- `facts.md`、`judge_prompt.md`：採点者に渡したもの
- `results/`：8本の提案と、採点者の結果（`judge-scores.json`）、伏せた名前との対応（`judge-key.json`）

再現の手順：

```bash
cp -r docs/retro/baseline-comparison /tmp/bench && cd /tmp/bench
```

```bash
KIROKU=/path/to/kiroku python3 sim.py base kirohome
```

```bash
./prep.sh C 1 && ./run.sh C1 1
```
