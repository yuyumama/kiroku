# 開発ハーネス改善の提案

対象は `.kiro/`（steering、hooks、skills、agents）と、フックから呼ばれる `scripts/` です。
この提案ではファイルを変更していません。

調べたこと：各ファイルを読み、`guard_shell.py` に実際のコマンドを渡して動作を確かめ、`python3 run_tests.py` を実行しました（15件すべて通過）。

優先度は、エージェントの動きが実際に狂うものを高、ずれが蓄積するものを中、整えるだけのものを低としました。

## 高：steering が実在しないものを指している

### 1. `python-style.md` が一度も読み込まれない

`fileMatchPattern: "src/**/*.py"` ですが、このリポジトリに `src/` は無く、コードは `kakeibo/` にあります。そのため、Python を編集してもこの steering は読み込まれません。

提案：`fileMatchPattern: "{kakeibo,tests,scripts}/**/*.py"` に直します（`run_tests.py` も対象にするなら `**/*.py`）。

### 2. `testing.md` の `make test` は存在しない

`Makefile` がありません。実際のコマンドは `python3 run_tests.py` で、README と `reviewer.json` はこちらを使っています。エージェントは `make test` を試して失敗します。

提案：`testing.md` のコマンドを `python3 run_tests.py` に直します。結果が `reports/junit.xml` にも出ることを1行足します。

### 3. `release.md` が存在しないファイルを前提にしている

- `CHANGELOG.md` がありません。
- `kakeibo/__init__.py` に `__version__` がありません。docstring の1行だけです。

手順1回目で、エージェントが推測で新規作成することになります。

提案：次のどちらかを選びます。
- 初回リリースの手順として「`CHANGELOG.md` が無ければ作る」「`__version__` を足す」と書く。
- 先に空の `CHANGELOG.md` と `__version__` を用意する。

あわせて、手順5・6のタグ付けと push は外向きの操作です。エージェントは確認なしで実行せず、利用者の承認を取ると明記してください。

## 高：ルールとコードのずれを、ハーネスが検知しない

`product.md` と `python-style.md` に反するコードが、すでに入っています。

| 箇所 | 違反 |
|---|---|
| `kakeibo/report.py` の `yearly_totals`、`format_year` | 型ヒントが無い。`format_year` は `%` ではなく f 文字列を使っている |
| `kakeibo/cli.py` の `year` 分岐 | 関数の中で import している（他のコードは先頭で import） |
| `kakeibo/report.py` の `yearly_totals` | `monthly_totals` のほぼ複製 |

原因は (1) の steering が読み込まれなかったことと、`reviewer` が実行されていないことだと考えられます。`git log` を見ると、`year` コマンドの追加は小さな1コミットです。

提案：

- (1) の修正で再発を防ぎます。
- 既存の違反は、ハーネスとは別の作業として直します。直すときは `reviewer` に通します。
- `python-style.md` に、次の2点を足します。
  - import はモジュールの先頭に書く。
  - 集計の関数は `monthly_totals` と重複させず、共通の部分を使う。

## 中：`guard_shell.py` の抜け

実行して確かめた結果です（止まる＝終了コード 2）。

| コマンド | 結果 | 望ましい動き |
|---|---|---|
| `git push origin main -f` | 止まる | 止まる |
| `git push --force-with-lease` | 止まる | 止まる |
| `git push origin +main`（`+` 付きの refspec は強制 push） | 通る | 止まる |
| `rm -rf data` | 通る | 止まる（`data/` は記録の置き場） |
| `rm -r -f /` | 通る | 止まる（フラグが分かれている） |
| `rm -rf ./` | 通る | 止まる |
| `rm data/kakeibo.json` | 止まる | 止まる |

提案：

- `git push` の検査に、`+` で始まる refspec（`\s\+\S`）を足します。
- `rm` の検査を、フラグを分けて解釈する形にします。再帰を示すフラグ（`-r`、`-R`、`--recursive`）と、対象が `/`、`~`、`.`、`..`、`data`、`*` のどれかを別々に判定します。
- `rm` の対象に `data/` 全体を含めます。いまは `data/kakeibo.json` だけです。
- `git reset --hard` と `git clean -fd` も、確認を求める対象に加えます。未コミットの変更が消えるためです。
- `scripts/` の検査には自分のテストがありません。上の表を `tests/test_guard_shell.py` にして、`run_tests.py` で一緒に回すことを勧めます。

## 中：`reviewer` エージェントの権限

`reviewer.json` の `permissions` は `fs_write` を全面拒否し、`shell` を `git diff*` などに限っています。方向は良いのですが、次の点があります。

- `python3 run_tests.py` は `reports/junit.xml` に書き込みます。`fs_write` の全面拒否と衝突する可能性があります。`reports/` だけ書き込みを許可するか、テストを実行しない運用に決めてください。
- 変更が `main` との差か、直前のコミットかが決まっていません。プロンプトに「`git diff main...HEAD`、無ければ `git diff HEAD`」のように基準を書くと、毎回同じ範囲を見ます。
- プロンプトに「決まり」の出典がありません。`.kiro/steering/*.md` を読むよう、明記してください。いまは steering が読み込まれる前提ですが、(1) のとおり、そうなっていません。
- 確認する観点を足します。`product.md` の、標準ライブラリのみ、金額は整数、検査は `make_entry` に集約、の3点と、`python-style.md` です。観点が無いと、指摘が一般論に寄ります。

## 中：フックの足りないところ

### 1. 構文以外の検査が無い

`check-python-syntax` は構文だけを見ます。次を足せます。

- `PostFileSave` で、保存したファイルに対応するテストだけを実行する。たとえば `kakeibo/report.py` を保存したら `tests/test_report.py` を実行します。全体でも 0.006 秒なので、`run_tests.py` を毎回走らせても負担になりません。
- エージェントの終了時（Stop 相当のトリガー）に `run_tests.py` を実行し、失敗したままでは終えないようにする。

### 2. `timeout: 10` の根拠

構文検査には十分ですが、テスト実行のフックを足すなら 30 秒ほどに分けてください。

### 3. `data/kakeibo.json` の保護がフックに無い

`product.md` は「`data/` は git に載せない」と言い、`testing.md` は「テストで `data/` を書き換えない」と言います。ファイル書き込みの `PreToolUse` フックで、`data/` 配下への書き込みを止めると、ルールが機械で守られます。

## 低：整理

- `product.md` と `README.md` に、`year` コマンドの説明がありません。README の使い方に `year` が無いのは、ハーネスの範囲外ですが、`add-category` スキルと同じ「README を直すか」の判断が、今後 `add-command` のような作業で必要になります。
- `testing.md` の「先にテストを書く」は、エージェントの動きに影響が大きい決まりです。`/tdd` のようなスキルへの案内を1行足すと、守られやすくなります。
- `add-category` スキルは、よくできています。足すとしたら次の2点です。
  - `CATEGORIES` の末尾が「その他」である前提を、テストで固定する（順序が崩れたら失敗する）。
  - 手順5を `python3 run_tests.py` と具体的に書く。
- `.kiro/steering/` に、全体の入口になる短い文書（このリポジトリの構成とコマンド一覧）が無いので、`README.md` の「構成」表を `inclusion: always` で読み込む steering にまとめることを検討してください。
- `__pycache__/*.pyc` は `.gitignore` 済みで、追跡もされていません。問題ありません。

## 実施の順番（案）

1. steering の実在しないものを直す：`python-style.md` のパターン、`testing.md` のコマンド、`release.md` の前提（高の 1〜3）。
2. `guard_shell.py` の抜けを塞ぎ、テストを足す。
3. `reviewer.json` の基準と観点を書き直す。
4. フックにテスト実行と `data/` の保護を足す。
5. 既存コードの規約違反を直す（別作業）。

1〜3 は小さな変更で、効果が大きいです。まず 1 だけでも、先に入れることを勧めます。
