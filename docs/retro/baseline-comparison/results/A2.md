# 開発ハーネス改善の提案

対象は `.kiro/`（steering、hooks、skills、agents）と、フックから呼ばれる `scripts/` です。
このファイル以外は変更していません。
各項目は、実際に読んだり動かしたりして確かめた事実に基づいています。

## 優先度の高い順

### 1. `python-style.md` の `fileMatchPattern` が実在しないパスを指している

- 事実：`fileMatchPattern: "src/**/*.py"` ですが、このリポジトリに `src/` はありません。コードは `kakeibo/` と `tests/` にあります。
- 影響：スタイルの決まりが、Python ファイルを編集するときに一度も読み込まれません。
- 提案：`"{kakeibo,tests,scripts}/**/*.py"` などに直します。複数パターンを書けない場合は、`kakeibo/**/*.py` だけにします。
- 補足：読み込まれるようになると、次の2点でコードとの食い違いが見えるはずです。先に決めておくと混乱しません。
  - 「型ヒントを書く」：`models.py` の `to_dict` は戻り値が `dict` で、型引数が無いだけで実害は小さいです。
  - 「`%` 書式にそろえる」：現状のコードは守れています。

### 2. `testing.md` の `make test` が存在しない

- 事実：`Makefile` がありません。実際のコマンドは `python3 run_tests.py` です（README と reviewer の許可リストもこちら）。
- 影響：エージェントが `make test` を実行して失敗するか、実行方法を探し回ります。
- 提案：`python3 run_tests.py` に書き換えます。`run_tests.py` は JUnit XML を `reports/junit.xml` に出すことも、1行添えます。

### 3. `release.md` が存在しないファイルを前提にしている

- 事実：`CHANGELOG.md` がなく、`kakeibo/__init__.py` に `__version__` もありません。タグも未作成です（`git log` は 5 コミットのみ）。
- 影響：手順の4と3がそのままでは実行できず、初回リリースで迷います。
- 提案：次のどちらかにします。
  - 手順の先頭に「初回のみ：`CHANGELOG.md` を作り、`__version__ = "0.1.0"` を置く」を足す。
  - 初期ファイルを先に作っておく。
- 補足：手順2の「テストをすべて実行」も、`python3 run_tests.py` と明記すると曖昧さが減ります。
- 補足：手順7は「前の版のファイルを読み込む」とありますが、前の版のサンプルを置く場所がありません。`tests/fixtures/` に各版の `kakeibo.json` を保存し、テストで読み込む形にすると、手作業が自動の確認に変わります。

### 4. `guard_shell.py` の検出に抜けがある

実際に実行して確かめた結果です（2 = 止める、0 = 通す）。

| コマンド | 結果 | 望ましい結果 |
|---|---|---|
| `git push origin main --force` | 2 | 2 |
| `git push -f` | 2 | 2 |
| `git push origin +main`（refspec での強制） | **0** | 2 |
| `rm -rf /` | 2 | 2 |
| `rm -fr ~` | 2 | 2 |
| `rm -r -f /` | **0** | 2 |
| `rm -rf *` | **0** | 2 |
| `rm data/kakeibo.json` | 2 | 2 |
| `git reset --hard` | **0** | 要検討 |

- 提案：
  - `+<ref>` 形式の push を止める。
  - フラグが分かれた `rm -r -f` を止める。
  - `rm -rf *` を止める。
  - `git reset --hard`、`git clean -fd`、`git checkout .` など、未コミットの変更を失うコマンドを止めるか、確認を求める。
- 限界：正規表現による検出は、`bash -c "..."` や変数展開を使った回避を防げません。フックは事故防止の網であり、防御ではありません。
  この限界を `scripts/guard_shell.py` の docstring に書いておくと、過信を避けられます。
- 補足：テストが無いので、上の表をそのまま `tests/test_guard_shell.py` にすると、正規表現を直しても退行に気づけます。
  `scripts/` は現在テスト対象外です。

### 5. `data/kakeibo.json` の保護が `rm` にしかかかっていない

- 事実：`guard_shell.py` は `rm ... data/kakeibo.json` だけを止めます。`mv data/kakeibo.json /dev/null`、`> data/kakeibo.json`、`git clean -fdx` は通ります。
- 提案：リダイレクトによる上書きと `mv` も対象に加えます。
  すでに `reviewer.json` は `fs_write` を全面拒否しているので、メインのエージェント側にも `data/**` への書き込み拒否ルールを置くのが素直です。
  `testing.md` の「`data/` を書き換えません」とも揃います。

### 6. `reviewer` エージェントの許可範囲

- 事実：
  - `tools` に `shell` があり、許可は `git diff*`、`git log*`、`git status*`、`python3 run_tests.py` です。
  - `python3 run_tests.py` は `reports/junit.xml` を書きます（`reports/` は gitignore 済みです）。
  - `fs_write` を全拒否しているので、このテスト実行が拒否される可能性があります。
- 提案：`reports/**` への書き込みだけを許可するか、`run_tests.py` に出力先を変える引数を足して `/tmp` に向けます。
  実際に拒否されるかは、使っている Kiro のルール評価順（deny 優先かどうか）に依存します。実行して確かめてください。
- 提案：プロンプトに、見るべき観点を足します。現状は「決まりに合っているか、テストが足りているか」だけです。
  `steering/` の各ファイルを読むよう明記し、レビューの出力形式（重大度の付け方）も決めます。

### 7. フックの抜け

- 事実：フックは「構文確認」と「シェルの検査」の2つだけです。構文確認は `compile` だけなので、`NameError` や import の誤りは見つかりません。
- 提案：
  - 保存時に、対応するテストファイルだけを実行するフック（例：`kakeibo/report.py` を保存したら `tests/test_report.py` を実行）を足す。
    全体でも 15 テストが 0.006 秒で終わるので、全件実行のフックでも負担になりません。
  - `Stop` 相当のタイミングで全件を実行し、失敗が残っていたら知らせる。
  - どちらも、先に 1 つ入れて様子を見ます。フックが多いと、保存のたびに待たされます。
- 補足：`check_syntax.py` は `OSError` を黙って成功扱いにします。削除された場合は妥当ですが、権限エラーも同じ扱いになります。実害は小さいので、優先度は低いです。

### 8. スキル `add-category` の手順の細部

- 事実：
  - `CATEGORIES` に追加するときの順序の根拠（「その他」は最後）は書かれていますが、`医療` のように途中に入れるか末尾の手前に入れるかは決まっていません。
  - 手順3は「順が変わらないことを確かめる」ですが、集計の順は `CATEGORIES` の順なので、実際には「順が変わる」のが正しいです。ここは文面が逆に読めます。
  - 手順4の「README に一覧は書いていない」は、README が変わると嘘になります。
- 提案：
  - 手順3を「新しいカテゴリが `CATEGORIES` の位置どおりに集計に出ることを確かめる」に直す。
  - 手順4は削除するか、「`README.md` と `--help` の文言にカテゴリの一覧が書かれていないかを `grep` で確かめる」にする。
  - `git log` に前例（`2733609 医療カテゴリを追加`）があるので、その差分をスキルの例として参照させる。
- 他にも、繰り返す作業があれば、同じ形でスキルにできます。
  - 新しいサブコマンドの追加（`year` の追加が前例）。
  - 月の集計の表示変更。
  - テストを書く前に失敗を確かめる手順（`testing.md`）。

### 9. steering の構成

- 事実：`product.md` と `release.md`、`testing.md` には `inclusion` の指定がありません。`python-style.md` だけが `fileMatch` です。
- 提案：
  - `product.md` と `testing.md` は常時読み込みのままにします。短く、常に関わる内容だからです。
  - `release.md` は、リリースの作業時だけ必要です。
    `inclusion: manual` にするか、スキル `release` に移し、「リリースして」と頼まれたときだけ読み込まれるようにします。常時のコンテキストを節約できます。
  - `product.md` の「入力の検査は `make_entry` に集める」は、現状のコードと一致しています。ただ、`storage.load` が `make_entry(**row)` を呼ぶので、壊れたファイルを読むと `InvalidEntry` が CLI の `list` や `report` で捕捉されずに落ちます。
    決まりとして「読み込み時の `InvalidEntry` をどう扱うか」を書くか、コードを直すかの判断が要ります。これはハーネスよりコードの課題ですが、steering に書くと再発を防げます。

### 10. README と実態のずれ

- 事実：README の使い方に `year` コマンドがありません（`1e92e00` で追加済み）。
- 提案：スキル（新しいサブコマンドの追加）か steering に「コマンドを足したら README の使い方を更新する」を足します。
  今回のずれが、決まりの欠如から起きていることの例です。

## 実施の順序（案）

1. 事実の誤りを直す（項目 1、2、3、10）。いずれも文面の修正で、副作用がありません。
2. `guard_shell.py` にテストを足してから、検出を広げる（項目 4、5）。
3. `reviewer` の許可の確認と、フックの追加（項目 6、7）。
4. スキルと steering の整理（項目 8、9）。

- `reports/junit.xml` を読む側（CI やエージェントのツール）の有無。
