## 1. `testing.md` の実行コマンドを直す

現状は `テストは make test で実行します` と書いてありますが、Makefile はありません。README と実際の運用は `python3 run_tests.py` です。

- s1 と s2 のどちらでも `make test` を先に実行して失敗し、その後 `python3 run_tests.py` に切り替えました。毎回、承認 1 回と失敗 1 回を無駄にしています。
- 直し方は 1 行です。「テストは `python3 run_tests.py` で実行します。結果は `reports/junit.xml` にも書かれます」とします。
- Makefile を足す案もありますが、このリポジトリは標準ライブラリだけで動かす方針なので、steering のほうを直すのが軽いです。

## 2. `python-style.md` が一度も読み込まれていない

`inclusion: fileMatch` の `fileMatchPattern` が `src/**/*.py` ですが、このリポジトリのコードは `kakeibo/` にあり、`src/` はありません。そのため、Python を編集しても決まりが読み込まれません。

- s3 では、レビュー担当が型ヒントと `%` 書式の決まりを見ずにレビューし、「steering に書いてあるよ」と指摘されました。
- s2 で書いた `yearly_totals` と `format_year` は、型ヒントがなく f-string でした。決まりに反しており、s3 の指摘どおりです。
- 直し方は `fileMatchPattern: "kakeibo/**/*.py"` にします。テストも対象にするなら `"{kakeibo,tests}/**/*.py"` などにします。
- あわせて、steering が実際に効いているかを確かめます。Python を 1 ファイル編集して、読み込まれることを確認します。

## 3. 繰り返し言われている指摘を steering に入れる

次の 3 点は、複数のセッションで同じことを言われています。新しい steering（例：`.kiro/steering/workflow.md`、常時読み込み）に書くのが妥当です。

- **返答は結論から短く書く。** s1 と s2 の両方で「説明が長い。結論から書いて」と言われています。「最初の 1 文に結果を書く。経緯は聞かれたときだけ書く」とします。
- **コミットメッセージは日本語で書く。** s1 で指示し、s2 でも「前にも言ったよ」と言われています。s4 と s5 は日本語でしたが、決まりとして書かれていないので、保証がありません。
- **「完了」と言う前にテストを実行する。** s5 で「毎回言ってる気がする」と言われています。「コードを変えたら、`python3 run_tests.py` を実行して結果を確かめてから完了と伝える」とします。

書かない（一回限りの指示）ものもあります。

- s1 の「今回だけ、比較する月は 2026-10 にして。既定値にはしないで」は、本人が既定値にしないと明言しています。
- s4 の「確かめ終わるまで待ってて」は、その場の依頼です。
- s4 の「前月が無いときの表示だけは、毎回自分の目で見たい」は、繰り返しの希望に見えます。ただし 1 回しか出ておらず、範囲も「表示の確認」としか分かりません。steering に入れる前に、本人に「表示を変えたときは、コミットの前に画面を見せて確認を取る、という決まりにしますか」と聞くことを勧めます。

## 4. 承認の負担を減らす

どのセッションでも、実行のたびに承認（accept）が必要でした。全部 accept で、拒否はありませんでした。

| コマンド | 承認回数 | 提案 |
|---|---|---|
| `python3 run_tests.py` | 9 回実行（s1・s2・s4・s5 で、ほぼ毎回承認） | 許可 |
| `make test`（失敗するもの） | 2 回 | #1 で消える |
| `ls -la`、`ls -la <dir>` | 5 回（s4） | 許可（読み取りのみ） |
| `git add … && git commit -m …` | 4 回 | 許可するかは本人が決める。下記参照 |
| `git push origin main` | 2 回 | 許可しない。承認を残す |

- 許可するのは、副作用のない `python3 run_tests.py`、`ls*`、`git status*`、`git diff*`、`git log*` です。`reports/junit.xml` を書きますが、`.gitignore` 済みで害はありません。
- s4 では、`data` と `reports` を見たいだけなのに `ls` を 5 回に分けて承認しています。読み取りの許可があれば、承認なしで済みます。
- コミットは取り消せるので許可しても構いませんが、「コミットして」と頼んだときだけ実行する運用を保てるか、本人の判断です。push は共有先に出るので、承認を残すことを勧めます。
- reviewer エージェントにはすでに `git diff*` などの許可があります。同じ書き方をメインのエージェントの設定にも持ち込めます。設定ファイルの場所と書式は Kiro の版によって違うため、実装時に確認してください。

## 5. reviewer エージェントに steering を読ませる

s3 のレビュー担当は、diff だけを見て「年の境界のテストは十分」「空の表示をそろえるとよい」と指摘しました。型ヒントの欠落と f-string には、指摘されるまで触れませんでした。

- `reviewer.json` の `prompt` に「最初に `.kiro/steering/` の全ファイルを読み、変更が各決まりに合っているかを 1 つずつ確かめる」と足します。
- 確認の観点を列で渡します。型ヒント、`%` 書式、日本語の文言、`make_entry` に検査を集めること、外部パッケージを足していないこと、金額が整数であること、先にテストがあること。
- `tools` に `read` があるので、steering の読み込み自体はできます。足りないのは指示です。
- #2 で `fileMatch` を直しても、レビュー担当に自動で読み込まれるとは限りません。プロンプトで明示するほうが確実です。
- `python3 run_tests.py` はすでに許可されています。「実行して通ることを確かめる」も足せます。

## 6. 先にテストを書く運用

`testing.md` には「振る舞いを変えるときは、先にテストを書きます」とありますが、s2 では実装から始めました。「テストは？ testing.md に、先にテストを書くって書いてあるよね」と言われ、その後で書いたところ、年の前方一致の不具合が見つかりました（`202` が 2026 年に一致する）。s4 は逆にテストを先に書けています。

- steering の文だけでは守られていません。#1 の修正に合わせて、手順を具体的にします。「1) 失敗するテストを書く 2) `python3 run_tests.py` で失敗を確かめる 3) 実装する 4) 通ることを確かめる」。
- 機能追加用の skill（`add-feature` など）を作る案もあります。ただし、機能の追加は形がまちまちなので、まずは steering の手順化で十分です。
- 既存の `add-category` skill は、s1 で手順どおりに動きました。ただし s1 では、テストを足す前にコードを直しています。手順 1 と 2 の順を守るよう、「テストを先に足し、失敗を確かめる」に並べ替えられます。

## 7. guard-shell の穴（任意）

s5 の `git push --force origin main` は、`guard-shell` で止まりました。フック自体は機能しています。ただ、`scripts/guard_shell.py` の正規表現は、次のような書き方を止めません。

- `git push origin +main`（`+` を付けた refspec は強制 push と同じ）
- `git push origin main --force` は止まりますが、`git push --mirror` や `git push --delete` は止まりません。
- `rm -rf data/`（`data/kakeibo.json` を含まない形）。`data/` に記録があるので、危険です。
- `git reset --hard`、`git clean -fd` も、未コミットの変更を失います。

足すなら、`\+\S+` の refspec、`--mirror`、`rm -r* data` の 3 つが妥当です。逆に、過剰に広げると s4 のような通常の作業を邪魔するので、実際に起きた形だけにとどめるのが良いです。

また、s5 のログでは、フックに止められたコマンドの `cwd` が別の場所（`.../bench/base`）になっていました。これはハーネスの問題ではなく、ログの取り方の違いかもしれません。気になるなら確認してください。
