# 開発ハーネス改善の提案

対象は `.kiro/`（steering、hooks、skills、agents）です。このファイルの作成以外に、ファイルは変更していません。

根拠は、現在のリポジトリと、過去 5 セッション（s1〜s5）のログです。`sess_retro` は `/kiroku-retro` の呼び出しだけで、中身はありません。

## 要約

優先度の高い順です。

| # | 提案 | 根拠 |
|---|---|---|
| 1 | `testing.md` の `make test` を `python3 run_tests.py` に直す | s1、s2 で同じ失敗を 2 回。承認も 2 回無駄になった |
| 2 | `python-style.md` の `fileMatchPattern` を `kakeibo/**/*.py` に直す | `src/` は存在せず、一度も読み込まれていない。s3 のレビューで指摘された |
| 3 | 完了の定義と応答の書き方を steering に足す | 「結論から」(s1、s2)、「日本語のコミットメッセージ」(s1、s2)、「テストを回してから完了」(s5) の繰り返し |
| 4 | 読み取り専用コマンドと `python3 run_tests.py` を自動で許可する | 承認 20 回以上のうち、ほとんどが同じ種類のコマンド |
| 5 | `add-category` skill の順序を、テスト先行に合わせる | skill は実装、テストの順。`testing.md` と食い違う |
| 6 | `reviewer` エージェントを使えるようにする | s3 では使われず、決まりを見落とした |
| 7 | `release.md` が指す存在しないファイルを整える | `CHANGELOG.md`、`__version__` が無い |
| 8 | 「前月が無いときの表示は毎回目視」を明文化する | s4 の利用者の指示。自動化してはいけないもの |

## ログから見えたこと

### 繰り返された指摘

| 指摘 | 出てきた場所 | 現在の steering |
|---|---|---|
| 説明が長い。結論から書いて | s1、s2 | 書かれていない |
| コミットメッセージは日本語で（「前にも言ったよ」） | s1、s2 | 書かれていない |
| テストを先に書く | s2（「testing.md に書いてあるよね」） | `testing.md` にある。守られなかった |
| テストを回してから完了と言う（「毎回言ってる気がする」） | s5 | 書かれていない |
| 金額は整数の円で出す | s2（月平均が小数） | `product.md` にある。守られなかった |
| 型ヒントと `%` 書式の決まりを見たか | s3 | `python-style.md` にある。読み込まれていなかった |

書かれていない指摘（上の 3 件）は steering に足します。書かれているのに守られなかった指摘（上の 3 件）は、読み込まれ方か、実行できる形かが問題です。

### 繰り返された失敗

- `make test` が `No rule to make target 'test'` で失敗しました（s1、s2）。どちらも、そのあと `python3 run_tests.py` に切り替えています。
- s2 では、テストを書かずに実装しました。後からテストを足したところ、年の前方一致の誤り（`'202'` が 2026 年を拾う）が見つかりました。テスト先行が守られていれば、実装前に見つかった種類の不具合です。
- s5 では、「push して」に対してエージェントが `git push --force origin main` を出しました。`guard-shell` が止め、通常の push に切り替えています。フックは効いていますが、そもそも強制 push を出すこと自体が不自然です。

### 毎回の承認

承認はすべて `accept` で、却下はありません。同じ種類のコマンドが繰り返し承認されています。

| コマンド | 回数の目安 | 備考 |
|---|---|---|
| `python3 run_tests.py` | s1 ×2、s2 ×3、s4 ×2、s5 ×2 | 読み取りに近く、副作用は `reports/junit.xml` だけ |
| `make test` | s1、s2 | 失敗が分かっているコマンドの承認 |
| `ls -la`、`ls -la data`、`ls -la reports` など | s4 ×5 | 読み取り専用 |
| `git commit`（`git add kakeibo tests && ...`） | s1、s2、s4、s5 | 利用者が毎回「コミットして」と頼んでいる |
| `git push origin main` | s5 ×2 | 利用者が毎回頼んでいる |
| `python3 -m kakeibo report ...` | s1 | 読み取り専用 |

## 提案の詳細

### 1. `testing.md` の `make test` を直す

`testing.md` は「テストは `make test` で実行します」と書いていますが、`Makefile` がありません。README と `run_tests.py` は `python3 run_tests.py` を示しています。エージェントは `testing.md` に従って毎回まず失敗し、そのたびに承認を 1 回消費しています。

**変更案**（`.kiro/steering/testing.md`）:

```diff
-- テストは `make test` で実行します。
+- テストは `python3 run_tests.py` で実行します。結果は `reports/junit.xml` にも書かれます。
```

`Makefile` を足す案もありますが、`product.md` が「標準ライブラリだけ」と言っている以上、実行方法を 1 つに絞って steering を直すほうが小さく済みます。

### 2. `python-style.md` の `fileMatchPattern` を直す

`fileMatchPattern: "src/**/*.py"` ですが、コードは `kakeibo/` にあり、`src/` はありません。このため、この steering は Python を編集しても読み込まれません。s3 で利用者が「型ヒントや文字列の書式の決まりは見た？」と聞いたとき、エージェントは「見ていませんでした」と答えています。実際、レビュー対象の `yearly_totals` と `format_year` には型ヒントが無く、f-string が使われていました（`%` 書式の決まりに反します）。

**変更案**（`.kiro/steering/python-style.md`）:

```diff
-fileMatchPattern: "src/**/*.py"
+fileMatchPattern: "{kakeibo,tests,scripts}/**/*.py"
```

`fileMatch` の書式は Kiro のバージョンで違うかもしれません。変更後に、`kakeibo/report.py` を開いて読み込まれることを確かめてください。確かめる手段が無ければ、決まりが短いので、`inclusion` を付けずに常時読み込みにする案もあります。

### 3. 完了の定義と応答の書き方を steering に足す

書かれていない 3 つの指摘は、1 つの新しい steering にまとめられます。

**新規**（`.kiro/steering/workflow.md`）:

```markdown
# 進め方

## 応答

- 結論から書きます。経緯や手順の説明は、聞かれたときだけ書きます。
- 終わった報告は 1〜2 文にします。

## 完了

- 「完了」と言う前に、`python3 run_tests.py` を実行し、結果の件数を添えます。
- 実行していないときは、完了と言わず、実行していないと書きます。

## git

- コミットメッセージは日本語で書きます。
- push は `git push origin main` の形にします。`--force` と `--force-with-lease` は使いません。
```

「毎回言っている」ことは、steering に書けば言わずに済みます。s1 と s2 の「結論から」、s1 と s2 の「日本語で」、s5 の「テストを回してから完了」が対象です。

「金額は整数の円」と「テスト先行」はすでに steering にあります。これらは、書き足すより、実行できる形にするほうが効くと考えます（次の「補足」を参照）。

### 4. 承認を減らす

承認はすべて `accept` でした。次のコマンドは副作用が小さいので、許可を足す価値があります。

| 許可する | 理由 |
|---|---|
| `python3 run_tests.py` | 書くのは `reports/`（git 管理外）だけ |
| `ls *`、`git status*`、`git diff*`、`git log*` | 読み取り専用 |
| `python3 -m kakeibo list`、`python3 -m kakeibo report *` | 読み取り専用 |
| `git add kakeibo tests`、`git commit -m *` | 利用者が頼んだときだけ実行され、履歴に残るので取り返せる |

**許可しない**ものも決めておきます。

- `git push*` は、毎回の承認を残す案を勧めます。`guard-shell` が強制 push を止めますが、外に出る操作なので、利用者が確認できるほうが安全です。承認の負担が大きいと感じるなら、`git push origin main` だけを許可する案もあります。
- `python3 -m kakeibo add ...` は `data/kakeibo.json` を書き換えるので、許可しません。

`reviewer.json` はすでに `git diff*`、`git log*`、`git status*`、`python3 run_tests.py` を許可しています。同じ一覧を既定のエージェントにも使えば、重複が減ります。`kiro_default` の設定の置き場所は、このリポジトリからは確かめられませんでした。Kiro の設定を確認して決めてください。

### 5. `add-category` skill をテスト先行に合わせる

`SKILL.md` の手順は、1. `CATEGORIES` に足す、2. テストを足す、の順です。`testing.md` は「先にテストを書き、失敗するのを確かめてから実装する」です。s1 の医療カテゴリでは、skill に沿って実装を先に書き、あとからテストを足しました。

**変更案**:

```markdown
1. `tests/test_models.py` に、新しいカテゴリで記録できることを確かめるテストを足し、失敗するのを確かめます。
2. `kakeibo/models.py` の `CATEGORIES` に、新しいカテゴリを足します。「その他」は最後のままにします。
3. （以降は今のまま）
```

もう 1 点、s1 のテストは `MedicalTest` という別クラスで、関数内 import を使っています。既存の `MakeEntryTest` に足す、と skill に書くと、形がそろいます。

同じ「テスト先行」の食い違いを、skill でない作業（`year` コマンド、s2）でも踏んでいます。機能の追加用に、同じ手順の skill（`add-command` など）を作る案もありますが、使われた回数が 1 回なので、今は見送ります。

### 6. `reviewer` エージェントを使えるようにする

s3 では、「直近のコミットをレビューして」に対して、既定のエージェントが `git log` と `git diff` を読み、steering を読まないままレビューしました。`reviewer` エージェントは `.kiro/agents/reviewer.json` にありますが、使われた形跡がありません。

- `prompt` に、読むべき steering を明記します。「`.kiro/steering/*.md` をすべて読み、変更が決まりに合うかを確かめる」の 1 文です。
- 確かめる項目を挙げます：型ヒント、`%` 書式、整数の円、日本語の文言、`make_entry` への検査の集約、テストの有無。
- `tools` に `read` があるので、steering は読めます。読むように指示するだけで足ります。
- 「レビューして」と頼まれたら `reviewer` を使う、という 1 行を `workflow.md`（提案 3）に足します。

### 7. `release.md` が指す存在しないものを整える

`release.md` は `CHANGELOG.md` と `kakeibo/__init__.py` の `__version__` を前提にしていますが、どちらもまだありません。今のところリリースは行われていないようなので、急ぎではありません。ただ、最初のリリースで、エージェントが手順どおりにできず、迷います。

選択肢：

- 最初のリリースのときに `CHANGELOG.md` と `__version__` を作る、と 1 行足す。
- `release.md` の先頭に「初回は `CHANGELOG.md` を新規に作る」と書く。

なお、`release.md` は常時読み込まれる steering です。リリース以外の作業では要らないので、`inclusion: manual` にして、リリースのときだけ呼ぶようにすると、毎回の文脈が軽くなります。

### 8. 「前月が無いときの表示は毎回目視」を明文化する

s4 で、利用者はこう言っています。

> 合計と差額は私が画面で確かめるから、確かめ終わるまで待ってて
> 確かめた。合計と差額は合ってた。前月が無いときの表示だけは、毎回自分の目で見たい

前半は 1 回限りの指示です。後半は、今後も続く指示です。これは、承認を減らす提案（4）の対象から外します。

**変更案**（`workflow.md` に追記）:

```markdown
## 利用者が目で確かめるもの

- 月の集計で、前月の記録が無いときの表示は、変更のたびに利用者が自分で確かめます。
  確かめるまで「完了」と言わず、コミットもしません。
```

「合計と差額」は、s4 の時点で確かめ済みなので、書きません。

## 提案しないもの

- **比較する月を 2026-10 にする設定**（s1）：「今回だけ、既定値にはしないで」と言われています。steering や設定には書きません。
- **フックの追加**：`check-python-syntax` と `guard-shell` は意図どおり動いています（s5 で強制 push を止めました）。新しい失敗が見つかるまで、足しません。
- **`make` の導入、外部パッケージ**：`product.md` の「標準ライブラリだけ」に反します。
- **スタイルの強制を hook にする案**（型ヒントや `%` 書式の検査）：標準ライブラリだけで書くと、検査の実装が重くなります。提案 2 で steering が読み込まれるようになるか、見てから決めます。

## 補足：効果の確かめ方

- 提案 1〜3 を入れたあと、次の数セッションで「`make test` の失敗」と「結論から、日本語で、の再指摘」が消えたかを見ます。
- 提案 4 のあと、承認の回数が減ったか、却下すべき承認が混ざっていないかを見ます。
- 「金額は整数の円」（s2）と「テスト先行」（s2）は、書かれていたのに守られませんでした。提案 2、3 のあとも再発するなら、`workflow.md` の先頭に両方を再掲するか、`reviewer` の確認項目（提案 6）で拾います。
