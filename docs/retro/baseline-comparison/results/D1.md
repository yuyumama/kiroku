# 開発ハーネスの改善提案

対象は `.kiro/`（steering、hooks、skills、agents）と `scripts/` です。この文書の作成時に、ほかのファイルは変更していません。

根拠は、`.kiro/` と `scripts/` の現状と、過去5セッション（s1〜s5）の記録です。`sess_retro` は `/kiroku-retro` の起動だけで、中身はありません。

## 先に確認したいこと

次の3点は、質問に「わからない」と返ってきたため、推奨を決めて書きました。違えば直します。

- 提案2（前月が無いときの表示を、人が見る）は、止まる場所と steering にするかを推奨で決めました。
- 提案4（`make test`）は、Makefile を足すより `testing.md` を直す案を推奨にしました。
- 提案5（結論から書く、日本語のコミットメッセージ）は、この repo の steering に置く案を推奨にしました。

読むだけのコマンドを承認なしにするかは、決めていません。提案1の「保留」に書きました。

## 1. `python3 run_tests.py` だけ承認なしにする

### 記録で見えたこと

- 5セッションで、実行系ツールの承認が約30回ありました。選択はすべて `accept` で、却下はありません。
- そのうち `python3 run_tests.py` は8回です（s1、s2、s4、s5）。
- 回答は「`python3 run_tests.py` は自動で通してよい」でした。`git commit` と `git push` は毎回確かめたいとのことでした。

### 提案

- `python3 run_tests.py` だけを承認なしにします。
- 方法は、既定のエージェントの設定で、このコマンドを許可することです。`reviewer.json` の `permissions.rules` と同じ書き方で足せます。
- 完全一致で許可します。`python3 run_tests.py*` のようなワイルドカードにはしません。
- `git commit`、`git push` は許可しません。これまでどおり毎回確かめます。

### 保留

- 読むだけのコマンドは、回答が「わからない」でした。現時点では許可しません。
- 判断の材料は次のとおりです。
  - s4 では「data と reports に何があるか見せて」に対して、`ls` の承認が5回続きました。
  - 次に同じ頼みが続くようなら、`ls` と `git status`、`git diff`、`git log` の許可を足せばよいでしょう。
  - `reviewer.json` は、すでに `git diff*`、`git log*`、`git status*` を許可しています。

## 2. 「前月が無いときの表示」を人が見る決まりを書く

### 記録で見えたこと

- s4 で、合計と差額の正しさは、利用者が画面で確かめて済ませました。
- そのうえで、「前月が無いときの表示だけは、毎回自分の目で見たい」と言われました。
- このときの返答は「承知しました。」だけでした。決まりとして残っていないので、次のセッションでは守られません。

### 提案

次の内容を `.kiro/steering/testing.md` の末尾に足します。新しいファイルは作りません。

```markdown
## 人が確かめるところ

- 月の集計で、前の月の記録が無いときの表示は、人が画面で確かめます。テストが通っても、確かめてもらうまでは完了と言いません。
- 合計や差額の数字は、テストで確かめます。人には頼みません。
```

### 止まる場所

- 推奨は「コミットの前」です。コミットは、どのみち毎回の承認が必要です。
- 表示を見せて、確かめてもらい、そのあとコミットします。
- 対象は、前月が無いときの表示だけです。ほかの表示までは広げません。
- 回答は「わからない」でした。違うときは、この節の文言だけ直せば済みます。

## 3. `python-style.md` の適用範囲を直す

### 記録で見えたこと

- `python-style.md` の `fileMatchPattern` は `src/**/*.py` です。
- この repo のコードは `kakeibo/` にあり、`src/` はありません。`.kiro/` の中で `src/` が出てくるのは、この1か所だけです。
- そのため、このファイルはどの編集でも読み込まれていません。
- 現れた失敗は2つです。
  - s2 では、year コマンドの `yearly_totals` と `format_year` に、型ヒントがありませんでした。
  - s2 では、f-string を使っていました。決まりは `%` 書式です。
- s3 の reviewer も、読まずにレビューしました。利用者に「steering に書いてあるよ」と指摘されています。

### 提案

`.kiro/steering/python-style.md` の先頭を、次のように直します。

```yaml
fileMatchPattern: "kakeibo/**/*.py"
```

- テストにも同じ決まりを当てるなら、`"{kakeibo,tests}/**/*.py"` にします。ただし、テストでは型ヒントを書いていません。この点は決めていないので、まず `kakeibo/` だけに絞ります。

## 4. `testing.md` の `make test` を直す

### 記録で見えたこと

- `testing.md` は、テストを `make test` で実行すると書いています。
- Makefile はありません。s1 と s2 の両方で `make test` が失敗し、そのあと `python3 run_tests.py` に切り替えています。
- README は `python3 run_tests.py` と書いていて、`run_tests.py` の docstring には「動作確認用」とあります。
- 回答は「わからない」でした。

### 提案

- `testing.md` の該当行を、次のように直します。

  ```markdown
  - テストは `python3 run_tests.py` で実行します。結果は `reports/junit.xml` にも書かれます。
  ```

- Makefile を足す案より、こちらを推奨します。外部の道具を増やさず、README と `testing.md` が一致するからです。
- もし `run_tests.py` が仮のもので、本物のテストツールを使う予定があるなら、その時点で `testing.md` を直します。

## 5. 返答とコミットの決まりを steering に足す

### 記録で見えたこと

- 「説明が長い。結論から書いて」を、s1 と s2 で言われました。直後の返答は、どちらも1文に縮んでいます。
- 「コミットメッセージは日本語で」を、s1 で言い、s2 では「前にも言ったよ」と言われました。
- 実際のコミットメッセージは、s1、s2、s4、s5 のすべてが日本語でした。ただ、決まりにはなっていません。
- 同じ指摘が2回出ているので、steering に残す価値があります。

### 提案

新しい steering `.kiro/steering/working-style.md` を作り、次の内容を書きます。

```markdown
# 作業の進め方

- 返答は、結論を先に1〜2文で書きます。経緯や内訳は、聞かれたときだけ書きます。
- コミットメッセージは日本語で書きます。
- 変更したら、テストを実行して結果を確かめてから、完了と言います。
```

### 置き場所

- この repo の `.kiro/steering/` に置くことを推奨します。
- 「結論から書く」は、利用者個人の好みかもしれません。その場合は、`~/.kiro/steering/` に移したほうがよいです。回答は「わからない」でした。
- 日本語のコミットメッセージは、この repo の方針として書いてよいと考えます。利用者に見える文言は日本語、という `product.md` の流れと合うからです。
- 迷うなら、まず repo に置き、他の repo でも同じ指摘が出たら全体設定に移します。

## 6. 完了の前にテストを走らせる決まりを書く

### 記録で見えたこと

- s2 では、`testing.md` に「先にテストを書く」とあるのに、テストなしで実装しました。
- 利用者に指摘されたあとにテストを書くと、年の前方一致のバグが見つかっています（`'202'` が 2026 年に当たる）。
- s5 では、list の並び替えを直したあと、テストを走らせずに「並べるようにしました」と返しました。
- そのあと「テストを回してから完了って言って。毎回言ってる気がする」と言われています。
- 「毎回」は、記録の範囲では s2 と s5 の2回です。

### 提案

- 提案5の `working-style.md` に、「テストを実行してから完了と言う」を書きます。これが最小の対応です。
- 提案1で `python3 run_tests.py` を承認なしにすれば、毎回の承認が減り、テストを走らせるコストも下がります。
- 保存のたびに走らせるフックは、今は足しません。
  - 既存の `check-python-syntax` と同じ形で足せますが、全テストを走らせると編集のたびに遅くなります。
  - 11〜15件のテストなら、まだ問題は小さいです。
- 完了前に走らせるフックは、Kiro のバージョンによって呼べるトリガーが違う可能性があります。今の設定では確かめられていません。steering で足りなければ、次の段階で検討します。

## 7. reviewer に、steering を読む手順を足す

### 記録で見えたこと

- s3 の reviewer は、`git log` と `git diff` だけでレビューしました。steering は読んでいません。
- 利用者から、型ヒントと文字列の書式の決まりを見たかと指摘されました。指摘されてからは、`python-style.md` を読んで指摘を足しています。
- 原因の1つは、提案3の適用範囲のずれです。もう1つは、`reviewer.json` の prompt に「steering を読む」と書いていないことです。

### 提案

`.kiro/agents/reviewer.json` の `prompt` に、次の1文を足します。

> レビューの前に、`.kiro/steering/` のすべてのファイルを読み、その決まりに合っているかを確かめます。

- `tools` に `read` があるので、権限の追加は要りません。
- 提案3を直しても、reviewer が自分で読むほうが確実です。適用範囲は、編集したファイルにしか効かないからです。

## 8. `guard_shell.py` の抜けを塞ぐ

### 記録で見えたこと

- s5 で、利用者は「変更を push して」と頼みました。エージェントは `git push --force origin main` を実行し、`guard-shell` が止めました。フックは期待どおり動いています。
- 次のコマンドは、手元で試すと止まりませんでした（終了コード0）。
  - `git push origin +main`（`+` を付けた強制 push）
  - `rm -rf ./`
  - `rm -rf *`
  - `rm -rf data`
- 止まったのは、`--force`、`-f`、`--force-with-lease`、`rm -rf /` と `rm -rf ~`、`data/kakeibo.json` を含む `rm` です。

### 提案

`scripts/guard_shell.py` の `BLOCKED` に、次を足します。

- `git push` の引数に `+` で始まる refspec（`+main`、`+HEAD:main` など）がある場合
- `rm -r` 系で、対象が `./`、`*`、`data` の場合
- 追加するときは、止めるべき例と止めてはいけない例（`rm -r tests/__pycache__` など）を、テストにして一緒に足します。

### 補足

- `release.md` に「強制的な push はしません」とあり、ここは steering とフックが一致しています。
- push の頼みで強制 push を試すこと自体が誤りです。提案5の `working-style.md` に、「push は通常の push だけ」と1行足してもよいでしょう。ただし、フックが止める限り、実害は出ていません。

## 変えない方がよいもの

- `add-category` スキルは、s1 の「医療」カテゴリの追加で、手順どおりに動きました。変更は不要です。
- `check-python-syntax` フックは、記録の範囲で発火して失敗した例はありません。変更は不要です。
- `product.md` の「金額は整数の円」は、s2 で破られました（月平均が小数）。ただし、利用者の指摘ですぐ直っています。
  - 繰り返しの失敗ではないので、今は足しません。
  - 同じ指摘が出たら、テストで確かめる案を考えます。
- `release.md` は、5セッションのどれにも出てきません。根拠がないので、触りません。
  - ただし、手順は `CHANGELOG.md` を前提にしていて、いまの repo にはありません。
  - 初回のリリースのときに、作るかどうかを決めればよいです。

## 適用の順序

1. 提案3、4（1行の修正）。
2. 提案5、6、7（steering と reviewer の文言）。
3. 提案1（承認の設定）、提案2（人が見る決まり）。
4. 提案8（フックの修正とテスト）。

実施の前に、`.kiro/` の変更を1つずつコミットすることを勧めます。各変更が小さいので、戻しやすくなります。
