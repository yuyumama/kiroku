# 開発ハーネス改善の提案

対象は `.kiro/`（steering、hooks、skills、agents）と、そこから呼ばれる `scripts/` です。このファイルを書いただけで、ほかのファイルは変えていません。

根拠は、過去のセッション s1〜s5 と s3（レビュー）のログです。`sess_retro` は `/kiroku-retro` の呼び出しだけで、中身はありませんでした。

## 先に結論（優先順）

| # | 提案 | 直すもの | 根拠 |
|---|---|---|---|
| 1 | `testing.md` の `make test` を直す | steering | s1・s2 で毎回失敗 |
| 2 | `python-style.md` の適用範囲を直す | steering | `src/` が無く一度も読み込まれない。s3・s2 の指摘漏れ |
| 3 | テスト自動実行のフックを足す | hooks | s5「毎回言ってる」、s2「テストは？」 |
| 4 | 繰り返しの指摘を steering に書く | steering（新規） | 結論から（s1・s2）、日本語コミット（s1・s2） |
| 5 | `run_tests.py` だけを自動承認にする | 承認設定 | 5回中5回、承認を押している |
| 6 | reviewer に steering を読ませる | agents | s3 |
| 7 | 前月が無い表示の確認ルール | steering | s4 |

## 1. `testing.md` の `make test` を直す

**問題**
- `testing.md` は「テストは `make test` で実行します」と書いていますが、リポジトリに Makefile はありません。
- s1 と s2 の両方で、まず `make test` を実行して `No rule to make target 'test'` で失敗し、そのあと `python3 run_tests.py` に切り替えていました。承認の手間も1回ずつ無駄になっています。
- s2 の最終報告にも「今回も失敗しています」とあり、エージェントはずれに気づいているのに、直す先がありません。

**案**
- `testing.md` の該当行を `python3 run_tests.py` に直す。README の手順と `reviewer.json` の許可コマンドも、すでに `python3 run_tests.py` です。
- 結果が `reports/junit.xml` にも出ることを、1行足す。

**未決（質問1の「わからない」）**
- 既定は、文書を実態に合わせる案です。Makefile を足すと、手順が2つになり、直す場所も増えます。
- Makefile が必要だと分かったら、`test:` の1行だけ足し、`testing.md` はそのままにする案もあります。判断は、あとから変えられます。

## 2. `python-style.md` の適用範囲を直す

**問題**
- 冒頭の `fileMatchPattern` は `src/**/*.py` ですが、コードは `kakeibo/` にあり、`src/` はありません。このファイルは、どの編集でも読み込まれていません。
- 実際に、s2 で追加された `yearly_totals` と `format_year` には型ヒントがなく、`format_year` は f-string でした（決まりは `%` 書式）。s3 のレビューでも最初は見落とされ、ユーザーが「steering に書いてあるよ」と指摘して、ようやく読まれました。

**案**
- `fileMatchPattern` を `kakeibo/**/*.py` にする。
- テストにも適用するかは、別に決める。いまの書き方の決まりは、テストコードにも当てはまるかを確かめていません。

## 3. テスト自動実行のフックを足す（質問4: 使いたい）

**問題**
- s5 でユーザーが「テストを回してから完了って言って。毎回言ってる気がする」と言いました。
- s2 では、テストを書かずに実装を終えていて「テストは？ testing.md に先にテストを書くって」と指摘されました。s5 でも、`list` の並び替えは、テストを足さず `run_tests.py` を回しただけで終わっています。

**案**（`.kiro/hooks/project.json` に足す）
- `.py` の保存後に `python3 run_tests.py` を自動で動かす。結果は、失敗したときだけ短く返す。
- 既存の `check-python-syntax` は、構文エラーだけを見ます。テスト実行はその次の段階なので、別のフックにする。
- 保存のたびに動かすと、編集の途中で赤が出て、うるさくなる恐れがあります。応答の終わりに1回だけ動かせるトリガーがあれば、そちらを使う。

**確かめること**
- 使える `trigger` の名前（`PostFileSave` のほかに、応答の終了を表すものがあるか）は、ログからは分かりませんでした。Kiro のフックの仕様で確認してください。
- 実行時間は、いまのテスト15件で約 0.006 秒です。`timeout` は 10 秒で足ります。

**あわせて**
- `check-python-syntax` と `guard-shell` が実際に動いているか、ログで確かめられたのは、s5 の `guard-shell`（`git push --force` を止めた）だけです。`check-python-syntax` は、s1・s2 の `.py` 編集で呼ばれた記録がありません。記録されない仕様なのか、動いていないのかは、不明です。
- 足したフックは、先に1回だけ手で動作確認してください。

## 4. 繰り返しの指摘を steering に書く

新しく `.kiro/steering/working-style.md` を作り、次を書きます（常に読み込む形）。

| 指摘 | 回数 | 書く内容 |
|---|---|---|
| 説明が長い。結論から | s1・s2 | 報告は結論を最初の1文にする。詳しい説明は、聞かれたときだけ |
| コミットメッセージは日本語 | s1・s2（s2 は「前にも言ったよ」） | コミットメッセージは日本語で書く |
| テストを回してから完了と言う | s5 | テストの結果を確かめる前に「完了」と言わない。振る舞いを変えるときは、先にテストを書く（`testing.md` と同じ） |

- s4・s5 のコミットメッセージは、すでに日本語でした。ルールが無くても守れる日があるので、書いておく価値は「毎回守らせる」ことにあります。
- 3つ目は、提案3のフックと重なります。steering は理由と手順、フックは強制、と役割を分けます。
- `product.md` の「利用者に見える文言は日本語」は、コミットメッセージには適用されません。同じ場所に混ぜず、別ファイルにします。

**ルールにしないもの**
- s1 の「今回だけ、比較する月は2026-10にして。既定値にはしないで」は、一回限りです。ルールにも、skill にも書きません。
- s4 の「合計と差額が合っているかは私が画面で確かめるから、待ってて」も、その場の依頼です。ユーザーが「合計は一致すればよい」と述べているので、合計の確認の待機は、ルールにしません。

## 5. `python3 run_tests.py` だけを自動承認にする（質問2）

**記録**
- s1〜s5 の `python3 run_tests.py` は、すべて承認が必要で、毎回「accept」が押されていました（約7回）。
- `git commit`（s1・s2・s4・s5）と `git push origin main`（s5 の2回）も承認されていましたが、ユーザーは、どちらも毎回確かめたいと答えています。

**案**
- 自動承認にするのは、`python3 run_tests.py` だけ。
- `git commit` と `git push` は、承認が必要なまま変えない。
- `ls` や `git status` などの読み取りコマンドは、ユーザーが決めていないので、今回は触りません。s4 では `ls -la` を4回承認していました。気になるなら、あとで決めてください。

**注意**
- 自動承認の設定場所と書き方（エージェント設定の許可コマンド一覧か、CLI 側の設定か）は、リポジトリの `.kiro/` から読み取れませんでした。`reviewer.json` の `permissions.rules` の書き方（`"capability": "shell"`, `"effect": "allow"`）を、既定のエージェントにも使えるかを確かめてください。
- 許可は、`python3 run_tests.py` のきっかり一致にします。`python3 run_tests.py && ...` のような連結は通さない。

## 6. reviewer に steering を読ませる

**問題**
- s3 で、reviewer は変更を読んだあと、`python-style.md` を見ずに「テストは十分」と報告しました。ユーザーに指摘されてから、型ヒントと f-string の問題を足しています。
- `reviewer.json` の prompt は「プロジェクトの決まりに合っているか」を指すだけで、決まりのファイルがどこにあるかを書いていません。

**案**
- prompt に、レビューの前に `.kiro/steering/` の `product.md`、`python-style.md`、`testing.md` を読む手順を書く。
- 指摘の形（場所、問題、直し方）は、そのままにする。
- steering と照らした結果（どの決まりを確かめたか）を、1行で最後に書かせる。
- 許可コマンドは、いまの `git diff*`、`git log*`、`git status*`、`python3 run_tests.py` で足りています。変えません。

## 7. 前月が無いときの表示（質問3）

**ユーザーの言葉**
- 「合計は一致すればよい。前月が無いときの表示だけは人が見る」
- 範囲と仕組みの強さは、「わからない」

**案（小さく始める）**
- `working-style.md` に、1項目だけ足す。
  - 月の集計（`report`）の表示を変えたときは、前の月に記録が無い場合の出力を、実際に表示してユーザーに見せる。
  - 見せたあと、ユーザーの OK が出るまで、コミットしない。
- 対象は、前月との差額の行を出す・出さないの判断に関わる変更に限ります。ほかの変更で待つ必要は、いまのところ出ていません。
- コミットは、もともと毎回承認が必要なので、止めるための仕組み（フック）は足しません。承認の画面が、そのまま待つ場所になります。

**あとで見直す点**
- 対象を広げたい（`year` の表示も同じように見たい、など）場合は、その時点で追加します。
- 「毎回」と言ったのが s4 の1回だけなので、ほかのコマンドにも当てはまるかは、実績が出てから決めるのが安全です。

## 見送るもの

- `.kiro/kiroku/data/` の `.gitignore` 追記は、s3 の差分に出てきた別の道具のためのもので、このハーネスの対象ではありません。
- skill `add-category` は、s1 で手順どおりに動き、問題は出ていません。変更しません。
- `release.md` は、`CHANGELOG.md` と `__version__` を前提にしていますが、どちらもまだありません（`kakeibo/__init__.py` は docstring のみ）。リリースの実績はこのログに無いので、今回は触りません。最初のリリースの前に、整合を確かめてください。
- README の使い方に `year` コマンドがありません。`add-category` skill は README を直さない前提ですが、コマンドを足す手順には、README の更新が要るかもしれません。これも、実績が出てから決めます。
- `guard-shell` は、s5 で意図どおり強制 push を止めました。変更しません。ただし、通常の push を頼まれたのに強制 push を試した点は、エージェントの側の問題です。`working-style.md` に「push は強制しない」と1行足す手もありますが、フックが止めているので、必須ではありません。
