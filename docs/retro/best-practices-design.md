# ベストプラクティス集と、承認の繰り返しからの権限の提案：設計と方針

2026-11-24。設計と方針（未実装）。Issue #24 のレビューと、利用者との確認（2026-11-24）で決めたことに基づく。旧版（2026-11-20 の「ハーネスの地図」の設計案。旧ファイル名 `harness-map-design.md`）は git の履歴にある。

## 要点

- `/kiroku-retro` は、いつ実行しても同じ手順で動く。経過した日数や実行の間隔で、処理を変えない。出てくるものを変えるのは、ログ、ハーネスのファイル、過去の回答、採否の記録だけである。実行は、気が向いたときでよい。
- そのために、期間の既定を「直近7日」から「前回の振り返りの後から」に変える（今回の設計で見つけた問題。3.2節）。
- 案と質問の件数の上限を外す。あれば全部出し、無ければ「なし」で終わる。質問は、答えで案が変わる順に並べ、上から答えれば済むようにする。
- 進める順は、段a（D5 の誤判定の修正）、段b（手作業の確認から合格条件を聞き出す）、段c（ベストプラクティス集と、毎回の照らし合わせ）、段d（承認の繰り返しからの許可の提案）。段ごとに PR を分ける。
- ベストプラクティス集は、kiroku を入れるどのプロジェクトにも使える、ハーネスの一般的な手本である。特定のプロジェクト向けには書かない。各項目に「当てはまる条件」（どのプロジェクトにも使える規則）と「満たした証拠」を持たせ、個々の事情はログと質問への答えで判断する。
- 承認の回数は、許可を決める材料ではなく、利用者に聞くきっかけにする。候補は2つ以上のセッションにまたがる承認で、拒否したことのあるもの、外に出る操作、取り返しのつかない操作、任意のコードの実行は外す。残りは、本人に聞いてから案にする。
- 効果は、デモに仕込んだ場面で、今の kiroku と新しい kiroku を AI が比べて確かめる。スクリプトで判定できる部分は自動テストにする。

## 1. 目的との関係

評価の範囲で合意した目的（[evaluation.md](evaluation.md)）は、「同じ指摘・説明の繰り返し（A）と、ハーネス整備の負担（B）を最優先で減らす。不具合・作業失敗の削減（C）も評価する」である。

| 段 | 効く目的 | どう効くか | 効き方 |
|---|---|---|---|
| 段a D5 の修正 | C、B | CI でテストが動いていないのに「動いている」と出ると、確かめる仕組みの欠けを見逃す。誤った診断から外れた案が出て、読んで捨てる手間も増える | 直接。小さいが確実 |
| 期間の既定の変更 | A、B | 間が空いた実行で、7日より前の会話が読まれず、繰り返しの説明を拾い損ねるのを防ぐ | 直接 |
| 段b 合格条件の聞き出し | A、C | 毎回人がしている確認を条件にして自動化し、その確認と説明を減らす | 直接。失敗が無くても手間がある場面で効く |
| 段c ベストプラクティス集 | B、C | 利用者が知らない仕組みに気づけるようにし、質問で確かめてから案にする | 間接。案が採用され、使われて初めて効く。効果は未検証 |
| 段d 承認の提案 | B | 毎回の承認と、許可の規則を自分で書く手間を減らす | 直接。ただし「同じ説明の繰り返し」とは別の種類の負担 |

## 2. 決まったこと（利用者の判断、2026-11-24）

1. 進める順は、段a → 段b → 段c → 段d。
2. ベストプラクティス集の項目は、ログに兆しが無くても候補にする。兆しのある項目を先に並べる。件数は絞らない。
3. 集の更新は、利用者が頼んだときに、kiroku のリポジトリで行う。決まった周期の自動実行は置かない。
4. 集の出典は、公式資料と評価の高い道具に限る。点数は付けない。集はどのプロジェクトにも使える一般的なもので、特定のプロジェクト向けには書かない。
5. 効果は、デモに仕込んだ場面で、今の kiroku と新しい kiroku を比べて確かめる。比較は AI が行い、利用者は読まない。スクリプトで判定できる部分は自動テストにし、中身は AI が評価して、期待と違えば直してから PR を出す。
6. 「地図」という呼び名は「ベストプラクティス集」に変える。
7. 案と質問の件数の上限を外す。質問は、答えで案が変わる順に並べる。設定で 0 を書いたときの「出さない」の意味は残す。
8. 当てはまる条件は、どのプロジェクトにも使える汎用の規則として書く。
9. 手作業の確認は、開発の会話（ノート）と、steering・README・skill に書かれた人の確認の手順から拾う。
10. 承認の回数はすべて出すが、許可を決める材料ではなく、聞くきっかけにする（7節）。
11. 承認の記録の形は、実装の前に、利用者が実機で一度確かめる（承認画面で Allow と Always allow を選ぶ）。確かめられるまでは、分からない値を数えない。
12. いつ実行しても同じ手順で動かす。経過した日数で処理を変えない。

## 3. 全体の方針

### 3.1 いつ実行しても同じ手順

- 振り返りの手順は、毎回同じである。ベストプラクティス集との照らし合わせ、承認の集計、手作業の確認の拾い出しは、毎回行う。
- 何が出るかを変えるのは、データだけである（ログ、ハーネスのファイル、ノート、過去の回答、台帳の採否）。同じデータからは、同じ候補が出る。
- 毎回出しても繰り返しにならないよう、見送った案と、「使わない」と答えた項目は、前提が変わるまで出さない（6.4節、7.2節）。
- 出すものが無ければ「なし」で終わる。何も出ないことを、よい結果として扱う。

### 3.2 期間の既定を「前回の振り返りの後から」にする

**今回の設計で見つけた問題**：今の手順は、期間の指定が無ければ「直近7日」を読む（`SKILL.md` 手順1、各コマンドの `--since 7d`）。気が向いたときに実行すると、7日より前の会話は、何も知らせずに読まれない。実行の間隔で結果が変わる。

- 集約に `--since last` を足し、手順の既定にする。
  - 書き終えた最新のレポートがあれば、その検証値の終わり（`until`）から。そのレポートに未読が残っていた（`unread` が 0 でない）なら、その始まり（`since`）から。読み残しを落とさないため。
  - レポートが無ければ、記録の始まり（`reset.py` の時刻）から。それも無ければ、すべて。
- `--since 14d` のような指定は、これまでどおり使える。
- 1回に読む量は、これまでどおり `retro_read_chars` で区切る。期間が長くても、残りは次の実行で読む。

### 3.3 件数の上限を外す

- 一歩先の改善案（`one_step_max`）と質問（`question_max`）の既定を、「上限なし」にする。設定に整数を書けばその数まで、0 を書けば出さない（今の意味のまま）。
- 導入先の `config.json` に、すでに数を書いている場合は、その数を守る。
- 集約の出力の長さの目安（`retro_output_chars`）と、レポートの一覧の表示の上限（診断値の12件など）は、文脈の長さに収めるためのもので、案や質問の数ではないので残す。全件は、これまでどおり `--section` で出す。

### 3.4 質問の並べ方

- 1回にまとめて出す（今の grilling の形のまま）。並びは、答えで変わる案が大きい順にする。目安は、関わる型の負担（`D6`）が大きいもの、承認ならセッション数の多いもの、ベストプラクティス集なら兆しのある項目、の順である。兆しの無い項目は後ろに置く。
- 質問の冒頭に「上から重要な順です。全部に答えなくて構いません」と書く。

## 4. 段a：D5 の誤判定を直す

- **今の問題（2026-11-24 に確かめた）**：CI の定義の行を、そのままテストの記録設定の正規表現で探している（`diagnose.sensors()`）。コメントの行にテスト名があるだけでも「CI がテストを動かす」と判定する。模擬の CI（`run: echo hello  # python3 run_tests.py は後で足す`）で `ci_runs_tests` が `True` になった。
- **直し方**：照合の前に、コメントを除く。YAML（GitHub Actions、GitLab CI、CircleCI、Azure Pipelines、Buildkite）は、行頭の `#` と、空白の後の `#` 以降（引用符の外）を除く。Jenkinsfile は `//` 以降を除く。
- **テスト**：コメントだけの CI は「一致なし」。実際の `run: python3 run_tests.py` は「一致あり」。実際のコマンドの後ろのコメントは「一致あり」。引用符の中の `#` は除かない。直す前のコードで落ちることを確かめる。
- 文面で一致した行が、実行か言及か（`echo pytest` など）は、これまでどおり区別しない。ベストプラクティス集の「満たした証拠」でも同じ扱いにする。

## 5. 段b：手作業の確認から、合格条件を聞き出す

### 5.1 拾うもの

- **開発の会話**：ノートの種類に `manual_check`（手作業の確認）を足す。利用者が、自分で確かめた・これから確かめる・目で見た、と述べた発話や、エージェントに自分の確認を待たせた発話である。振り返りのエージェントが意味で読んで拾う。語で分類しない（変えない設計）。引用の照合は、ほかの種類と同じ。
- **ハーネスの文書**：手順4（ハーネスと比べる）で、steering・README・skill に書かれた、人が行う確認の手順（例：「リリース前に目視で確かめる」）を拾う。引用（ファイル）を付ける。

### 5.2 集約とレポート

- 集約に「手作業の確認」の一覧を出す（トピック、セッション数、例の引用）。件数は絞らない。
- 期間内に `manual_check` のあるトピックは、セッションの数にかかわらず、「対象の型」（`topic:…`）に入れる。採用した後に、その確認の発話が減ったかを、今の追跡で数えられるようにするため。骨組みの版を上げる（6節）。
- 一歩先の改善案の手がかりに、比較表に出たハーネスのファイルのパスも書けるようにする。文書に書かれた手作業の確認から案を作るため。根拠は、これまでどおり引用（ファイル）で確かめる。

### 5.3 聞き方と案

- 質問の雛形（`references/harness-guide.md` に置く）：「〇〇を、毎回目で確かめています。何が一致すれば、確認済みにできますか。人が見たい例外はありますか？」
- 選択肢：a 条件を書く（自由に）→ 条件の照合を自動にする案（テスト、スクリプト、終了時の hook）／b 毎回人が見る必要がある → 自動にしない。理由を決まりに残す案だけを出す／c わからない → 様子見／d その他。
- 例：「通常分は合計が一致すればよい。返金だけは人が見る」→ 通常分の照合を自動にし、返金だけを人に知らせる案（V3「確かめる手段を渡す」）。

## 6. 段c：ベストプラクティス集と、毎回の照らし合わせ

### 6.1 集の形

- `kit/.kiro/skills/kiroku-retro/references/best-practices.md` を同梱する。冒頭に集の版（整数）を書く。
- 項目は、変えない ID（例：`BP-S2`）を持つ。消した ID は使い回さない。各項目に書くこと：
  - 何のためか（言い換えつき）
  - 当てはまる条件（どのプロジェクトにも使える規則）
  - 満たした証拠（スクリプトが見るもの）
  - 案の形（hook、テスト、steering など）
  - 聞き方（質問の雛形と、選択肢）
  - 出典（URL、確認した日、Kiro の版に依存するなら対象の版）
- 判定はスクリプト（新しく `practices.py`）が ID ごとに持つ。集の ID とスクリプトの ID が一致し、各項目に出典と確認した日があることを、テストで確かめる。

### 6.2 最初の版の項目（案）

レビューの指摘を受け、項目ごとに当てはまる条件と、満たした証拠を決めた。状態は「満たしている」「満たしていない」「当てはまらない」「未確認（スクリプトでは決められない）」のどれかである。

| ID | 項目 | 当てはまる条件 | 満たした証拠 | 主な出典 |
|---|---|---|---|---|
| BP-G1 | 毎回読ませる決まりがある | 常に | AGENTS.md（どの階層でも）か、常時読み込みの steering | Kiro Steering、Codex AGENTS.md、Claude Best practices |
| BP-S1 | テストの実行方法が決まっていて、kiroku が結果を取り込める | テストのファイルか、テストを実行する手段（package.json の test、Makefile の test、テスト用のスクリプト）がある | テストの記録設定がある | Claude Best practices（通ったか落ちたかを返すもの）、Kodus |
| BP-G2 | 決まりに、テストの実行方法が書いてある | BP-S1 を満たす | 常時読み込みの決まりに、テストの記録設定に当たる行がある | Claude Best practices、Codex AGENTS.md |
| BP-S2 | 作業の終わりか保存時に、検査を動かす hook がある | BP-S1 を満たす | kiroku 以外の hook のうち、トリガーが終了時・保存時・タスクの後で、呼ぶコマンドがテストの記録設定か lint の設定に当たるもの | Kiro Hooks、Claude Best practices、Fowler |
| BP-S3 | lint・整形の設定がある | プログラムのコードがある | 今の D5 の lint | Kodus、Factory |
| BP-S4 | コミットの前の検査がある | BP-S1 か BP-S3 を満たす | 今の D5 の pre-commit | Kodus、Factory |
| BP-S5 | CI がテストを動かす | BP-S1 を満たし、git のリモートがある（手元だけで完結するプロジェクトは当てはまらない） | CI の定義の、コメントを除いた行に、テストの記録設定に当たる行がある（段a） | Kodus |
| BP-P1 | 取り返しのつかない操作を止める規則がある | 常に | リポジトリの中のエージェント定義の deny 規則に、`rm -rf`、`git push --force`、`git reset --hard`、`sudo` に当たるものがある。ワークスペースとユーザー共通の規則はリポジトリの外にあり見ないので、無ければ「未確認」 | Kiro Permissions、Claude Permissions |
| BP-P2 | 毎回承認している操作が、規則になっている | 常に | 承認の候補（7節）が無い | Kiro Permissions、Claude `/fewer-permission-prompts`、Codex rules |
| BP-P3 | 秘密のファイルの読み取りを止めている | リポジトリに `.env`、`*.pem`、`*.key` などがある | BP-P1 と同じ見方。無ければ「未確認」 | Kiro Permissions |
| BP-G3 | 決まりを、条件付きの読み込みに分けている | 常時読み込みの合計が目安（8,000 文字）を超えている | fileMatch・auto・manual の steering がある | Kiro Steering、Claude Best practices |
| BP-G4 | 繰り返す手順が skill になっている | 会話からの型の候補がある | kiroku 以外の skill がある（その型に関わるかは、エージェントが読んで決める） | Kiro Skills、Claude Best practices |
| BP-R1 | 大きな変更を、spec や計画として残している | 未確認（会話から、エージェントが判断する） | `.kiro/specs/` がある | Kiro Specs、Claude Best practices |
| BP-R2 | セッションの始めに、状態や前提を渡す | 未確認（繰り返しの説明のうち状態にあたるものがあるかを、エージェントが判断する） | SessionStart の hook がある | Kiro Hooks、Anthropic の長時間の作業のハーネス |
| BP-E1 | 依存を固定している | 依存を定義するファイルがある（package.json、pyproject.toml、requirements.txt、go.mod、Cargo.toml など） | ロックファイルがある | Kodus |

- memories（一貫して守らせたいことは steering に書く）は、保存場所とログでの形を確かめていないので、最初の版では参考として載せ、候補にしない。
- 外部依存を持たない家計簿のデモでは、BP-E1 は「当てはまらない」になる（レビューの指摘）。

### 6.3 照らし合わせ（毎回）

- 集約が、毎回すべての項目の状態を決め、「ベストプラクティス集との照らし合わせ」の節に出す。冒頭に、集の版と、いちばん古い確認日（何か月前か）を書く。日付は表示だけで、処理は変えない。
- 「満たしていない」かつ「当てはまる」項目を、候補（`practice:<ID>`）にする。
- 並びは、兆しのある項目を先にする。兆しは、項目ごとにスクリプトが決める（例：BP-S2 なら、テストの回帰候補、書き込みの後にテストを実行したターンの少なさ。BP-G3 なら、常時読み込みの合計。BP-P2 なら、承認の候補の数）。兆しの無い項目は、集の並び（前提の順）で後ろに置く。
- 状態が「未確認」の項目は、候補とは別に一覧に出す。エージェントが会話と文書から判断し、要るときだけ質問にする。

### 6.4 振り返りでの使い方

- 手順4（ハーネスと比べる）で、照らし合わせの結果を読む。手順5で、候補を質問にする（言い換えと見立てつき。件数は絞らず、3.4節の順）。
- 答えを受けて、手順6で一歩先の改善案にする。手がかりに `practice:<ID>` を書き、対象の型にも `practice:<ID>` を書く（採否と、その後の追跡のため）。
- 見送った項目（台帳で、対象の型が `practice:<ID>` の案を見送ったもの）は、候補から外す。集のその項目の確認日が、見送った日より新しくなったら（外の知見が変わったら）、また候補にする。
- 「使わないと決めている」という答えは、スクリプトでは分類しない。エージェントが「前回までの回答」を読んで、新しい兆しが無ければ聞き直さない。

### 6.5 レポートと検査

- 骨組みを作るときに、集の版、候補の ID、照らし合わせの行を、state に控える（`report_practices`）。レポートの「ハーネスの診断」の節には、控えから作った行を書く。検査は、控えから同じ行を作り直して照合する。集を `--update` で更新しても、以前のレポートの照合が崩れない（レビューの指摘）。
- 一歩先の改善案の手がかりとして認めるもの：集約の型、診断値、控えた `practice:<ID>`、比較表のハーネスのファイルのパス。
- 集の文面は、引用（ファイル）で引用させない。集は kiroku が配るもので、更新のたびに文面が変わり、以前のレポートの照合が崩れるため（レビューの指摘）。集は、ID と版で指す。
- 対象の型に `practice:<ID>` と承認の型（7節）、手作業の確認のトピック（5節）が入るので、骨組みの版を上げる。以前の版のレポートは、作ったときの版の規則で検査する（今の `as_version` の仕組み）。

### 6.6 更新のしかた

- 利用者が「ベストプラクティス集を更新して」と頼んだときに、kiroku のリポジトリで、出典を読み直して更新する。版を上げ、各項目の確認日を直し、PR にする。導入先には `--update` で配る。
- 振り返りのエージェントには web を調べさせない。同じ入力で同じ結果にし、出典を人が確かめられ、利用者のコードや会話を外に出さず、エージェントの権限を広げないため。

## 7. 段d：承認の繰り返しからの、許可の提案

### 7.1 数えるもの

- 開発のセッションのログで、承認画面に人が答えた呼び出し。`tool_call` と、同じ `toolCallId` の `interaction_resolved` を結ぶ。振り返りのセッションと、kiroku 自身のコマンドは数えない。
  - 承認：`selectedOption` が承認を表す値（実機で確かめた値だけ。今は `accept`）。
  - 拒否：`selectedOption` が `reject`。
  - 取り消し：`outcome` が `cancelled`。
  - 知らない値：「不明」として別に数え、承認には数えない（実機で確かめるまで）。
- まとめ方：シェルは、今の集約と同じコマンドの見出し。MCP は、サーバーとツール。web の取得は、取得先のドメイン。そのほかは、ツールの名前。
- 集約に「承認の記録」の節を出す。見出しごとに、承認・拒否・取り消しの回数、セッション数、最後に承認した日、危険の区分、候補かどうかを、件数を絞らずに出す（出力が長いときは、全件を `--section approvals` で出す）。

### 7.2 候補の決め方

| 段階 | 誰が決めるか | 決め方 |
|---|---|---|
| 入口 | スクリプト | 2つ以上のセッションにまたがって承認している（`approval_min_sessions`、既定2。最初の値）。1つのセッションに固まったものは、その場限りの作業として、候補にしない |
| 外す | スクリプト | 同じ見出しを一度でも拒否したもの（中身で判断している）。危険の区分が「外に出る」「取り返しがつかない」「任意のコードの実行」のもの |
| 規則の範囲 | スクリプト | 7.3節 |
| 本人に聞く | 質問機能 | 「毎回確かめたいものですか、それとも自動で通してよいですか」。見立てに、回数、セッション数、最後に承認した日を添える。わざと毎回確かめている操作を、許可にしないため |

危険の区分は、コマンドの文面から決める（利用者の発話ではないので、変えない設計には当たらない）。区分の表は、出典（Kiro の deny の例、Claude の「任意のコードの実行」、phx:permissions の区分）とともに、`references/harness-guide.md` に置く。

| 区分 | 例 | 扱い |
|---|---|---|
| 読み取り | `git status`、`git diff`、`git log`、`ls`、`cat`、`grep` | 候補になる |
| 手元の検査 | テストの記録設定に当たるコマンド、lint、型検査、ビルド | 候補になる |
| 手元の書き換え | `git add`、`git commit`、`mkdir`、`mv`、`cp` | 候補になる（質問で確かめる） |
| 外に出る | `git push`、`curl`、`wget`、`gh`、`npm install`、`pip install`、`npm publish`、`docker push`、`ssh` | 外す |
| 任意のコードの実行 | `python -c`、`bash -c`、`sh -c`、`node -e`、`eval`、`npx`、`docker exec` | 外す |
| 取り返しがつかない | `rm -rf`、`git reset --hard`、`git push --force`、`git clean -f`、`sudo`、`chmod -R 777`、`kill -9` | 外し、deny の案の候補にする |
| 区分を決められない | 上のどれにも当たらない | 候補になる。エージェントが中身を見て、要らなければ外す |

### 7.3 規則の範囲と、確かめ方

- 観測したコマンドの違いを覆う、最も狭い段にする。全部同じなら完全一致、先頭2語が同じなら2語＋`*`、先頭1語が同じなら1語＋`*`。それでも覆えなければ、案にしない。
- 出さないもの：`*` だけの規則。`sudo`・`env` で始まるコマンドの、2語・1語の段（Kiro も出さない）。引数まで絞る規則（Claude の資料が壊れやすいとする）。
- スクリプトが、Kiro の文書に書かれた当たり方（`*` は任意の文字の並び、つないだコマンドは分けて判定）で、案の規則を試す。観測したコマンドには当たり、危険な変形（同じ先頭の語の `push --force`、`reset --hard`、`-C . push` など）には当たらないことを確かめる。当たってしまう段は使わず、狭い段に戻すか、案にしない。案には「当たる例」と「当たらない例」を添える（Codex の `match`／`not_match` と同じ考え）。
- deny の案には、当たらない書き方が残ること（例：`git -C . push`）を添える。deny は守りの境界ではない。

### 7.4 案の書き方

- 主な反映の手順：「次にこの承認画面が出たら、Always allow を選び、段は〇〇、範囲は This workspace を選ぶ」。ファイルの編集が要らない。
- チームで共有したいときのために、リポジトリの中のエージェント定義の `permissions` に書く文面も添える。ワークスペースの規則は利用者ごとで、リポジトリに入らないことも書く。
- 区分を決められない承認が多いときは、Approve for me を、注意（有料、判定の費用、「セキュリティの仕組みの代わりにはならない」）つきで紹介する。決まった規則（狭い allow と deny）を先に勧める。

### 7.5 追跡

- 対象の型を `approval:<見出し>` にし、承認の時刻を発生として数える。採用した後に、その承認が減ったかを、今の「採用した案の追跡」で数える。
- 反映の日は、ワークスペースの規則のファイル（`~/.kiro/workspace-roots/<hash>/permissions.yaml`）の更新時刻で決める。`<hash>` は、セッションのログの置き場のフォルダ名と一致する（CLI 3.2.1 で実測）。ファイルを見つけられなければ、これまでどおり「反映を確認できない」と出す。

- 場面は、役に立つべきものと、余計な案を出してはいけないものの両方を入れる（[demo-cases.md](demo-cases.md) に D28〜D35 として足す）。

## 9. 変えない設計との関係

- 記録はスクリプトで決定論的に行い、LLM は振り返りだけで使う：記録のフックは変えない。承認はログから読む。ベストプラクティス集の判定、承認の集計と区分、規則の当たり方は、スクリプトが決める。
- 記録の時点では分類しない：変えない。
- 発話を正規表現やキーワードで分類しない：手作業の確認は、エージェントがノートで意味から拾う。「使わない」という答えも、スクリプトでは分類しない。危険の区分は、コマンドの文面から決める（発話ではない）。
- 会話の本文は保存しない：変えない。ノートとレポートの引用は、これまでどおり短い一節だけ。
- 振り返りのエージェントはハーネスを変えない：権限の規則も、案として示すだけである。反映は人が行う。
- エージェントの申告をそのまま使わない：引用の照合、候補の判定、規則の当たり方の確かめを、スクリプトが行う。
- 生のデータを git に載せない：変えない。

## 10. 既存の導入先への影響

見込みは、すべての段で「`--update` だけで済む」。ただし、振る舞いは次のように変わる。

- 期間の既定が「前回の振り返りの後から」になる。更新した後の最初の振り返りは、前回のレポートの後の会話をすべて読む対象にする（1回に読む量は、これまでどおり区切る）。
- 案と質問の件数の上限が無くなる。`config.json` に数を書いていればその数を守り、書いていなければ上限なしになる。元に戻したいときは、`one_step_max` と `question_max` に数を書く。
- 振り返りの集約に、手作業の確認、ベストプラクティス集との照らし合わせ、承認の記録の節が増える。
- 骨組みの版が上がる。以前の版のレポートは、作ったときの版の規則で検査する。
- 新しい設定（`approval_min_sessions`）は、既定値をコードに持つ。`config.json` の書き換えは要らない。
- ノートの種類が1つ増える（`manual_check`）。以前のノートは、そのまま読める。
- state に項目が増える（`report_practices` など）。以前の版のスクリプトは、この項目を読まない。
- フックと、専用エージェントの権限は変えない。手作業は要らないので、インストーラーの注意の表示は足さず、README の「導入と更新」に書く。

## 12. 実機で確かめること（予定。実装の後に、手順を詳しくして渡す）

実装の後に、AI に実施させるための手順書を作る。今の時点で予定している項目は次のとおり。

1. **承認の記録の形（段d の前に必要）**：Kiro CLI 3.4 系で、承認画面で Allow（1回）、Always allow（段と範囲を選ぶ）、Deny を選び、ログの `interaction_resolved` の `selectedOption` と `outcome` の値、`toolCallId` での結び付きを記録する。Always allow で保存された規則のファイルの場所と中身も記録する。
2. **規則の当たり方**：Always allow で2語＋`*` の規則を作り、同じ先頭2語の別のコマンドと、危険な変形で、承認画面が出るかを確かめる。
3. **期間の既定**：前回の振り返りから間を空けて実行し、前回の後の会話がすべて対象になることを確かめる。
4. **振り返りの通し**：デモに D30〜D35 の場面を作り、`/kiroku-retro` を通して実行する。質問の並び、件数を絞らないこと、質問の後にターンを終えて待つこと、ベストプラクティス集の候補、承認の案、レポートの検査が通ることを確かめる。
5. **更新の互換**：以前の版の kiroku を入れたデモに、`install.sh --update` をかけ、以前のレポートの検査が通ることと、記録が止まらないことを確かめる。

## 13. 未確認のこと

- 承認画面で Allow と Always allow を選んだときの `selectedOption` の値（CLI 3.3.0 で見たのは、拒否、取り消し、承認した後の中断だけ）。
- 既定の権限で、読み取りだけのコマンドに承認画面が出るか。
- Kiro の規則の当たり方の細部（文字列全体に当たるのか、先頭に当たるのか）。文書の例からは、全体に当たると読んだ。
- memories の保存場所と、ログでの形。
- OpenAI「Harness engineering」の記事の本文（403 で未読。アーカイブ経由の取得は、制限の迂回にあたるため行っていない）。
- 外部の知識が逆効果になる場面があること（SkillsBench の初版では、手で整えた skill で平均16.2ポイント上がった一方、84タスク中16で下がった）。ベストプラクティス集の案も、比較で確かめてから広げる。
