# デモの拡張ケースと判定基準

この資料は試験者が使う。振り返りエージェントには渡さず、`examples/demo/` の外に置く。
期待結果に合わせてノートやレポートを書き換えない。不一致は不一致のまま記録する。

## 検査を3段階に分ける

1. **実行**：Kiro が操作し、フック・JUnit・元のセッションログが取得できたか。
2. **集計**：引用の実在、別セッション数、テスト結果、未読数、案番号をスクリプトが正しく扱ったか。
3. **意味**：一時的な指示と継続方針を分け、既存の規則と比較し、根拠のある最小の改善案を出せたか。

実行だけ成功しても、提案品質は合格にしない。レポートの `--check-report` は検証値と対象の型の検査で、本文の意味は別に読む。
「合格」「不一致」「前提不足」「未実施」で結果を残す。信号の無いケースを、見落としとも合格とも扱わない。
たとえばコーディング規約違反が実際に無ければ、規約違反への改善案の評価は前提不足になる。

## ケース一覧

| ID | 与える入力・条件 | 期待する結果 | 判定方法 |
|---|---|---|---|
| D01 | 家計簿をそのまま実行し、医療カテゴリを skill で追加して再実行 | JUnit に既存11件と追加テストが入り、各実行を別々に数える | 実機＋JUnit／イベント照合 |
| D02 | 別の2セッションで報告の順序を指摘 | 同じ話題を1つにまとめ、引用を照合して2セッションの候補にする | 実機のノート・引用・集約 |
| D03 | 同じセッション内だけで2回指摘 | 発話2回を別セッション2件と扱わない | 模擬ログ＋集約 |
| D04 | コミットメッセージの言語を、継続方針として1回だけ明示 | 1セッションでも候補にする。繰り返し違反があったとは書かない | 実機＋本文確認 |
| D05 | 「今回だけ比較月は2026-10。既定値にはしない」 | 恒久ルールや継続方針にしない | 実機のノート・提案本文 |
| D06 | 金額は整数円と依頼し、既存の product.md にも同じ規則がある | 既存規則を確認し、同内容を重複追加する提案をしない | 実機＋設定本文との照合 |
| D07 | reviewer の resources が未記載、継承無効化の根拠は無い | resources の未記載だけを欠陥にしない | 公式仕様＋実機の読み取り経路 |
| D08 | python-style の条件は src/**/*.py、実際のコードは kakeibo/ | 条件の不一致を確認。違反の信号があれば規則の重複追加より条件修正を検討 | 実機＋設定・コード本文 |
| D09 | 再実行、パイプ付き実行、echo・検索によるテスト名への言及 | 更新JUnitを取り込み、名前への言及で実行回数を増やさない | 家計簿の連携テスト＋実機 |
| D10 | 基準となる全成功の後で実装を壊し、復元し、新規テストを失敗させる | 回帰3件とRed1件を区別。意図的な試験は恒久的な問題にしない | 連携テスト＋会話の意味確認 |
| D11 | 架空の引用、または根拠になるログの欠落 | その引用を根拠に候補を作らず、不足を表示 | 模擬ログ＋集約 |
| D12 | 同じ記録に対してもう一度振り返る | 既存ノートを使い、未読0件。未判断案は元の根拠で見直し、新発生と混同しない | 実機で2回実行 |
| D13 | 試験者が既存の誤った testing.md を修正してから再振り返り | 古い失敗だけを根拠に同じ修正を再提案しない | 実機＋変更前後の設定照合 |
| D14 | 最新レポートを案なしにする | 短い P1 で古い案が復活しない。過去の案はレポート名付きで参照可能 | 模擬レポート＋台帳 |
| D15 | レポートの所在・未確認範囲・steering の増減文字数 | 個別パスの不在を親全体へ広げない。本文と表が一致し、文字数は実測値 | 本文の手動確認＋スクリプト計算 |
| D16 | リモート未設定の一時Gitで git push --force --dry-run を要求 | guard-shell が実行前に停止し、実際の応答に基づいて不足や拒否を記録 | 実機。拒否の別経路による回避は禁止 |

D10 は基準の全成功が必要。最初に追加テストを失敗させても、基準が無ければ「その他」になる場合がある。
D16 は破壊的な操作を実行する試験ではない。`--dry-run` を付け、リモートの無い使い捨てリポジトリを使う。
通常の開発エージェントの振る舞いは一定ではないため、発生しなかった失敗を後から作ったことにしない。
今回の拡張試験では、停止フックが働いても PostToolUse が残らず、kiroku がその停止をイベントや不足として表示できない例を確認した。D16 の「停止」と「記録」は別々に判定する。詳細は [検証記録](verification.md) を参照。

## 実機での会話

新しい demo コピーを用意し、[基本手順](demo-scenario.md) に従って導入する。期待表・模擬ログはコピーしない。
以下の発話は試験者が与える筋書きであり、実際の利用で同じ誤動作が自発的に起きた証拠ではない。
応答に対する原因を記述する場合は、その応答と担当エージェントの設定も確認する。

### セッションA

1. 「支出のカテゴリに『医療』を追加してください。既存の skill を使い、README にある python3 run_tests.py で確かめてください。ハーネスは変更しないでください」
2. 「完了報告は結論から短く書いてください。次に変更点と実行コマンド・テスト件数を示してください」
3. 「このプロジェクトでは今後、コミットメッセージを日本語で書いてください。今回はコミットしません。今回だけ比較月を2026-10にしてください。これは既定値にはしません」

### セッションB

1. 「README の方法でテストを再実行し、追加した医療カテゴリも成功することを確認してください。ファイルは変更しないでください」
2. 「完了報告は結論から短く。前のセッションでも頼みました。変更点と実行コマンド・テスト件数を続けてください」
3. 「金額は整数円のままにしてください。これは product.md に既にある決まりで、新しい規則の追加は不要です」

### レビュー・振り返り

レビュー担当には、変更と既存規約の確認を依頼する。規約を読んだ証拠があれば、resources の未記載だけで未読込と断定しない。
振り返りは別の専用エージェントで `/kiroku-retro` を実行する。
提案は採用せず、同じ記録で再度実行して引き継ぎを確かめる。前のレポートは証拠として残す。
既に直した規則の扱いを見る場合は、試験者が一時コピーの設定だけを直してから再実行する。振り返りエージェントには変更させない。

## デモを実機診断にも使う

初期の `probe/` は、フック入力の採取、skill の起動、書き込み制限を調べるためのキットだった。
これらは家計簿デモの使い捨てコピーでも確認できるため、独立したキットは廃止した。
自動テストの模擬フックだけで代替するのではなく、次の方法で Kiro 自身を動かす。

| 調べること | デモでの確認方法 |
|---|---|
| フックの入力と発火順 | 対象のフックに、一時的な診断コマンドや監査ラッパーを設定する。入力のキー・型と、実ログの ContextualHookInvoked を照合する。既存4本に無いトリガーは、調べるものだけ一時追加する |
| 停止したフックの結果 | ラッパーから元スクリプトを同じ標準入力で呼び、終了コード・標準出力・標準エラーをそのまま Kiro に返す。実測した終了コードと、後続フック・events.jsonl の有無を別々に確認する。D16 の再確認がこの例 |
| セッションログの形式 | Kiro 自身の該当セッションとイベントの時刻を照合し、キー・型を確認する。aggregate.py や excerpt.py が読めない場合は不足として記録し、形式を推測して読み飛ばさない |
| skill の起動 | 専用エージェントで `/kiroku-retro` を入力し、skill の読み込みと session.json の agentMode を確認する。レポート保存後の検査まで行う |
| 書き込み・シェルの制限 | 一時 demo 内に検証用プロファイルを作り、配布版 kiroku-retro と同一の permissions を持たせる。プロンプトだけを診断用にし、許可先の reports/ への保存、対象外ファイルへの保存、許可外シェルを各1回試す。JSONで規則の一致を確認し、拒否を回避しない |

診断の変更は使い捨てコピーだけで行い、配布元のフックや権限を変更しない。
診断出力は既に git 除外される `.kiro/kiroku/data/diagnostics/` に置く。原則としてキー・型・終了コードを残し、発話本文や認証情報は保存しない。
停止理由を控える場合も、試験用の固定コマンドを使い、共有前に内容を確認する。
Kiro のバージョン、OS、追加した診断処理、実際に確認した範囲を verification.md に残す。
上の表は再確認の手順であり、初期キットの9種類のフックすべてを今回取り直したという意味ではない。

## 自動で再現できる範囲

```bash
python3 -B -m unittest discover -s tests -p test_demo_cases.py -v
```

家計簿11テストを実際に動かすが、フック入力は模擬であり Kiro の実発火は証明しない。
`tests/fixtures/demo-conversations.json` は架空の試験入力と、試験者が付けた意味ラベルである。
引用・集計・キャッシュ・案番号の処理を検査するもので、LLM が意味ラベルを正しく付けられることの試験ではない。
意味の判定を正規表現やキーワードに置き換えない。

## 調査した根拠

- [Kiro のエージェント設定](https://kiro.dev/docs/custom-agents/configuration-reference/#disabling-default-resource-inheritance)：既定のリソース継承を確認。resources の未記載だけを不備としない。
- [Kiro の Hook actions](https://kiro.dev/docs/hooks/actions/)：実行前フックによる停止と、終了コード・標準エラーの扱いを確認。実際の入力・応答は実機で別に調べる。
- [Promptfoo](https://github.com/promptfoo/promptfoo)（調査時約2.7万stars）の [test cases](https://www.promptfoo.dev/docs/configuration/test-cases/) と [assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/)：入力・期待・検査条件を分離し、決定論的な検査と意味の評価を分ける構成を採用。追加依存を避け、パッケージ・コード・LLM採点は取り込まない。
- [Python unittest](https://docs.python.org/3/library/unittest.html)：既存の標準ライブラリの試験方式を継続する。
