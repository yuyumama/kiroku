# 評価計画と現在の証拠

## 合意した評価範囲

同じ指摘・説明の繰り返しと、ハーネス整備の負担を最優先で減らす。不具合・作業失敗の削減も評価する。
週次を想定し、評価中は手動起動する。自動起動・自動採否・適用・提案管理は今回評価しない。
過去の会話の再検証を目的とした独自保存は行わず、現在のハーネスへの改善を優先する。

## 現在確認できたことと未確認のこと

- Python テストでは、記録・集約・導入・ログのページ取得・文脈の抜粋を模擬入力で検証する。
- 公式資料では CLI V3／IDE 1.x の共通フック形式、execute_pwsh、エクスポート機能を確認した。[仕様調査](compatibility.md)
- 以前の CLI 3.2.1 実測は [verification.md](verification.md) に残る。今回の変更後の証拠とは区別する。
- Windows のファイルロック、PowerShell の実応答形式、IDE のログ本文形式、専用エージェントの製品上の権限制御、LLM の提案品質は未検証。

## 妥当性の評価

記録を決定的な処理にし、原因の判断を後から行う分離は妥当。実行時の Git 状態・ハッシュ・JUnit は、会話ログだけでは復元できないのでフックに残す。
会話はログを唯一の本文ソースにし、ユーザー発話の一次確認と候補周辺の取得に分ける。キーワードのみの絞り込みは、繰り返し説明する負担を見逃すため行わない。

ただし、次の分類は推定であり、変更を自動適用できる根拠にはまだならない。

- 新規に観測した失敗やテストファイル変更は、正常な TDD を意味しない。
- 成功基準は現在全 test_run に共通で、異なるテストコマンド・部分実行が混在すると分類に影響する。評価では固定のテスト範囲を使い、複数スイートの基準分離は今後の改善候補とする。
- 現在の内容とエージェントの最終保存ハッシュが違うことは、人による修正を証明しない。
- フックの欠落やログ形式変更、セッションが記録対象に登場しない場合は会話を網羅できない。
- 現在のハーネスは事象発生時と異なる可能性がある。既に解消された問題を再度修正しない。

## 製品連携の試験

使い捨てのプロジェクトで実施する。Kiro のバージョン、OS、Python 起動名を記録する。
CLI Linux、CLI Windows PowerShell、IDE Windows でそれぞれ確認する。

1. `examples/demo/` を一時ディレクトリにコピーして Git 初期化・初期コミットする。
2. 対応する install.sh／install.ps1 で導入し、3本のフックが読み込まれることを確認する。
3. テスト成功、意図した失敗、実装だけを壊した失敗を順番に起こす。JUnit と Git 状態の取り込みを確かめる。
4. シェル失敗・取り消し・権限拒否を各1回実行し、種類・終了コードを確認する。recording_gap があれば実入力を調べ、対応済みと扱わない。
5. 日本語・空白入りパスで作成・追記・置換し、ハッシュを確認する。同時フックでも JSONL が壊れないことを確認する。
6. ユーザー発話が events.jsonl に本文として保存されないこと、ログから発話一覧を取得できることを確認する。IDE は Export Chat の展開先を指定する。
7. セッション一覧と1件ずつの要約表示で会話を読めること、候補の前後だけ AI 応答の全文を取得できることを確認する。ノートを書いたセッションが次回「ノートあり」になることを確認する。
8. ログなし・壊れたログで、会話に基づく判断を保留できることを確認する。
9. 専用エージェントで `/kiroku-retro` を実行し、レポートを書けること、ハーネスへの直接書き込みや許可外シェルを拒否することを確認する。

## 提案品質の試験

実セッションまたは明示的に模擬と分かるログ・設定で、次のケースを用意する。

| ケース | 期待する判断 |
|---|---|
| 別セッションで同じ開発手順を説明し直す | 既存手順と照合し、欠落・未読込・適用条件を区別する |
| 同じ指示が steering に存在するのに守られない | 同じルールを重複追加せず、効かない原因に対応する |
| 継続的な方針を一度だけ明示する | 一度でも候補にする |
| 「今回はこの値で試して」という一時的指示 | 恒久ルールにしない |
| 意図した Red と、実装破壊による失敗 | 失敗数だけで善悪を決めず、意図・原因を確認する |
| プロジェクトにはないがユーザー共通設定に同じ規則がある | 不在と誤認せず、優先順位・適用条件を比較する |
| MCP がないが現在の機能で作業できる | MCP を機械的に追加しない |
| ハーネスもイベントもないが README にテスト手順がある | 必要性に基づく初期提案として区別する |
| 失敗後にハーネスが修正済み | 古い事象を理由に不要な変更を足さない |

提案ごとに、根拠（別のセッション2件以上の引用、または記録）、対象ファイル、既存ルールとの対応、変更の内容、形を選んだ理由、確かめ方を確認する。
改善案は文章で示す。差分の生成と適用は、今回の評価の対象外とする。
未実施の検証を成功と記載しない。

今回の合格は記録取得・提案品質について判定する。実際の指摘回数や整備時間の削減は、継続利用後の効果測定として別途確かめる。

## CLI 3.2.1 での実機確認（2026-11-12 追記）

ユーザーが通常の端末から使い捨て demo プロジェクトでテスト実行を依頼し、生成されたイベントと実セッションログを読み取り確認した。

- UserPromptSubmit と PostToolUse により、prompt 1件・test_run 1件を記録。
- prompt イベントは schema v2 で、本文の text フィールドを持たない。
- test_run の終了コードは0、JUnit から成功したテスト1件を取得。コミットハッシュも取得。
- aggregate --prompts は同じ session ID の実ログからユーザー発話を取得。coverage は ok、欠落報告なし。
- excerpt は該当ユーザー発話と、その後の AI 応答・ツール実行を読み出せた。

これは Linux CLI での正常系1ケースの証拠。失敗・書き込み・権限拒否・振り返り品質・Windows／IDE は引き続き未確認。

### 実装変更による失敗の記録（2026-11-13 JST）

同じ実セッションで、ユーザーが意図的に add を減算へ変更し、テスト失敗を維持するよう依頼した。

- calc.py（当時のサンプル。現在は家計簿の CLI に置き換え）の保存をフックが取得。二つの保存イベントを集約では1回の書き込みとして計上。
- テスト実行は累計2回。以前通っていたテストの失敗を回帰候補1件として分類し、Red 候補・その他は0件。
- ユーザー発話はログから2件取得、coverage は ok。
- この失敗は検証のための明示的な依頼であり、AI が独断で不具合を起こした根拠ではない。振り返りでは不要な恒久ルールを提案しないことを確認する。
