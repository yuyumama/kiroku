# コードの判定の見直し

2026-11-19。kiroku のスクリプトが行っている判定を全部見直し、コードに残すものと、振り返りのエージェントに任せるものを分け直した。
実装は自動テストだけで確かめていて、実機の振り返りでの効果は未検証。

## 要点

- きっかけは2つの報告である。モノレポで D2（参照先が無い）が130件以上の誤検出を出した。vitest のテストの失敗が、テストファイルを書き換えていても「テストファイルは変更なし」の回帰候補になった。
- 2つに共通する原因は、コードが分からない場面で断定していたことである。「無い」「変更なし」「人間の手直し」と書いていた。コードを使うこと自体が原因ではない。
- そこで、スクリプトの判定を3種類に分けて見直した。数える（事実）、形式を読む（ログ、JUnit、構文）、意味を決める（参照か例か、誰が変えたか）。
- 数えるものと形式を読むものは、コードに残す。ただし、確かめた形だけを読み、分からないものは「特定できず」「候補」と書く。
- 意味を決めるものは、コードが候補を絞って根拠（行の文面、時刻、コマンド）を添え、エージェントが決める。エージェントに渡す量は、トークン量で上限を決める。
- 目的は、失敗を数えて直すことだけでなく、事実から一歩先の案を出すことである。そのために、安く作れる事実を2つ足した。要約表示の、失敗したシェル実行とテストの終了コード。`D5` の、書き込みの後にテストを実行したターンの数。

## 1. 置き場所の決め方

| 置き場所 | 条件 |
|---|---|
| コード | 入力の形が決まっている（ログ、JUnit、設定、構文）。結果を検証値や追跡に使う（実行ごとに揺れては困る）。件数が多く、1件ずつ読むと費用が大きい |
| エージェント | 文脈を読まないと決まらない（参照か例か、やり直しか続きの作業か、誰が変えたか）。どうせ読む文書や会話の中にあり、追加の費用が小さい。誤ったときの害が大きい（実在するファイルを直す案になる） |
| 分担 | コードが候補を絞り、根拠を添えて出す。エージェントは、案に使うものだけを確かめる。断定できないものは「候補」「特定できず」と書く |

トークン量は、出力の文面から次の目安で見積もった。日本語は1文字でおよそ1トークン、英数字と記号は4文字でおよそ1トークンとする。目安であり、測ったものではない。

| 何を読むか | 量の目安 |
|---|---|
| D2 の1行（以前の形。理由だけ） | 約50トークン。130件で約6,600トークン。以前は件数の上限が無く、集約の出力（目安2万文字）の半分近くを使いえた |
| D2 の候補の1行（理由と行の文面） | 約65〜85トークン。全件を出すと130件で約1万トークンになるので、出力とレポートには上位12件（約1,000トークン）だけを出し、全件は `--section harness` で出す |
| 抜粋1回（`excerpt.py --context 3`） | 最大7項目×1,200文字。コードやログが多いと約2,000トークン、日本語が多いとそれ以上 |
| 要約表示に足した行 | 失敗やテストのあるターンだけ、1ターンあたり約20〜55トークン |

## 2. 判定ごとの評価

種類は、数える（事実）、形式（決まった形を読む）、意味（文脈で決まる）の3つ。

### 記録（`record.py`、`commands.py`）

| 処理 | 種類 | 評価 | 置き場所 | 今回 |
|---|---|---|---|---|
| 終了コードの読み取り（`Exit Code: N`） | 形式 | Kiro CLI 3.2.1〜3.3.0 で実測した形。読めなければ「記録の不足」にする | コード | 変更なし |
| 完了しなかった呼び出しの種類（拒否、取り消し、タイムアウト） | 形式 | Kiro の応答の決まった文言で分ける。分からないものは「記録の不足」 | コード | 変更なし |
| テスト実行の検出 | 形式 | 設定の `match` と照合する。文面だけの一致は、結果が取り込めなければ数えない | コード | 変更なし |
| 古い JUnit の判定 | 数える | 実行の前後でファイルの状態を比べる | コード | 変更なし |
| 秘密値を伏せる | 形式 | 完全ではないと明記している | コード | 変更なし |
| コマンドの見出し（失敗をまとめる単位） | 形式 | 単純な形だけを解釈し、それ以外は先頭3語。推測しない | コード | 変更なし |

### 集約（`aggregate.py`、`prompts.py`、`notes.py`、`ledger.py`）

| 処理 | 種類 | 評価 | 置き場所 | 今回 |
|---|---|---|---|---|
| テスト失敗の基準（前回の全テスト成功） | 数える | **誤り。** 一部のテストだけを流して通った実行も「全テスト成功」になり、その前に書き換えたテストファイルを見落として、Red を回帰と取り違えた | コード | そのテストが最後に通った実行を基準にした |
| テストのファイルの特定 | 形式 | **誤り。** `file` 属性と Python のモジュール名の形しか想定せず、対応できないと「変更なし」と断定した。vitest（classname がパス）、jest（classname が題）、go（パッケージ）で誤る。実機で確かめていたのは、`file` 属性を出すデモのランナーだけだった | コード | 実行の時点のファイルから候補を探す。見つからない、または同じ名前の候補の一部だけが変わったときは「特定できず」 |
| 実行前に止められた・中断された呼び出し | 形式 | 実測した形だけを拾い、合わないものは「判定できない」に分ける | コード | 変更なし |
| 書き直し候補（複数の発話にまたがる書き込み） | 数える＋意味 | やり直しか続きの作業かは、発話を読まないと決まらない。候補と発話の時刻を出し、エージェントが読む。どうせ読む会話なので、追加の費用は小さい | 分担 | 変更なし |
| 手直し候補（最後の書き込みの後に変わったファイル） | 数える＋意味 | **見出しが誤り。** 「人間の手直し候補」と書いていたが、エージェントがシェル（ヒアドキュメント、`sed`、整形コマンド）で書き換えても、書き込みの記録が残らないので同じになる。誰が変えたかは記録からは決まらない | 分担 | 見出しを「手直し候補」にし、書き込みの後のシェル実行にファイルの名前が出るものに、そのコマンドの1行目を添える。確かめるのは、案にするときだけ（抜粋1回、約2,000トークン） |
| 二重に記録された発話 | 形式 | ログの癖への対処。近さと包含で決める | コード | 変更なし |
| ノートの状態（既読） | 数える | 前回、一覧の表示を直した。見直し用の要約（`review.py`）は、発話の無いセッションをまだ未読に数えていた | コード | 未読の数を一覧とそろえた |
| 引用と「確認済み」の照合 | 数える | 実在だけを確かめ、解釈は判定しない | コード | 変更なし |
| 会話からの型の候補（2セッション以上） | 数える＋意味 | 数えるのはコード、同じ話題かどうか（名前を付けること）はエージェント。名前が揺れると数え漏れる | 分担 | 変更なし（5節） |
| 採用した案の追跡（前後の回数と判定） | 数える | 判定のしきい値（3日、半分）が「最初の値」と書かれておらず、設定で変えられない（AGENTS.md の決まりに合わない） | コード | 変更なし（5節） |

|---|---|---|---|---|

## 3. 調べたこと

### Kiro の公式ドキュメント

[Steering](https://kiro.dev/docs/steering/)（2026-10-21 更新）を読んだ。

- steering には、ほかのファイルを参照する記法がある。`#[[file:<相対パス>]]`、行の範囲を付けた `#[[file:<相対パス>:<始め>-<終わり>]]`、フォルダの `#[[folder:<相対パス>]]`。
- 相対パスの基準は、ワークスペースの steering ならワークスペースのルート、ユーザー共通の steering なら `~/.kiro/steering/`、AGENTS.md ならそのファイルのフォルダ。解決できない参照は、落とされずに印が残る。
- AGENTS.md は読み込みの条件を持たず、常に読み込まれる。サブディレクトリのものも見つけられる。

kiroku の D2 は、この記法を一度も確かめていなかった（`[` を含む語を除外していたため）。Kiro が実際に解決する参照なので、断定の対象にした。

### JUnit の形（配布物のソースで確認）

| ランナー | 確かめた版 | file 属性 | classname |
|---|---|---|---|
| vitest | 3.2.4 | 既定では出さない（`addFileAttribute` が偽） | vitest の root からのファイルのパス |
| jest-junit | 16.0.0 | 既定では出さない | `{classname} {title}`（describe の題とテストの題） |
| pytest | 8.3.3 | 既定の `junit_family=xunit2` では出さない（`xunit1` で出す） | ファイルのパスを `.` でつなぎ、`.py` を除いたもの（`tests.test_a`） |

kiroku のデモのランナー（`examples/demo/run_tests.py`）は `file` 属性を出す。classname からファイルを推定する処理は、実際のランナーで確かめられていなかった。go（go-junit-report の classname はパッケージ）は、ソースを読んでいない。

### 似た実装

| リポジトリ | 要点 | 採り入れる | 採り入れない |
|---|---|---|---|
| [lychee](https://github.com/lycheeverse/lychee) | リンクの記法（Markdown、HTML）から URL を取り出して確かめる。コードブロックは、`--include-verbatim` を付けないと見ない（README の要約からの読み取り） | 書き方からリンクと決まるものだけを確かめる考え | URL の確認（kiroku はネットワークを使わない） |
| [remark-validate-links](https://github.com/remarkjs/remark-validate-links) | Markdown のリンクと定義の、ローカルのファイルと見出しを確かめる。インラインのコードは対象に書かれていない | Markdown のリンクを断定の対象にする | 見出しの確認 |
| [driftlint](https://github.com/alifurkangokce/driftlint) | CLAUDE.md や AGENTS.md の、存在しないパスやコマンドを見つける。誤検出を、無視の注釈（`driftlint-ignore`）、テンプレートの指定、テンプレートらしいファイルの推定で抑える。どこからパスを拾うかは README に書かれていない | 確かめられないものを「壊れている」としない考え（前からの方針） | 誤検出を規則と注釈で抑える方式。規則を足すほど別の誤りが出ることは、kiroku の D2 で起きた |

コードとして書かれた語が参照かどうかを、文脈から決める仕組みは、これらには見つからなかった。driftlint が注釈や推定で抑えていることは、規則だけでは誤検出を消せないことの表れと読んだ。

## 5. 実装しなかったもの（次の候補）

- **話題の名前の揺れ**：同じ話題を別の名前で書くと、2セッション以上にならず、型の候補に上がらない。今は、集約が既存の名前を並べて使い回させているだけである。エージェントが名前をまとめる手順と、台帳の追跡（`topic:` の型）を保つための別名の仕組みが要る。追跡に関わるので、別に設計する。
- **追跡のしきい値**：採用した案の判定に使う3日と「半分」を、「最初の値」と明記し、設定で変えられるようにする。
- **steering の重さ**：`#[[file:…]]` で取り込むファイルを、常時読み込みの合計に入れるか。取り込まれ方を実機で確かめてから決める。
- **一歩先の案の確かめ方**：採用した一歩先の案が手がかりにした診断値（`D2:…` など）が、反映の後に消えたかを、スクリプトが追う。
- **D2 の候補の記憶**：例やプレースホルダと分かった候補が、毎回出続ける。エージェントの判断を記録して次から出さない仕組みは、driftlint の無視の注釈にあたる。候補の量が問題になってから考える。
- **JUnit の file 属性の基準**：`cd frontend && …` で実行したとき、相対パスを `frontend/` から読む。今は集約の末尾一致で吸収している。

## 6. 未確認のこと

- 実機の振り返りで、D2 の候補をエージェントが正しく読み分けるか。案の質が上がるか。
- vitest、jest-junit、pytest の形は、配布物のソースを読んで確かめた。実際に実行した出力ではない。go は読んでいない。
- Kiro が、コードの中に書かれた `#[[file:…]]` も解決するか。kiroku はコードの中のものを記法の例として数えない。
- （確認済み。#18）`references/harness-guide.md` の「現行の CLI のカスタムエージェントは、既定で steering・skills・AGENTS.md を継承する」と、公式の Steering ページの「カスタムエージェントには steering が自動では含まれない」の食い違い。Custom agents の設定リファレンスは既定で継承するとしており、Kiro CLI 3.4.0 V3 の実機でも、`resources` の無いエージェントに steering が読み込まれた。手引きのままでよい。skills と AGENTS.md の継承は未確認。

## 6.1 実機レビュー（#18）を受けた修正

- 要約表示が、テストの記録設定に一致したが完了しなかった呼び出し（終了コード -1。承認されなかった、止められた）を、テストの実行に数えていた。実行には数えず、件数を別の行に出す。
- D2 の断定のうち hook のコマンドとエージェント定義を、ルートからだけ解決する。別の場所の同じ名前のファイルに末尾が一致しても「有る」としていたため、実行すると失敗する hook を見落としていた。
- 見送ったもの：`#[[folder:…]]` がファイルを指すような種類の取り違え（見落としに留まり、書かれにくい）。「終了コードが0以外」の行にテストの失敗を載せないこと（テストの行に終了コードが出ている）。

## 7. 既存の導入先への影響

`--update` だけで済む。`config.json`、記録、ノート、台帳の形は変えていない。配布するファイルの追加・削除は無い。

更新すると、表示と分類が変わる。

- D2 の件数が減り、残ったものが「断定」と「候補」に分かれる。Kiro のファイル参照の参照切れが、新しく出ることがある。
- 一部のテスト失敗の分類が変わる。一部だけを流した実行を基準にしていた分は Red に、vitest で書き換えたテストの失敗は Red に、ファイルを決められないものは「特定できず」の回帰候補になる。過去の記録も今の規則で数え直すので、採用した案の `test:` の型の追跡の数も変わることがある。
- 手直し候補の見出しが変わる。
- 更新の前に作った書きかけのレポートは、検査で「スクリプトが書いた行」が合わないことがある。骨組みを作り直す（`--new-report`）。
