# 一歩先のハーネス改善案：調査と設計案

2026-11-18。調査と設計案。利用者が B（手順と診断値）で進めることを決め、同じ日に実装した（11節）。実装は自動テストだけで確かめていて、実機の振り返りでの案の質は未検証。

## 要点

- 今の kiroku の案は「観測した型1つに、案1つ」で作る。手順も検査も評価も、誤った案を出さないことに寄せてある。型を越えて「何が価値になるか」を考える段が無い。
- 調べた資料は、ハーネスの改善を「決まりを足すこと」ではなく、「どの仕組みが欠けているか」で考えている。仕組みとは、事前の案内（guides）と、事後の検査（sensors）である（Fowler、Anthropic、Factory）。
- そこで、案の単位を「事例」から「ハーネスの能力」に上げる。改善の段を「事例に対処する」→「種類ごと無くす」→「起きにくい環境にする」の3段とし、観測した事例より少なくとも1段上の案を出す。
- 具体的には、(1) 振り返りの手順に、8つの観点で考える段を足す。(2) ファイルだけで決まる「ハーネスの診断値」をスクリプトが出す。(3) 一歩先の案には、観点・価値・確かめ方を必須にする。件数は最大3件とし、重なる個別の案はまとめて置き換える。
- 根拠は「観測（型・診断値）」と「手引きに書いた原則（出典つき）」の組にする。観測の無い一般論は出さない。

## 1. 解きたいこと

利用者の指摘（2026-11-18）：

- 改善案が、観測できたことしか書いていない。期待を超えることがなく、事例を数えているだけになっている。
- 何が価値になるのか、というメタの視点が欠けている。

kiroku の評価の目的は、「同じ指摘・説明の繰り返しと、ハーネス整備の負担を減らす」ことである（[evaluation.md](evaluation.md) の「合意した評価範囲」）。この目的から見ると、良い案とは、1回分の手間ではなく、ある種類の手間をまるごと無くす案である。そのような案は、観測した事例の「一歩先」にある。

## 2. 今の作りで、一歩先の案が出ない理由

| 理由 | 根拠（今のファイル） |
|---|---|
| 案の単位が、観測した型と1対1になっている | `SKILL.md` 手順6：案の見出しは `### P<番号>.`、「対象の型」は集約に出ている名前。手順5：「根拠が足りなければ『様子見』にします。数を増やしません」 |
| 根拠の無い案を出さない決まりが、観測の外を考えること自体を止めている | `SKILL.md`「実行範囲」：「根拠のない案は出しません」。手順3：「自分の判断で型に格上げしません」 |
| ハーネスとの比較が型ごとで、ハーネス全体を見る段が無い | `SKILL.md` 手順4：「型ごとに、対応する既存の決まりを探します」 |
| 価値の物差しが回数しかない | 集約が出すのは、回数とセッション数だけ。誰のどんな手間が減るかを比べる値が無い |
| 学ぶ材料が失敗だけ | 記録するのは失敗・指摘・取り消し。試行錯誤の末に通った手順や、ハーネス自体の古び（読まれない決まり、存在しないパス）は見ていない |
| 評価が、抑制だけを測っている | [demo-cases.md](demo-cases.md) の D01〜D16 は、重複を足さない（D06）、一時的な指示を恒久にしない（D05）、直った問題を再提案しない（D13）など、出しすぎを防ぐケースばかりである。一歩先の案を出すことを求めるケースは1つも無い |

最後の理由が根にある。これまでの改善（Issue #7、#9、#12）は、誤った案を出さない方向に積み上げてきた。その結果、案の精度は上がったが、案の価値を上げる仕組みは無いままになっている。

## 4. 設計の芯：「一歩先」とは何か

### 改善の3段

| 段 | 何をするか | 例 |
|---|---|---|
| 1. 事例に対処する | 起きた事例について、決まりを足す・直す | 「テストは make test で」と2回言い直した → testing.md に1行足す |
| 2. 種類ごと無くす | 同じ種類の手間を、仕組みで無くす | 決まりを検査に上げる。手順を skill にする。複数の型に共通する、欠けた仕組みを足す |
| 3. 起きにくい環境にする | エージェントが自分で確かめられ、早く気づけ、ハーネスが古びない状態にする | 終了時にテストを実行して結果を返す hook。読み込まれない決まりの修正 |

今の kiroku の案は、ほぼすべてが段1にある。**一歩先の案とは、観測した事例より少なくとも1段上に立つ案**とする。価値は「減る負担の種類」で書く。

### 8つの観点

一歩先の案は、次のどれかの観点から作る。観点はレポートに書き、あとで観点ごとの効果を数えられるようにする。

| ID | 観点 | きっかけ（観測・診断値） | 案の形 | 出典 |
|---|---|---|---|---|
| V1 | まとめる（共通の原因） | 2つ以上の型が、同じ作業・同じファイル・同じ欠けた仕組みから来ている | 1つの仕組みで複数の型を無くす。重なる個別の案は、この案に置き換える | GEPA（失敗を要素に帰す）、Fowler（繰り返すなら制御を良くする）、claude-reflect（訂正を作業の skill に帰す） |
| V2 | 決まりを仕組みに上げる | 決まりがあるのに守られない。または、毎回機械的に判定できる決まり | hook、テスト、lint | Claude Code（強調しても守られないなら hook）、Fowler（決定的な検査）、手引きの「形を選ぶ」 |
| V3 | 確かめる手段を渡す | エージェントが完了を自分で確かめられない（完了の報告の後に指摘が来る、確認の手順が文章だけ） | 通ったか落ちたかを返すコマンド、終了時の hook、テスト | Anthropic（テストの道具で性能が上がった）、Claude Code（pass/fail を返すもの）、Fowler（案内だけの失敗） |
| V4 | 早く知らせる | 誤りに気づくのが遅い（CI や人のレビューで初めて分かる。失敗から次の成功まで実行が何回もかかる） | 保存時・実行前・終了時の検査に前倒しする | Fowler（keep quality left）、Factory（pre-commit なら5秒、CI なら10分） |
| V5 | 減らす・保つ | 読まれない、古い、重複する、矛盾する、膨らんだ決まり | 削る、直す、まとめる、条件付きにする | Anthropic（最小の高信号）、Claude Code（コードを読めば分かるものは書かない）、Fowler（古びを見る検査）、ACE、backpass（予算） |
| V6 | うまくいった道を残す | 試行錯誤の末に通った手順や、繰り返し行う手順 | 確かめ方つきの skill | self-learning-skills（golden path と昇格の条件）、Anthropic（init.sh、起動の手順） |
| V7 | 先回りする | 取り返しのつかない操作に近づいた（1回でも）。止められた呼び出し、権限による拒否 | 守りの仕組みを確かめる・足す | kiroku の記録。1回で案にしてよいのは、取り返しのつかない操作に関わるときだけ（kiroku の判断で、出典は無い） |
| V8 | 引き継ぐ（作業の状態） | セッションの始めに、今の作業の状態や続きを毎回説明し直している（繰り返しの説明のうち、決まりではなく状態にあたるもの） | 進み具合のファイル、セッション開始時に状態を渡す hook。決まり（steering）として書き足さない | Anthropic（進み具合のファイルと git の履歴を起動時に読む）、learn-harness-engineering（進み具合をディスクに残す） |

観点の漏れは、learn-harness-engineering の5つの部分で確かめる。指示は V2・V5、状態は V8、検証は V3・V4、範囲は V7、ライフサイクルは V6 にあたる。

## 5. 設計の選択肢

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| A. 手順だけ | `SKILL.md` に「一歩先の検討」の段と8つの観点を足す | 手間が小さい | 案の質が LLM 任せ。根拠を検査できない |
| **B. 手順と診断値（推奨）** | A に加えて、ファイルだけで決まる「ハーネスの診断値」をスクリプトが出し、一歩先の案の根拠に使わせる | 観測の無い場面でも、決定的な根拠から案を出せる。根拠を検査できる | 診断値の作り込みが要る |
| C. B と学びのループ | 採用した一歩先の案の効果を、観点ごとに数え、効いた観点を次回の優先に使う | どの種類の案がこの利用者に効くかを学べる | 採否の記録が貯まるまで意味が無い |

B を先に作り、C は採否の記録が貯まってから足すことを推奨する。

### B の中身

**(1) 振り返りの手順**

型をまとめた後（手順3）に、「一歩先の検討」の段を足す。

1. 観点ごとに、当てはまる型と診断値を挙げる。当てはまらない観点は飛ばす。
2. 当てはまる観点から、一歩先の案を作る（最大3件。最初の値）。
3. 個別の案と重なるときは、個別の案を一歩先の案にまとめる。件数を増やさず、減らす方向に働かせる。
4. 案ごとに、改善の段（1〜3）が観測より上がっていることを確かめる。上がらないなら、一歩先の案にしない。

**(2) ハーネスの診断値**（ファイルだけで決まり、同じ入力なら同じ結果になる）

| ID | 診断値 | 例（家計簿のデモ） |
|---|---|---|
| D1 | 読み込みの条件（`fileMatchPattern`）に当たるファイルが無い steering（driftlint の dead-glob にあたる） | `python-style.md` は `src/**/*.py` だけで読み込まれるが、コードは `kakeibo/` にある |

## 8. 変えない設計との関係

AGENTS.md の「変えない設計」は、すべて守る。

- 記録はスクリプトが行う。診断値も、ファイルから決定的に計算する。
- 発話を正規表現やキーワードで分類しない。D2 は決まりのファイル（ハーネス）を調べるもので、発話は対象にしない。
- 振り返りのエージェントはハーネスを変更しない。一歩先の案も、文章で提案するだけである。
- 数えられるもの（回数、診断値、引用、ID）は、スクリプトが確かめる。

変わるのは、`SKILL.md` の「根拠のない案は出しません」の意味である。根拠を「観測した型」から「観測（型・診断値）と、手引きの原則の組」に広げる。観測の無い一般論は、引き続き出さない。
