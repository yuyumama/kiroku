# 振り返りでの質問と、kiroku の不具合の欄：調査と設計案

2026-11-20。調査と設計案。同じ日に、利用者が10節の7点を決めた。質問の聞き方と答え方は、grilling（mattpocock/skills）を参考にする（4.3節）。実装は、9節の不具合の修正、質問（段1）、デバッグ欄（段2）の順に、別々の PR で行う。段1は同じ日に実装した（11節。自動テストのみ）。

## 要点

- ログだけでは決められないことがある。たとえば、ある仕組みを使っていないとき、知らないから使わないのか、要らないと決めたのかは、ログからは分からない。そこで、振り返りの途中で利用者に聞き、その答えを案の判断に使う。
- Kiro CLI と IDE には、選択肢を出して質問するツールが無い。Kiro 自身の Plan モードと、AWS の AI-DLC の Kiro 向け手順は、番号つきの選択肢を応答の文章で出し、利用者は「1=a」のように答える。kiroku もこの形にする。
- 質問は、型をまとめてハーネスと比べた後、案を作る前に1回だけ出し、ターンを終えて答えを待つ。上限は3問とする（最初の値。設定で変えられ、0 にすると聞かない）。
- 質問は grilling の形にならい、1回分をまとめて番号を振って出す。各質問には、見立て（記録から推測した答え）と、その手がかりを書き、見立てのとおりなら「はい」だけで答えられるようにする。選択肢ごとに、それを選んだらどうするかも書く。選択肢の最後には、必ず「わからない」と「その他（自由に書く）」を置く。
- 回答は、レポートの新しい節に、利用者の発話の引用つきで残す。検査は、その引用が振り返り自身のセッションログにあることを確かめる。エージェントが代わりに答えた回答は、検査を通らない。回答は観測の代わりにしない。案の手がかりは、今までどおり型か診断値とする。
- デバッグ欄は、`/kiroku-retro --debug` で作る。Kiro は、skill の名前の後ろに書いた文字をエージェントに渡す（公式資料。3.2.1 の実機でも確認済み）。環境と、振り返り中の kiroku 自身の失敗は、スクリプトが書く。不具合の推定は、エージェントが「現象、期待、根拠、再現、確度」の形で書く。
- 調べる途中で、既存の不具合を1つ見つけた。骨組みを作った後に `record-errors.log` が増えると、検査が不一致を出す。この機能より先に直した（9節）。

## 1. 解きたいこと

利用者の指摘（2026-11-20）は、次の2つである。

1. ログを取るだけでは限界がある。利用者は知らないものを使わないので、使っていないことが妥当かどうかを、ログからは判断できない。振り返りのときにエージェントから質問し、その答えを判断の材料にしたい。利用者は高度なプログラマーではない前提なので、質問にはエージェントの見立てを入れる。答えは選択式と自由記述の両方で受け、「わからない」という答えも想定する。
2. kiroku 自体の不具合と推定されるものを書く欄を、デバッグのためにレポートに作りたい。`/kiroku-retro` の実行時のオプションで出したい。

今の手順にも、ログでは決められず、利用者に聞くしかない場面がある。

| 場面 | 今の扱い（`SKILL.md`） | ログでは分からないこと |
|---|---|---|
| 仕組みが無い（kiroku 以外の hook、pre-commit、CI、lint、skill） | 「設定ファイルが無いこと自体は欠陥ではありません。必要性を確認できなければ「根拠不足」とします。」 | 知らないのか、要らないと決めたのか |
| 意図して起こした失敗 | 「利用者が検証のために意図して起こした失敗は、型にしません。」 | 発話に書かれていなければ、意図したかどうか |
| いつもの方針か、その時だけか | 迷うものは、ノートの「確認事項」（`unsure`）にする | 利用者の意図 |
| 実行前に止められた呼び出しが繰り返す | 「繰り返し出ているときは、その下の欄で利用者に確認を求めます。」 | 止まってよかったのか。今はレポートに書くだけで、答えを受け取る手順が無い |
| 手直し候補 | 「手直し候補は、誰が変更したかを証明しません。」 | 人が直したのか |

## 2. 今の作りとの関係（コードで確かめたこと）

- 振り返りは、手順1から7までを1回のターンで続けて行う。利用者とやり取りするのは、最後の採否（手順7）だけである。そこでは「記録するのは、利用者がこの会話で明言した判断だけです」としている。
- 振り返り自身のセッションログは、すでに読んでいる。表の「確認済み」を照合するためで、`reads.py` の `opened()` が `prompts.running_session_log()` でログを探す（`sessions_dir` に無ければ、Kiro の既定の置き場も探す）。回答の照合にも使える。
- 引用の照合（`citations.py`）は、session と index で指した発話に、引用が実在するかを確かめる。回答の引用にも同じ考えが使える。ただし今の照合は `sessions_dir` だけを探すので、振り返り自身のログには `running_session_log()` を使う。
- `/kiroku-retro` より後の発話と記録は、振り返りの会話として集約から除く（`prompts.retro_start()`）。回答の発話は、記録フックが `prompt` として残すが、集約には入らない。
- 骨組みは版4である。版を上げても、以前の版のレポートは作ったときの規則で検査する仕組みがある（`aggregate.as_version()`、`skeleton.build(version=…)`）。
- 「スクリプトが書いた行を直す必要があると考えたときは、行は直さず、「記録の不足、確認事項」の欄にそう書きます」（手順6）。kiroku の不具合の推定は、今はこの欄に、利用者向けの補足と混ざって書かれる。
- 「通常の成功したシェル実行と kiroku 自身のコマンドは記録しません」（README）。そのため、振り返り中に kiroku のスクリプトが失敗しても、どこにも残らない。
- 設定の既定値はコードに持つ（`record.DEFAULT_CONFIG`）。上限は `one_step_max` と同じ形で足せる（`COUNT_KEYS` で「0 にすると〜しない」を表示する）。
- 手順1には「期間の指定がなければ直近7日を対象にします」とあり、利用者が期間を指定できる前提がある。`/kiroku-retro` の後ろに書いた文字も、エージェントには同じように届く（3節）。

## 4. 設計案：振り返りの中で利用者に確かめる

### 4.1 どこで聞くか

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| **A. 案を作る前に聞く（推奨）** | 手順4（ハーネスと比べる）の後に質問を出し、ターンを終える。答えを受けて、案を作る手順から続ける | 答えを、その回の案に使える | 人がいない実行では、質問のところでターンが終わり、レポートができない |
| B. レポートの後に聞いて、書き直す | 見立てのまま書いたレポートを検査してから聞く。答えで書き直し、もう一度検査する | 答えが無くても、レポートが残る | 2回書くことになる。答えの前に、見立てだけで書いた案が一度できあがる |
| C. 次回に回す | 質問をレポートに書き、次の振り返りの始めに答えを聞く | 今の流れを変えない | 答えが使われるのが、次の振り返りまで遅れる |

A を推奨し、利用者が A に決めた。人がいない実行（headless。`kiro-cli chat --no-interactive` のように、対話をしないで呼び出すもの）は、利用者が基本的に使わない（README も「週次を想定して手動で専用エージェントを呼びます」）。使うときは、上限を0にすれば聞かずに進む。

手順は次のように変わる（番号は今の手順）。

1〜4. 今までどおり（集約、セッションを読む、型にまとめる、ハーネスと比べる）。
新しい手順. 利用者に確かめる。質問を出したら、ターンを終える。答えを受け取ったら、手順1〜4をやり直さずに、次の手順から続ける。
5〜7. 今までどおり（案を作る、レポートを書く、採否を聞く）。答えはレポートの新しい節に書く。

### 4.2 何を聞くか

次の3つをすべて満たすものだけを聞く。

1. **答えで、レポートが変わる。** 案を出すか出さないか、案の形、型にするかどうか、様子見にするかが変わるもの（spec-kit の「答えで実装や検証が大きく変わる質問だけ」）。
2. **ログ、ファイル、抜粋で確かめられない。** ファイルやログで分かることは、エージェントが調べる（grilling の「事実を調べるのはエージェントの仕事」）。
3. **手がかりがある。** 集約の型、診断値、記録の不足、ノートの確認事項（`unsure`）、比較表の「なし」のどれかを、バッククォートで書く。手がかりの無い一般的な質問（「困っていることはありますか」など）はしない。

質問のきっかけは、次のようなものになる。

| きっかけ | 聞くこと（例） |
|---|---|
| 比較表や `D5` で仕組みが無く、その仕組みで減らせそうな型がある | その仕組みを知っているか。使わないと決めているか |
| 失敗の型（`tool:…`、`test:…`）に、意図した失敗かもしれないものがある | 確かめるために、わざと起こしたか |
| ノートの確認事項（`unsure`）。「今回は」などがあり、方針かその時だけかが分からない話題 | いつもの方針か、その時だけか |
| 実行前に止められた呼び出しが繰り返す | 止まってよかったか（守りが、意図どおりに働いているか） |
| 手直し候補で、シェルの手がかりが無い | 人が直したか |

上限より多いときは、「答えで変わる案の大きさ」と「見立ての不確かさ」が大きいものから選ぶ（spec-kit の「影響×不確かさ」）。選ばなかったものは、今までどおり「補足と、利用者に確かめたいこと」の欄に書く。

上限は、設定の `question_max`（既定3。最初の値で、根拠は薄い。0 にすると聞かない）とする。比べた値は、spec-kit が1回の対話で5問（1問ずつ）、AI-DLC が1回の発話に4問ほど、Claude の `AskUserQuestion` が1回に1〜4問である。長い振り返りの終わりに、プログラマーではない利用者に聞くので、少ない側の3にした。聞くのは1回だけとする。答えが読み取れないときに限り、その質問だけを1回聞き直してよい（spec-kit と同じ）。

### 4.3 質問の形（grilling にならう）

利用者が、grilling（mattpocock/skills）の聞き方と答え方を参考にすることを決めた。grilling は、答えを待たずに出せる質問を1回分にまとめ、番号を振り、各質問に推奨の答えを添えて出す。kiroku はこれを、1回だけ、3問までで行う。

利用者に見せる文面の例（家計簿のデモを想定した例で、実際に kiroku が出したものではない）：

```text
案を作る前に、2つ教えてください。答えによって、出す案が変わります。
見立ては、記録からの推測です。すべて見立てのとおりなら「はい」とだけ答えてください。
違う質問だけ「Q2=c」のように選び直すか、自由に書いてください。答えたくない質問は、飛ばして構いません。

Q1. 作業の終わりに、テストを自動で実行する仕組みを使いますか
書き換えのあったターン 12 回のうち、そのあとテストを実行したのは 3 回でした（`D5`）。
kiroku 以外の hook（決まった操作のときに自動で動く設定）は、まだありません。
  a. 使ってみたい → 作業の終わりにテストを実行する hook の案を出します
  b. 知っていて、使わないことにしている → この案は出しません。理由があれば書いてください
  c. わからない → 案にはせず、「様子見」に書いて、次回もう一度見ます
  d. その他（自由に書いてください）
見立て：a。この仕組みを知らなかったのかもしれない、と見ています。

---

Q2. 11月18日にテストを失敗させたのは、確かめるためにわざと行ったものですか
集計を壊してテストが失敗し、同じ日に元に戻して通しています（`test:…`）。
わざとかどうかは、会話には書かれていません。
  a. わざと（確かめるため） → 問題として扱いません
  b. わざとではない → 失敗の原因を調べて、案にします
  c. わからない・覚えていない → 問題としては扱わず、「様子見」に書きます
  d. その他（自由に書いてください）
見立て：a。すぐに元に戻しているので、確かめるための失敗だと見ています。
```

書き方の決まり：

- **1回にまとめる**：答えを待たずに出せる質問を、番号を振って1回にまとめて出す（grilling の「回」）。同じ回のほかの質問の答えで中身が変わる質問は、出さない。grilling では後の回に回すが、kiroku は1回だけなので、その回には聞かない。
- **題と本文**：題は1文で、何を決めたいかを書く。本文には、何を観測したか（手がかり）と、なぜ聞くのかを書く。数は、集約の値をそのまま使う。
- **見立て**：すべての質問に、いちばんありそうだと考える選択肢と、その理由を1文で書く（grilling の推奨の答え）。見立ては、選択肢の1つにする。「はい」で受け入れられるようにするためである。推測だと分かる書き方にする。
- **選択肢**：選んだらどうするかを「→」で書く。答えで何が変わるかが、利用者に見えるようにするためである。
- **最後の2つ**：必ず「わからない」と「その他（自由に書いてください）」にする。「わからない」には、選んだときの扱いを書く。
- **言葉**：専門用語は、その場で短く言い換える。言い換えは、`references/harness-guide.md` に公式資料のリンクつきで用意し、記憶で説明しない。
- **答え方**：見立てのとおりなら「はい」だけでよい。違う質問だけ「Q2=c」のように選び直す（Kiro の Plan モードの「1=a」と同じ形）。自由に書いても、一部だけ答えても、飛ばしてもよい。CLI では `/reply` でも答えられる（未検証）。
- **待つ**：質問を出したら、ターンを終える。答えを待たずに先へ進まない。
- **記号**：grilling の ❓ と ➡️ は使わず、「Q1.」と「見立て：」と書く。kiroku の文面に合わせるためである。

最初の設計案では、推奨を「どうするか」の質問だけに付け、「知っているか」「意図したか」の質問には付けないとしていた。答えを誘導しないためである。grilling にならい、すべての質問に見立てを付けることにした。見立てを示すことは、利用者の最初の求めでもある。その代わり、見立ての理由と手がかりを本文に書き、「はい」で受け入れた答えは、レポートに「見立てのとおり」と分かる形で残す。誘導がどの程度起きるかは、デモで確かめる（10節）。

### 4.4 答えの扱い

| 答え | 扱い |
|---|---|
| 「はい」 | 見立ての選択肢を選んだものとする。レポートには「見立てのとおり」と書く |
| 選択肢 | その選択肢の「→」のとおりにする |
| わからない | 見立ては「未確認」のままにする。質問に書いた「わからない」の扱い（多くは様子見）にする。見立てに同意したとはみなさない |
| その他（自由記述） | エージェントが読んで、どの扱いに近いかを決め、レポートにそう書く。スクリプトは、語で答えを分けない |
| 答えなし（飛ばした） | 見立てのまま進み、レポートに「未回答」と書く。採否と同じく、答えの無いものを推測で埋めない |
| 「もういい」「後で」 | 残りの質問を「未回答」にして進む |

答えは、「利用者の回答」という別の種類の根拠にする。観測の代わりにはしない。案の手がかりには、今までどおり型か診断値が要る。答えが決めるのは、案を出すかどうか、案の形、型にするかどうかである。答えだけから、新しい型や案を作らない。自由記述に新しい話（「実は毎回〜が面倒」）が書かれていたら、様子見に書き、次の振り返りでログと照らす。

### 4.5 レポートへの残し方と検査

骨組みを版5にし、冒頭の要約の次に「利用者に確かめたこと」の節を置く。案は答えを前提にするので、案より前に置く。

```markdown
## 利用者に確かめたこと

### Q1. テストを自動で実行する仕組みを使ってみるか

- 手がかり：`D5`
- 見立て：a（使ってみたい）。書き換えの後にテストを実行しないターンが多い。仕組みを知らなかった可能性がある
- 回答：a（見立てのとおり）
- 引用（回答）：index 41「はい」
- 反映：P1 を出した

### Q2. テストの失敗は、確かめるためにわざと起こしたものか

- 手がかり：`test:…`
- 見立て：a（わざと）。同じ日に元に戻して通している。意図は会話に無い
- 回答：未回答
- 反映：見立てのまま、型にせず、様子見に書いた
```

引用（回答）の session は、骨組みに書かれた振り返り自身のセッションなので、書かなくてよい。

検査（スクリプト）が確かめること：

- 引用（回答）が、振り返り自身のセッションの、`/kiroku-retro` より後の利用者の発話にある。エージェントが代わりに書いた答えは、ここで通らない（AI-DLC の「エージェントが自分で選んだ答えは無効」）。
- 回答が「はい」、選択肢、わからない、その他のときは、引用（回答）がある。「未回答」には引用は要らない。
- 質問の数が `question_max` 以内で、番号（Q1 など）が重複していない。
- 手がかりが、集約の型か診断値、または骨組みのスクリプトが書いた部分にある。
- 「反映」に書いた案の番号が、レポートにある。
- ログを読めないとき（IDE など）は、照合できないと表示し、不一致にはしない（「確認済み」の照合と同じ扱い）。

答えの解釈が正しいか、見立ての中身が正しいかは、判定しない。

### 4.6 次回以降

- 集約に「前回までの回答」を出す。スクリプトが、レポートの Q の見出し、回答、日付を読み出す（台帳が案を読むのと同じ形）。
- 新しい観測が無ければ、同じことを聞き直さない。前回の答えを使うときは、「前回の回答（<レポート名>#Q1、<日付>）による」と書く。
- 未回答の質問は、今回も当てはまるなら、もう一度聞いてよい（前回の未判断の案と同じ考え）。
- 答えが古くなったときに聞き直す日数は、根拠が無いので決めない。日付を見せ、エージェントが判断する。

### 4.7 聞けないとき

- **人がいない実行**：途中の入力はできない（Headless mode）。上限を0にすれば、聞かずに進む。これを文書に書く。
- **IDE**：質問は普通のチャットの文章なので、動く見込みである。回答の照合は、実行中のセッションのログを IDE でどこから読めるかが未検証なので、照合できないと表示する。

### 4.8 本当に選ぶ画面について（MCP の elicitation。後で検討）

Kiro は、MCP のツールが途中でフォームを出すことに対応している（CLI 2.34 以降のローカル V3 セッション）。kiroku が標準ライブラリだけで小さな MCP サーバーを書き、質問をドロップダウンと文字入力のフォームで出せば、本当に選ぶ画面になる。答えはサーバー（スクリプト）が受け取るので、記録も決定的になる。

一方で、次のものが増える。MCP サーバーを配ること。専用エージェントの定義に MCP を足すこと。MCP のツールの承認。IDE 1.x と headless での扱い（資料に無い）。エージェントが答えを受け取るかどうか（資料に無い）。そこで、実機で確かめてから、別の段階で検討する。A 案の答えの記録と照合は、どちらの出し方でも変えずに使える形にしておく。

## 5. 設計案：kiroku の不具合の欄（`--debug`）

### 5.1 渡し方

- `/kiroku-retro --debug` とする。Kiro は、skill の名前の後ろの文字を、エージェントに文脈として渡す（公式資料。3.2.1 の実機で確認済み）。本文の `$ARGUMENTS` の置き換えは CLI だけなので、使わない。
- `SKILL.md` に「`/kiroku-retro` の後ろに `--debug` があれば、骨組みを `aggregate.py --new-report --debug` で作る」と書く。期間の指定（「14日」など）と一緒に書ける。
- 専用エージェントのシェルの許可は `aggregate.py *` なので、権限は変えずに済む。
- 指定が無いときは、今までどおりとする。kiroku の不具合の推定は、「記録の不足、確認事項」の補足に書く。

### 5.2 欄の中身

レポートの末尾、検証値（`kiroku-facts`）の前に「kiroku の不具合の候補（デバッグ）」の節を置く。指定したときだけ作る。

スクリプトが書くもの（骨組みを作った時点の値。検査のときに、同じ文面を作り直せるもの）：

| 項目 | 中身 | 出どころ |
|---|---|---|
| 環境 | OS、Python の版、骨組みの版、kiroku のスクリプトの指紋（`scripts/*.py` の SHA-256 の先頭12桁） | 骨組みを作ったときに state に控え、検査は控えから作る（`report_heads` と同じやり方） |
| Kiro の版 | ログか `session.json` から取れれば書く。取れなければ「未確認」 | 実機で形を確かめてから決める（未検証） |
| この振り返りで失敗した kiroku のスクリプトの呼び出し | 振り返り自身のログにある kiroku のスクリプトの呼び出しのうち、終了コードが0以外のもの、Traceback を含むもの、権限の規則で拒否されたもの。コマンドと index を書く | 骨組みを作る呼び出しより前の項目だけを見る |
| 記録フックのエラー | 骨組みを作った時刻までの行の数と、最後の数行（`mask` を通す） | `record-errors.log`。行の先頭の時刻で区切る（9節の不具合を避けるため） |

kiroku には版の番号が無い。インストーラーは `scripts/*.py` を書き換えずに写す（Python の起動名を置き換えるのは `.json` と `.md` だけ）。そのため、スクリプトの指紋で kiroku の版が分かり、インストーラーを変えずに済む。

エージェントが書くもの（欄）：

```markdown
### B1. <不具合と推定されるものを1文で>

- 現象：<実際に起きたこと>
- 期待：<こうなるはずだったこと>
- 根拠：引用（出力）：index <番号>「<スクリプトの出力の一節>」、引用（ファイル）：`<kiroku のファイル>`「<一節>」
- 再現の手がかり：<実行したコマンドと条件>
- 確度：<確認済み（出力や抜粋で確かめた）／推定>
- 影響：<記録が欠ける、数がずれる、検査が誤って不一致になる、手順どおりに動かない、など>
```

書くもの：

- kiroku のスクリプトの異常終了や、想定外の出力。
- 集約の数や分類が、抜粋で確かめた事実と食い違うもの。Issue #18 の「実行されなかったテストを、実行に数えた」がその例である。
- 検査の誤り。スクリプトが書いた行を変えていないのに不一致になる、など（9節がその例）。
- `SKILL.md` の手順どおりにしたのに、権限で拒否された。手順と出力が食い違う。手順の文面が、2通りに読める。

書かないもの：

- 利用者のハーネスの問題。これは改善案に書く。
- Kiro 自体の不具合と見られるもの。「Kiro 側の可能性」と書き、Kiro の `/issue` を案内する。
- 直すためのコード。差分やパッチを作らない、という今の範囲のままとする。

### 5.3 検査

- 骨組みに `--debug` の印を残す。検査は、同じ印で骨組みを作り直し、スクリプトが書いた行を照合する。
- 欄が埋まっているか（無ければ「なし」）、B の番号が重複していないか、確度が「確認済み」なら引用が1つ以上あるかを確かめる。
- 引用（出力）は、振り返り自身のログのツール結果と照合する（新しい種類の引用）。引用（ファイル）は、今の仕組みで照合する。
- 書いた内容が本当に不具合かは、判定しない。

### 5.4 共有するときの注意

節の冒頭に、次を書く。「この節は、kiroku の開発者に渡すためのものです。渡す前に、パス、コマンド、引用に、見せたくないものが無いかを確かめてください。」Kiro の `/logdump` の注意と同じ考えである。秘密値は `mask` を通すが、完全ではない（README のとおり）。

## 6. 変えない設計との関係

AGENTS.md の「変えない設計」は、すべて守る。

- 記録はスクリプトが行い、LLM は振り返りだけで使う。質問も、振り返りの中だけで行う。フックは変えない。
- 記録の時点では分類しない。変えない。
- 発話を正規表現やキーワードで分類しない。答えの意味はエージェントが読む。スクリプトは引用の実在だけを確かめ、「a」「わからない」などの語で答えを分けない。`--debug` は、エージェントがスクリプトに明示して渡す。
- 会話の本文は保存しない。答えは、根拠に要る短い一節だけをレポートに引用する（ノートとレポートの引用と同じ）。
- 振り返りのエージェントはハーネスを変えない。答えが「使ってみたい」でも、反映は人が行う。
- エージェントの申告をそのまま使わない。答えの引用は、振り返り自身のログと照合する。デバッグ欄の引用も照合する。
- 生のデータを git に載せない。レポートは `data/` の下のままである。

## 7. 既存の導入先への影響

見込みは「`--update` だけで済む」。

- 骨組みを版5にする。版4までのレポートは、作ったときの版の規則で検査する（今の `as_version` の仕組み）。
- `question_max` の既定値は、コードに持つ。`config.json` の書き換えは要らない（更新のときに、既定値で動く項目として表示される）。
- 専用エージェントの定義（権限）は変えない。答えはレポート（`reports/**`）に書く。
- フックと、記録の形式は変えない。
- 振る舞いが変わる：更新した後の振り返りは、途中で質問をしてターンを終える（往復が1回増える）。望まない導入先は、`question_max` を0にする。手作業は要らないので、インストーラーの注意の表示は足さず、README の「導入と更新」に書く。
- 更新の前から開いている振り返りのセッション：古い手順のまま版5の骨組みを作ると、質問の節は「なし」で埋まり、検査は通る見込みである。`--debug` は、古い手順では読まれない。
- IDE：質問は文章なので動く見込み。答えの照合は未検証。

## 8. 評価のしかた

[demo-cases.md](demo-cases.md) に、次のケースを足す。

| ID | 与える入力・条件 | 期待する結果 | 反例（してはいけない） |
|---|---|---|---|
| D23 | 書き込みの後にテストを実行しないターンが多く（`D5`）、kiroku 以外の hook が無い | 仕組みを知っているかを聞く。「知らなかった、使いたい」なら終了時の hook の案、「使わないと決めている」なら出さない、「わからない」なら様子見 | ファイルで分かること（テストのコマンドなど）を聞く |
| D24 | 実装を壊してテストを失敗させ、発話には意図が書かれていない | 意図した失敗かを聞く。「わざと」なら型にしない | 聞かずに、意図したと決める |
| D25 | 利用者が、すべての質問を飛ばす | 未回答として進み、レポートができる | エージェントが答えを埋める（検査が、ログに無い答えを通さないこと） |
| D26 | 前回の答えがある状態で、もう一度振り返る | 新しい観測が無ければ、同じ質問をしない。前回の答えを、日付つきで使う | 同じ質問を繰り返す |
| D27 | `--debug` で振り返り、途中で kiroku のスクリプトが失敗する（9節の不具合を再現する、など） | スクリプトが失敗の一覧を書き、エージェントが現象、期待、根拠、確度を書く | 利用者のハーネスの問題を、デバッグ欄に書く |

自動テストで確かめること：版5の骨組み、版4までのレポートが今までどおり通ること、答えの引用の照合（実在する答え、作った答え、ログが読めない場合）、質問の上限と0、デバッグ欄が指定したときだけできること、kiroku のスクリプトの失敗の一覧、記録フックのエラーの数が骨組みの時刻で区切られること。

## 9. 調べる途中で見つけた不具合

- **現象**：骨組みを作った後に `record-errors.log` が1行増えると、`--check-report` が「スクリプトが書いた行が、消えているか、書き換えられています：- 記録フックのエラー：1 行（…）。」を出し、終了コード1になる。エージェントは、その行を変えていない。
- **原因（コードを読んで確かめた）**：集約は、`record-errors.log` の行をすべて数える（`aggregate.py` の `record_errors`）。期間でも、骨組みを作った時刻でも区切らない。検査は、検査をしたときの数で骨組みを作り直して照合する。
- **起こりうる場面**：振り返りの最中に、記録フックがエラーを出した場合（振り返り自身のシェル実行でも、記録フックは動く）。後でレポートを検査し直す場合。
- **確かめ方**：一時ディレクトリで、骨組みを作る → 欄を埋める → 検査する（終了コード0）→ `record-errors.log` に1行足す → 検査する（終了コード1）、を自動で再現した。実機では見ていない。
- **直したこと（2026-11-20。自動テストのみ）**：骨組みを作ったときの行数を `data/state.json` に控え、検査はその数で骨組みを作り直す。控えの無い以前のレポートは、作った時刻（`report_made`）までの行だけを数える（行の先頭に時刻がある。時刻の無い行は、直前の行と同じ件とする）。再現するテストを2つ足し、直す前のコードで落ちることを確かめた。この機能とは別の変更（先に出す PR）で直した。既存の導入先への影響は「`--update` だけで済む」。

## 11. 実装したもの（段1：質問。2026-11-20、自動テストのみ）

| 設計 | 実装 |
|---|---|
| 手順 | `SKILL.md` に手順5「利用者に確かめる」を足した。聞くもの、聞き方（grilling にならう）、答えの扱い。以降の手順の番号を1つずつ下げた |

| 設定 | `question_max`（既定3。最初の値。0 で聞かない） |
| 言い換え | `references/harness-guide.md` に「利用者に聞くときの言い換え」を足した |

設計から変えたところ、決めたところ：

- 引用（回答）には session を書かない。骨組みに書かれた、振り返り自身のセッションで照合する。index は書いてもよく、書けば先にそこを見る（エージェントは、自分のセッションの index を知らないことが多い）。
- 答えを探すのは、振り返り自身のログの、最初の集約（`aggregate.py`）より後の利用者の発話。`/kiroku-retro` の発話は答えに数えない。
- 手がかりに書けるのは、集約に出た型、診断値、トピック、テスト失敗と、集約の出力に `…` で出たもの（コマンド、パスなど）。
- 上限が0でも、節は作る。上限は欄の説明（【ここに書く…】の中）に書き、スクリプトが書いた行には入れない。設定を後で変えても、検査で行が合わなくならないようにするため。
- 版を上げると、以前の版の扱いが変わってしまう書き方（`form >= skeleton.VERSION`）を、版の番号で固定した。
