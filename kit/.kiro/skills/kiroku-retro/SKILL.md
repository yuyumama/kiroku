# kiroku の振り返り

開発中に記録された信号を読み、ハーネスの改善案を文章でまとめます。
ハーネスとは、`.kiro/steering`、`.kiro/hooks`、`.kiro/skills`、`.kiro/agents`、関連するスクリプトのことです。

## 守ること

- 書き込むのは `.kiro/kiroku/data/reports/` 配下のレポート1個だけです。ハーネスのファイルは変更しません。
- シェルで実行するのは `aggregate.py` と `excerpt.py` だけです。1回に1コマンドだけ実行し、`;` や `&&` でほかのコマンド（`date`、`ls` など）とつなげません。つなげると全体が拒否されます。
- 学びがなければ、レポートに「なし」と書いて終わります。無理に改善案を作りません。
- 記録に無いことを推測で補いません。根拠は回数とセッション数で示します。
- レポートにコードや出力をそのまま貼りません。必要なら1〜2行の要約にします。

## 手順

### 1. 集約する

`/kiroku-retro` の後ろに期間の指定があればそれを使い、無ければ直近14日にします。

```bash
python3 .kiro/kiroku/aggregate.py --since 14d
```

出力の先頭にある「レポートの保存先」を、手順6の保存先として使います。
イベント数が0なら、その旨だけをレポートに書いて終わります。

### 2. 繰り返しを探す

次の順に見ます。1回しか起きていないものは、原則として型とみなしません。

1. **回帰**：通っていたテストを壊した記録。同じテストや同じ領域で繰り返していないか。
2. **ツール失敗**：同じコマンドが何度も失敗していないか。環境の前提、手順の抜け、権限が原因ではないか。
3. **人による取り消し**：人が実行を止めた操作。エージェントが避けるべき操作の手がかりです。
   **権限の規則による拒否**は別の信号です。エージェントが許可されていない操作を繰り返していないかを見ます。
4. **人間の手直し候補**：エージェントが書いた後に人が直したファイル。同じ種類のファイルに偏っていないか。
5. **その他のテスト失敗**：分類できなかった失敗。記録の設定に不足がないか。

「正常な Red」は TDD の通常の流れなので、問題として扱いません。

### 3. 必要な箇所だけ、セッションログで確かめる

原因が集約結果だけでは分からない型について、該当箇所の前後を読みます。
多くても5箇所までにします。

```bash
python3 .kiro/kiroku/excerpt.py --session <session_id> --command "<コマンドの一部>"
```

```bash
python3 .kiro/kiroku/excerpt.py --session <session_id> --around <集約結果の時刻>
```

ログが見つからない場合は、集約結果だけで判断し、レポートにその旨を書きます。

### 4. 既存のハーネスと照らす

`.kiro/steering`、`.kiro/hooks`、`.kiro/skills`、`.kiro/agents` を読み、型ごとに次を確かめます。

- 既に同じ内容の決まりがあるか。あるのに守られていないなら、足すのではなく直す案にします。
- 既存の決まりと矛盾しないか。

### 5. 改善案を作る

型ごとに、最も安く確実な形を1つ選びます。上にあるものほど優先します。

1. **仕組みで防ぐ**：フック、スクリプト、テスト、lint の規則、権限の設定。
2. **手順にする**：skill の追加や修正。
3. **決まりを書く**：steering への追記や修正。

決まりを書く案は、仕組みで防げない理由を1文で添えます。
効果が見込めない型には、案を出さず「様子見」とします。

### 6. レポートを書く

集約結果の「レポートの保存先」のパスに、次の形で書きます。

```markdown
# 振り返り YYYY-MM-DD

- 対象期間：
- イベント数、セッション数：
- 確認したセッションログ：N 箇所

## 繰り返し出ている型

### 1. <型を1文で>

- 根拠：<回数、セッション数、代表的な例の要約>
- 原因の見立て：<1〜2文。推測なら推測と書く>

## ハーネスへの改善案

### 1. <案を1文で>（型1に対応）

- 形：<フック／スクリプト／skill／steering など>
- 変更するファイル：<パス。新規なら新規と書く>
- 内容：<何をどう変えるか。3文以内>
- 既存との関係：<重複や矛盾の有無>
- 不要になる条件：<この案を外してよい条件>

## 様子見

- <1回だけの事象や、根拠が足りないもの>

## 記録の不足

- <分類できなかった理由や、設定の不足>
```

型も改善案も無ければ、2つの見出しの下に「なし」とだけ書きます。

### 7. 報告する

レポートのパスと、型と改善案の数を、3行以内で伝えて終わります。
