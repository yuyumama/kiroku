# ハーネスの改善案を作るときの手引き

Kiro の公式ドキュメント（kiro.dev/docs の Steering、Skills、Hooks、Custom agents）に書かれている使い分けと推奨を、改善案の判断に使える形でまとめたものです。

## 既存の決まりが効かなかった理由を切り分ける

同じ趣旨の決まりが既にあるのに繰り返されている場合は、足す前に次を確かめます。

| 理由 | 確かめること | 案の方向 |
|---|---|---|
| 読み込まれていない | steering の `inclusion` が `manual` や `fileMatch` で、その場面では対象外だった | 読み込みの条件を直す |
| カスタムエージェントに渡っていない | 現行CLIのカスタムエージェントは既定でsteering・skills・AGENTS.mdを継承する。`chat.disableInheritingDefaultResources`、読み込み条件、明示した`resources`を確認し、渡っていない根拠があるか | 継承や条件の不一致を直す。`resources`の未記載だけでは追加を提案しない |
| skill が呼ばれていない | 説明文（`description`）が曖昧で、依頼の言い方と合わない | 説明文を「何をするか」と「いつ使うか」が分かる形に直す |
| 上書きされている | プロジェクト内とユーザー共通で矛盾している。矛盾したときはプロジェクト内が優先される | 片方に寄せる |
| 文面が曖昧 | 何をすればよいかが具体的でない、理由や例が無い | 文面を具体的にし、理由と例を足す |
| 埋もれている | 常時読み込みの steering が長く、多くの話題が混ざっている | 分割し、条件付きの読み込みに移す |
| 実行できない | 決まりが求める操作を、権限や環境が許していない | 決まりか権限のどちらかを直す |
| 文章では守れない | 毎回必ず行う機械的な確認を、文章で頼んでいる | hook やスクリプトに移す |

## 形を選ぶ

上にあるものほど確実です。型の性質に合う、いちばん上の形を選びます。

1. **hook（コマンド）**：毎回必ず行う、機械的に判定できる確認や整形。
   エージェントの文脈に依存しない決定的な処理は、コマンドにします。速く、追加の費用がかかりません。
2. **スクリプト、テスト、lint の規則**：コードで検査できる約束事。
3. **skill**：手順のある、繰り返し使う作業。
4. **steering**：プロジェクトの標準や方針、前提知識。
5. **agent**：使えるツールや権限を変える必要があるとき。応答の仕方を変えるだけなら steering を使います。
6. **MCP**：不足している機能があり、既存のツールで満たせないときだけ。

hook のエージェントプロンプト型は、文脈に応じた判断が要るときだけ使います。費用がかかり、遅くなります。

## steering の案

- 1ファイルに1つの領域（API 設計、テスト、デプロイなど）。内容が分かるファイル名にします。
- 決まりだけでなく、理由を書きます。良い例と悪い例を添えます。
- README に既にある内容を重複させません。
- API キーやパスワードなどの秘密値を書きません。
- 読み込みの条件を、内容に合わせて選びます。ファイルの先頭の front matter で指定します。

| `inclusion` | 使う場面 |
|---|---|
| `always`（既定） | すべての作業に関わる中核の標準だけ |
| `fileMatch` と `fileMatchPattern` | 特定の種類のファイルを扱うときだけ要る決まり |
| `auto` と `name`、`description` | 依頼の内容に応じて要る決まり |
| `manual` | 必要なときに人が `#名前` で呼ぶ資料 |

- `AGENTS.md` は読み込みの条件を指定できず、常に読み込まれます。
- 常時読み込みを増やす案には、その内容がすべての作業に要る理由を添えます。要らないなら条件付きにします。
- 集約の「steering の重さ」に、ファイルごとの文字数と、常時読み込みの合計が出ます。
  合計の目安は 8,000 文字です（最初の値で、使いながら調整します）。超えているときは、足す前に減らす案を先に検討します。

## skill の案

- 説明文に、何をするかと、いつ使うかを書きます。依頼に出てくる言葉を入れます。
  良い例：「プルリクエストをセキュリティの観点でレビューする。PR のレビューを頼まれたときに使う」。悪い例：「コードレビューを手伝う」。
- `SKILL.md` は手順に絞ります。詳しい資料は `references/` に、決定的な処理は `scripts/` に置きます。
- 名前はフォルダ名と同じにします（小文字、数字、ハイフン）。
- プロジェクト内の skill は、同名のユーザー共通の skill より優先されます。

## hook の案

- 1つの hook に1つの仕事。
- 対象を絞ります。ツールの種類やファイルのパターンを指定し、すべての操作で動かしません。
- 速く終わるようにし、タイムアウトを設定します（既定は60秒）。
- 入力を検証します。まず狭い対象で試してから広げます。
- 終了コード 0 の標準出力はエージェントの文脈に入ります。出力は必要なものだけにします。

## agent の案

- ツールと権限は、その役割に要る範囲に絞ります。
- 確認なしで許可するのは、信頼できる操作だけにします。
- steering や skill を使わせるなら、`resources` に明示します。

## 案を出す前の確認

カスタムエージェントの継承設定は [公式リファレンス](https://kiro.dev/docs/custom-agents/configuration-reference/#disabling-default-resource-inheritance) に従います。既定の継承を無効化する設定はCLIのグローバルまたはワークスペース単位です。設定や実際の読み込みを確認できなければ、その範囲は未確認とします。

- 根拠は、原則として2つ以上の別のセッションにあるか。
- 既存の決まりと重複や矛盾が無いか。
- 足すより、既存の修正・統合・削除で済まないか。
- その案が不要になる条件を書いたか。
- 期待する効果を、あとで確かめる方法があるか。
- テストコマンドの変更は、ランナーのJUnit生成、kirokuの検出設定、現在の権限と合わせて確認したか。コマンドの起動成功と、テスト結果の記録成功は別に確かめる。
- 所在や回数は集約の検証値と一致しているか。未確認の原因は未確認としているか。
