# ハーネスの改善案を作るときの手引き

Kiro の公式ドキュメント（kiro.dev/docs の Steering、Skills、Hooks、Custom agents）に書かれている使い分けと推奨を、改善案の判断に使える形でまとめたものです。

## 既存の決まりが効かなかった理由を切り分ける

同じ趣旨の決まりが既にあるのに繰り返されている場合は、足す前に次を確かめます。

| 理由 | 確かめること | 案の方向 |
|---|---|---|
| 読み込まれていない | steering の `inclusion` が `manual` や `fileMatch` で、その場面では対象外だった | 読み込みの条件を直す |
| カスタムエージェントに渡っていない | 現行CLIのカスタムエージェントは既定でsteering・skills・AGENTS.mdを継承する。`chat.disableInheritingDefaultResources`、読み込み条件、明示した`resources`を確認し、渡っていない根拠があるか | 継承や条件の不一致を直す。`resources`の未記載だけでは追加を提案しない |
| skill が呼ばれていない | 説明文（`description`）が曖昧で、依頼の言い方と合わない | 説明文を「何をするか」と「いつ使うか」が分かる形に直す |
| 上書きされている | プロジェクト内とユーザー共通で矛盾している。矛盾したときはプロジェクト内が優先される | 片方に寄せる |
| 文面が曖昧 | 何をすればよいかが具体的でない、理由や例が無い | 文面を具体的にし、理由と例を足す |
| 埋もれている | 常時読み込みの steering が長く、多くの話題が混ざっている | 分割し、条件付きの読み込みに移す |
| 実行できない | 決まりが求める操作を、権限や環境が許していない | 決まりか権限のどちらかを直す |
| 文章では守れない | 毎回必ず行う機械的な確認を、文章で頼んでいる | hook やスクリプトに移す |

## 形を選ぶ

上にあるものほど確実です。型の性質に合う、いちばん上の形を選びます。

1. **hook（コマンド）**：毎回必ず行う、機械的に判定できる確認や整形。
   エージェントの文脈に依存しない決定的な処理は、コマンドにします。速く、追加の費用がかかりません。
2. **スクリプト、テスト、lint の規則**：コードで検査できる約束事。
3. **skill**：手順のある、繰り返し使う作業。
4. **steering**：プロジェクトの標準や方針、前提知識。
5. **agent**：使えるツールや権限を変える必要があるとき。応答の仕方を変えるだけなら steering を使います。
6. **MCP**：不足している機能があり、既存のツールで満たせないときだけ。

hook のエージェントプロンプト型は、文脈に応じた判断が要るときだけ使います。費用がかかり、遅くなります。

## steering の案

- 1ファイルに1つの領域（API 設計、テスト、デプロイなど）。内容が分かるファイル名にします。
- 決まりだけでなく、理由を書きます。良い例と悪い例を添えます。
- README に既にある内容を重複させません。
- API キーやパスワードなどの秘密値を書きません。
- 読み込みの条件を、内容に合わせて選びます。ファイルの先頭の front matter で指定します。

| `inclusion` | 使う場面 |
|---|---|
| `always`（既定） | すべての作業に関わる中核の標準だけ |
| `fileMatch` と `fileMatchPattern` | 特定の種類のファイルを扱うときだけ要る決まり |
| `auto` と `name`、`description` | 依頼の内容に応じて要る決まり |
| `manual` | 必要なときに人が `#名前` で呼ぶ資料 |

- `AGENTS.md` は読み込みの条件を指定できず、常に読み込まれます。リポジトリ直下だけでなく、サブディレクトリの `AGENTS.md` も同じです（集約の「steering の重さ」に出ます）。
- 常時読み込みを増やす案には、その内容がすべての作業に要る理由を添えます。要らないなら条件付きにします。
- 集約の「steering の重さ」に、ファイルごとの文字数と、常時読み込みの合計が出ます。
  合計の目安は 8,000 文字です（最初の値で、使いながら調整します）。超えているときは、足す前に減らす案を先に検討します。

## skill の案

- 説明文に、何をするかと、いつ使うかを書きます。依頼に出てくる言葉を入れます。
  良い例：「プルリクエストをセキュリティの観点でレビューする。PR のレビューを頼まれたときに使う」。悪い例：「コードレビューを手伝う」。
- `SKILL.md` は手順に絞ります。詳しい資料は `references/` に、決定的な処理は `scripts/` に置きます。
- 名前はフォルダ名と同じにします（小文字、数字、ハイフン）。
- プロジェクト内の skill は、同名のユーザー共通の skill より優先されます。

## hook の案

- 1つの hook に1つの仕事。
- 対象を絞ります。ツールの種類やファイルのパターンを指定し、すべての操作で動かしません。
- 速く終わるようにし、タイムアウトを設定します（既定は60秒）。
- 入力を検証します。まず狭い対象で試してから広げます。
- 終了コード 0 の標準出力はエージェントの文脈に入ります。出力は必要なものだけにします。

## agent の案

- ツールと権限は、その役割に要る範囲に絞ります。
- 確認なしで許可するのは、信頼できる操作だけにします。
- steering や skill を使わせるなら、`resources` に明示します。

## 一歩先の案

個別の事例に決まりを1行ずつ足していくと、ハーネスは膨らみ、同じ種類の手間は残ります。
一歩先の案は、観測した事例より一段上で、ある種類の手間をまるごと無くす案です。

ハーネスは、事前の案内（steering、skill など）と、事後の検査（テスト、lint、hook など）の組で考えます。案内だけだと「決まりを書いたが効いたか分からない」、検査だけだと「同じ誤りを繰り返す」ことになります（[Böckeler, Harness engineering](https://martinfowler.com/articles/harness-engineering.html)）。

### 改善の段

| 段 | 何をするか | 例 |
|---|---|---|
| 1. 事例に対処する | 起きた事例について、決まりを足す・直す | 「make test で」と2回言い直した → testing.md に1行足す |
| 2. 種類ごと無くす | 同じ種類の手間を、仕組みで無くす | 決まりを検査に上げる。手順を skill にする |
| 3. 起きにくい環境にする | 自分で確かめられ、早く気づけ、ハーネスが古びない | 終了時にテストを実行して結果を返す hook |

### 8つの観点

| ID | 観点 | きっかけ（型・診断値） | 案の形 |
|---|---|---|---|
| V1 | まとめる | 2つ以上の型が、同じ作業・同じファイル・同じ欠けた仕組みから来ている | 1つの仕組みで複数の型を無くす。重なる個別の案は、この案に置き換える |
| V2 | 決まりを仕組みに上げる | 決まりがあるのに守られない型。毎回機械的に判定できる決まり | hook、テスト、lint。仕組みにした決まりの文章は、削るか短い参照にする |
| V3 | 確かめる手段を渡す | 完了の報告の後に指摘が来る。確認の手順が文章だけ。利用者が毎回、手作業で確かめている（集約の「手作業の確認」）。テストの記録が無い。`D5` で、書き込みの後にテストを実行したターンが少ない | 通ったか落ちたかを返すコマンド、終了時の hook、テスト |
| V4 | 早く知らせる | 誤りに気づくのが遅い（CI や人のレビューで初めて分かる）。`D5` に保存時・終了時の検査や pre-commit が無い | 保存時・実行前・終了時の検査、pre-commit に前倒しする |
| V5 | 減らす・保つ | `D1`（読み込まれない）、`D2`（参照先が無い。「候補」は行を読んで参照と確かめたものだけ）、`D3`（同じ文）、常時読み込みの合計が目安を超えている | 削る、直す、まとめる、条件付きにする |
| V6 | うまくいった道を残す | 試行錯誤の末に通った手順や、同じ手順を別のセッションで繰り返している | 確かめ方つきの skill |
| V7 | 先回りする | 取り返しのつかない操作に近づいた（実行前に止められた呼び出し、権限による拒否）。1回でもよい | 守りの仕組み（実行前の hook、deny 規則）を確かめる・足す |
| V8 | 引き継ぐ | セッションの始めに、今の作業の状態や続きを毎回説明し直している（決まりではなく、状態にあたるもの） | 進み具合のファイル、セッション開始時に状態を渡す hook。steering には書き足さない |

### 観点ごとの原則

- **V1**：同じ問題が繰り返すなら、案内か検査を良くして、起きにくくするか、起きないようにする（Böckeler）。結果を、手順や決まりのどの要素に帰すかを決めてから改訂する（[GEPA](https://arxiv.org/abs/2507.19457)）。
- **V2**：決まりの文を強調しても守られないなら、その決まりは hook に移す。hook は、例外の無い決まりだけにする（[Claude Code のベストプラクティス](https://code.claude.com/docs/en/best-practices)）。文章の決まりを lint の規則にし、文書の行は短い参照にする（[codemyrules](https://github.com/clirimajeti/codemyrules)）。
- **V3**：通ったか落ちたかを返す、実行できるものを渡す（Claude Code のベストプラクティス）。テストの道具を渡すと、エージェントの性能が大きく上がった（[Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。
- **V4**：安い検査は早い段階（変更の直後、コミットの前）に置く（Böckeler の keep quality left）。pre-commit が無いと、5秒で得られる結果を CI で10分待つ（[Factory, Agent Readiness](https://factory.com/news/agent-readiness)）。
- **V5**：望む結果に要る、最小の情報だけを常に読ませる（[Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。コードを読めば分かることは書かない（Claude Code のベストプラクティス）。文書がもう支えられていない記述（存在しないパス、当たらない読み込み条件）を見つけて直す（[driftlint](https://github.com/alifurkangokce/driftlint)）。
- **V6**：試行錯誤の末に通った手順は、繰り返す前に skill にする。昇格の条件は、通った確認、名前のある失敗の型、除外した行き止まり（[self-learning-skills](https://github.com/Kulaxyz/self-learning-skills)）。
- **V7**：1回で案にしてよいのは、取り返しのつかない操作に関わるときだけ（kiroku の判断で、出典は無い）。
- **V8**：作業の進み具合をファイルと git の履歴に残し、次のセッションの始めに読む（Anthropic, Effective harnesses for long-running agents）。

### 書くときの注意

- 手がかりには、集約にある型か診断値を、必ず1つ以上書きます。比べたハーネスの表のファイル（文書に書かれた手作業の確認など）も手がかりにできます。そのときは、そのファイルからの引用（`引用（ファイル）：`…`「…」`）を、その案に書きます。
- 段が上がらない案は、一歩先の案にしません。
- 価値は「誰のどんな手間が減るか」で書きます。量は、集約の「型ごとの負担」（`D6`）の値をそのまま使います。
- 一歩先の案で置き換えた個別の案は、別に書きません。案の数を増やさず、減らします。
- テストや CI の設定を変える案は、今の実行方法（README、ランナー、kiroku のテストの記録設定）と合わせて書きます。

## 利用者に聞くときの言い換え

手順5で利用者に聞くときに使います。利用者は、プログラマーとは限りません。質問の本文では、言い換えを先に書き、カッコで元の言葉を添えます（例：「決まった場面で自動で動く設定（hook）」）。言い換えで足りないときは、公式資料のリンクを添えます。

| 言葉 | 短い言い換え | 公式資料 |
|---|---|---|
| steering | Kiro に、いつも守ってほしい決まりや前提を書いておくファイル | [Steering](https://kiro.dev/docs/steering/) |
| hook | ファイルの保存や作業の終わりなど、決まった場面で自動で動く設定 | [Hooks](https://kiro.dev/docs/hooks/) |
| skill | 決まった手順をまとめ、`/名前` で呼び出せるようにしたもの | [Agent Skills](https://kiro.dev/docs/skills/) |
| エージェント | 使えるツールや権限を、作業ごとに決めた Kiro の設定 | [Custom agents の設定](https://kiro.dev/docs/custom-agents/configuration-reference/) |
| MCP | Kiro に、外のツールやサービスをつなぐ仕組み | [MCP](https://kiro.dev/docs/mcp/) |
| pre-commit | コミットする前に、自動で検査を動かす仕組み（git の hook） | [githooks](https://git-scm.com/docs/githooks) |
| CI | push したときに、別の場所で自動でテストや検査を動かす仕組み（GitHub Actions など） | — |
| lint | 書き方の誤りや、決まりへの違反を、自動で見つける道具 | — |
| テスト | コードが期待どおりに動くかを、自動で確かめるプログラム | — |

## 手作業の確認から、合格条件を聞く

利用者が毎回、自分の目で確かめていること（集約の「手作業の確認」、またはハーネスの文書に書かれた、人が行う確認の手順）は、何が一致すれば良いかが分かれば、自動にできることがあります。その条件は利用者だけが知っているので、手順5で聞きます。

```text
Q<番号>. <何>を、毎回目で確かめています。何が一致すれば、確認済みにできますか。人が見たい例外はありますか？
<観測したこと（`topic:…` やファイルのパス）と、聞く理由>
  a. 条件を書く（自由に書いてください）→ その条件を照合する仕組み（テスト、スクリプト、終了時の hook）の案を出す
  b. 毎回、人が見る必要がある → 自動にしない。人が見る理由を決まりに残す案だけを出す
  c. わからない → 様子見にする
  d. その他（自由に書いてください）
見立て：<選択肢の記号>。<理由を1文で>
```

- 例：「通常分は合計が一致すればよい。返金だけは人が見る」→ 通常分の照合を自動にし、返金だけを人に知らせる案（V3「確かめる手段を渡す」）。
- 案が確かめる対象は、利用者が実際に目で見ているもの（その月の実データ、実際の出力）です。既存のテストが固定の例で似た条件を確かめていても、利用者が見ているものを確かめていなければ、確認済みとはみなしません。そのテストは、案の材料（流用できる部分）として書きます。
- 条件の一部だけでも、自動にできる部分があれば案にします。残りは、人が見る理由と一緒に書きます。
- 合格条件を、推測で埋めません。答えが無ければ、様子見にします。
- 「b」の答えは、次の振り返りの「前回までの回答」に出ます。新しい観測が無ければ、聞き直しません。

## 毎回の承認から、許可の規則を提案する

集約の「承認の記録」は、開発のセッションで、人が承認画面に答えた呼び出しを数えたものです。回数は聞くきっかけで、許可にする理由ではありません。わざと毎回確かめている操作もあるので、手順5で聞きます。

### 危険の区分

区分は、スクリプトがコマンドの文面から決めます（利用者の発話ではありません）。つないだコマンドは、いちばん危ないものを取ります。

| 区分 | 例 | 扱い |
|---|---|---|
| 読み取り | `git status`、`git diff`、`git log`、`ls`、`cat`、`grep` | 許可の候補になる |
| 手元の検査 | テストの記録設定に当たるコマンド、lint、型検査、ビルド | 許可の候補になる |
| 手元の書き換え | `git add`、`git commit`、`mkdir`、`mv`、`cp` | 許可の候補になる（質問で確かめる） |
| 外に出る | `git push`、`git pull`、`curl`、`wget`、`gh`、`npm install`、`pip install`、`npm publish`、`docker push`、`ssh` | 候補にしない |
| 任意のコードの実行 | `python -c`、`bash -c`、`node -e`、`eval`、`npx`、`docker exec`、`docker run`、`find -exec` | 候補にしない |
| 取り返しがつかない | `rm -rf`、`git reset --hard`、`git push --force`、`git clean -f`、`sudo`、`chmod -R 777`、`kill` | 候補にせず、deny の案の候補にする |
| 区分を決められない | 上のどれにも当たらない（`python3 scripts/x.py` など） | 許可の候補になる。中身を読み、要らなければ外す |

出典：Kiro の deny の例（`rm -rf *`、`sudo *`。[Permissions](https://kiro.dev/docs/permissions/)）、Claude Code の「任意のコードを実行できるものは許可の一覧から外す」（`/fewer-permission-prompts`。[Commands](https://code.claude.com/docs/en/commands)）、[oliver-kriska/claude-elixir-phoenix](https://github.com/oliver-kriska/claude-elixir-phoenix) の `phx:permissions`（取り返しのつかない操作は、決して自動で許可しない）。

### 聞き方

```text
Q<番号>. `<見出し>` を、毎回確かめたいですか。それとも、自動で通してよいですか？
<承認の回数、セッション数、最後に承認した日（集約の値）と、区分>
  a. 自動で通してよい → 許可の規則の案を出す
  b. 毎回確かめたい → 出さない
  c. わからない → 様子見にする
  d. その他（自由に書いてください）
見立て：<選択肢の記号>。<理由を1文で>
```

### 案の書き方

- 対象の型は `approval:<見出し>` にします。採用した後に、その承認が減ったかを数えて追います。
- 規則は、集約の「規則の案」をそのまま使います。観測したコマンドの違いを覆う、いちばん狭い段（完全一致、2語＋`*`、1語＋`*`）で、危険な変形には当たらないことをスクリプトが確かめたものです。「規則の案なし」のものは、規則を作らず、理由を書きます。`*` だけの規則と、引数まで絞る規則は書きません。
- 当たる例と、当たらない例を、集約のとおりに添えます。
- 主な反映のしかた：「次にこの承認画面が出たら、Always allow を選び、段は〇〇、範囲は This workspace を選ぶ」。ファイルの編集は要りません。This workspace の規則は、ワークスペースの規則のファイル（集約に出るパス、`~/.kiro/workspace-roots/<hash>/permissions.yaml`）に保存されます。利用者ごとで、リポジトリには入りません。対象のファイルには、このパスを書きます。
- チームで共有したいときのために、リポジトリの中のエージェント定義の `permissions` に書く形も添えます（例：`{"capability": "shell", "match": ["git diff", "git diff *"], "effect": "allow"}`）。
- deny の案には、当たらない書き方が残ることを書きます（例：`git push --force *` を止めても、`git -C . push --force` は当たらない）。deny は守りの境界ではありません。
- 区分を決められない承認が多いときは、Approve for me（規則で決まらない操作を、LLM の判定で通す・止める・聞く）を、注意（有料で、判定の費用がかかる。「セキュリティの仕組みの代わりにはならない」）つきで紹介できます。決まった規則（狭い allow と deny）を先に勧めます（[Approve for me](https://kiro.dev/blog/introducing-approve-for-me/)）。
- 承認画面で Always allow を選ぶと、ログの答えは `selectedOption=always-accept` になり、範囲は `_meta.kiro.consentOutcome.scope` に残ります（CLI 3.5.0 で実測）。This workspace の規則は、ワークスペースの規則のファイルに `capability: shell`、`effect: allow`、`match: ["git diff *"]` の形で保存されました。
- 規則の当たり方は、Kiro の資料の書き方（`*` は任意の文字の並び、つないだコマンドは分けて判定）を kiroku が近似したものです。CLI 3.5.0 では、`git diff *` を保存した後、`git diff --stat` と `git diff --stat && git status` は画面が出ず、`git -C . diff` は出ました。引数の無い `git diff` も出ませんでしたが、保存前の対照が無いので、`git diff *` が当たったのかは確かめていません。案にも、確かめていない部分を書きます。
- 既定の権限では、`git status`、`git log` のような読み取りの git のコマンドに承認画面が出ませんでした（CLI 3.5.0）。そのため、読み取りの git のコマンドは、承認の記録にあまり出ません。

## 案を出す前の確認

カスタムエージェントの継承設定は [公式リファレンス](https://kiro.dev/docs/custom-agents/configuration-reference/#disabling-default-resource-inheritance) に従います。既定の継承を無効化する設定はCLIのグローバルまたはワークスペース単位です。設定や実際の読み込みを確認できなければ、その範囲は未確認とします。

- 根拠は、原則として2つ以上の別のセッションにあるか。一歩先の案は、型か診断値が手がかりにあるか（診断値だけでもよい）。
- 既存の決まりと重複や矛盾が無いか。
- 足すより、既存の修正・統合・削除で済まないか。
- その案が不要になる条件を書いたか。
- 期待する効果を、あとで確かめる方法があるか。
- テストコマンドの変更は、ランナーのJUnit生成、kirokuの検出設定、現在の権限と合わせて確認したか。コマンドの起動成功と、テスト結果の記録成功は別に確かめる。
- 所在や回数は集約の検証値と一致しているか。未確認の原因は未確認としているか。
